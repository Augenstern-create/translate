### 1.6 ORT（W6）的实际情况——D-92 被实测确认

`.build\target\debug\build\ort-sys-*\output` 里的原始构建指令：

```
[ort-sys] [DEBUG] looking for prebuilt binaries matching feature set: (no features)
cargo:rustc-link-search=native=C:\Users\25026\AppData\Local\ort.pyke.io\dfbin\x86_64-pc-windows-msvc\f99aae…98405
cargo:rustc-link-lib=static=onnxruntime
cargo:rustc-link-lib=DirectML
cargo:rustc-link-lib=D3D12 / DXGI / DXCORE / dxguid / shell32
```

三条结论：

1. **默认特征解析到 `directml` 变体**（`f99aae…` 正是 `dist.tsv` 里 `x86_64-pc-windows-msvc+directml` 的 sha256）——
   `docs/31` D-92 的"读代码推断"在真机被确认。
2. 该包提供的是 **静态库** `onnxruntime.lib`（343.3 MB）+ `DirectML.dll`（17.7 MB），链接方式是 `static=onnxruntime`；
   所以 `target\debug\` 下**没有** `onnxruntime.dll`，只有 `DirectML.dll`（我先前按"会多一个 onnxruntime.dll"的猜测是错的）。
3. 因此 **Windows 的 ORT 与 Linux 的 `none`（CPU 静态）不是同一发行变体**：Windows 这套带 DirectML/D3D12 链接，
   即使只用 CPU EP，二进制构成与 Linux 也不同 → **性能数字不可并排算倍数**（ADR-052 口径再加一条）。

模型传输：3 个文件共 **110 MB**（`encoder_model_quantized.onnx` 52,899,742 B / `decoder_model_merged_quantized.onnx`
60,212,804 B / `tokenizer.json` 1,716,196 B），`sha256` 与本机一致（已比对 `encoder` 的哈希 `d3b7912b…`）。
落点 `.build\model-cache\ort-model\`，通过 `P4_ORT_MODEL_DIR` 注入。

## 3. 与原设计的偏差及原因

- **D-108：`cargo fmt --check` 在 Linux 与 Windows 上同时失败——我之前的"基线 PASS"是过期的。**
  原因：`p4_bench.rs` 的一段注释在我后来的编辑中失去了缩进，而我没有重跑 fmt。
  影响：这条同时证明"同一份输入在两个平台给出同样结果"，因此不是平台问题；已修（`aa92f57`）。
  **顺带纠正**：`docs/33` §2 里"W2 应完全一致"的预期是对的，只是当时没跑。
- **D-109：三处 clippy `-D warnings` 只在 Windows 上失败**（`term_grace` 死字段、快照测试的 `path`、
  `assert!(true)`）。原因：写法上"读/用在 `#[cfg(unix)]` 里，字段/变量声明在外"，Linux 上恰好没有告警。
  影响：修法分别是 `cfg_attr(not(unix), allow(dead_code))`（保留字段以维持 `WorkerConfig` 平台对称）、
  把取值移进 cfg 块、删掉无意义断言。**没有**放宽 lint 等级。
- **D-110：5 个 Bergamot 配置用例用 POSIX 绝对路径当夹具（`/snap/abc`）。**
  Windows 上 `/snap/abc/model.bin` 不是绝对路径 → 渲染函数按设计拒绝 → 用例失败。
  处理：`#[cfg(unix)]`。理由不是"跑不过就跳过"，而是 **Bergamot 配置渲染在 Windows 上根本不可达**
  （`ensure_supported()` 返回 `CapabilityUnavailable`），这些用例覆盖的是 Linux 专属路径。
- **D-111：2 个 transport 用例依赖进程隔离 worker 与宿主 RSS。** Windows 上门禁先返回
  `CapabilityUnavailable`，用例在 setup 就失败 → `#[cfg(target_os = "linux")]`。
- **D-112：`worker_process.rs`（17 个）与 `lifecycle.rs`（6 个）整目标限定 Linux。**
  关键理由：这两个文件用 `/proc/<pid>` 判活。Windows 上 `reachable()` 恒为 false，`gone_within()` 会**立刻返回真**，
  于是"进程被杀掉后宿主仍活着"这类断言会**假通过**——比失败更危险。按 ADR-055：宁可记为"未验证"。
- **D-113：`lc08`（安装关键点崩溃后仓库仍可修复）在 Windows 上必然 `LockTimeout`。**
  链路：崩溃子进程留下 `state.lock` → `probe()` 在非 Linux 恒返回 `Unknown` → 保守地视为"仍被占用" →
  `install_from_dir` 等到超时。**这是平台能力缺口，不是仓库逻辑错**：实现 Windows 存活探测
  （`OpenProcess` + `GetExitCodeProcess`）属于 P5.4 的资源管理/故障测试范围，本轮用
  `cfg_attr(windows, ignore = "…")` 记录，Linux 侧继续 real 跑。
- **D-114：三个 Python 工具在 Windows 上会崩在两处编码上（已修）。**
  ① `subprocess.run(text=True)` 用 ANSI（cp936）解码 `cargo/git` 的 UTF-8 输出 → `UnicodeDecodeError`
  （`check-release.py` 直接 traceback 退出）；② 打印含 `U+FFFD` 或中文的行时 stdout 用 cp936 编码 → `UnicodeEncodeError`。
  修法：文本模式显式 `encoding="utf-8", errors="replace"`；启动时 `sys.stdout/stderr.reconfigure(utf-8)`。
  影响：**这类 bug 在 Linux 上永远看不到**，属于"必须到真机才会暴露"的一类。
- **D-115【需要你处置】：ORT 缓存写到了工作区外——`C:\Users\25026\AppData\Local\ort.pyke.io`，360.9 MB。**
  这是 `ort-sys` 的默认行为（下载并解包到 `%LOCALAPPDATA%`），不是我显式指定的路径；出现时间 17:23:54，
  即第一次 `--all-features` 构建时。当前内容：`dfbin\x86_64-pc-windows-msvc\f99aae…\onnxruntime.lib`（343.3 MB）
  与同目录 `DirectML.dll`（17.7 MB）。**这违反了 ADR-057 的"工作区外只读"**，虽然是无意的、且可复现地由工具决定。
  处置选项：① 保留（下次构建免下载，但它确实在工作区外）；② 删除（我再重建时会再写一次，除非找到重定向变量）；
  ③ 我先查 `ort-sys` 是否支持把缓存重定向到工作区（如 `ORT_DFBIN_CACHE` 之类），确认后再决定。**在你决定前我不动它。**
- **D-116：D-92 由"读码推断"升级为"真机实测"，且细节要更正两处。**
  实测：默认特征 → `directml` 静态包；产物**没有** `onnxruntime.dll`（静态链接进 exe），但会复制 `DirectML.dll`；
  缓存目录不在 `target/` 而在 `%LOCALAPPDATA%`（见 D-115）。影响：Windows ORT 与 Linux 的 `none` 变体
  **二进制构成不同，性能不可并排**；`docs/31` §1.1 里"会多出 onnxruntime.dll"的说法作废。
- **D-117：Windows 的测试计数口径必须成文**（ADR-058）。322 vs 372 不是"覆盖率掉了"，而是
  Linux 专属用例被显式 gate；报告里必须同时给两个数并解释差值，否则下一个人会以为 Windows 少测了 50 个功能。

## 5. 复现命令（含本轮踩到的坑）
