## 2. P7 的目标与非目标

### 2.1 目标

1. 保持 `translator-api` 和 JNI v1 的四个导出入口稳定：`nativeProtocolVersion`、`nativeCreate`、`nativeCall`、`nativeClose`。
2. 把 P6 的未完成安全与生命周期测试做成**可复现、可比较、不会因平台差异假绿**的自动化矩阵。
3. 做好 Linux 与 Windows 的构建/包清单、模型与词库来源、许可证审计、哈希、可回滚发行准备。
4. 明确 Android 的交付边界：模拟器可运行 SDK 绑定，但无真实 Android NMT 及 ARM64 运行证据。
5. 保持资源、推理 Runtime、词库、语言规则、LLM Provider 的可替换插件契约；P7 不因发行需要把某后端写死到核心。
6. 验收报告坚持三分口径：**工作包交付／门禁闭合／候选可用性**。

### 2.2 非目标

- 不开发 UI、OCR、语音、完整 Android 应用或远程 LLM 新产品功能。
- 不以 P7 为名重写 `TranslationEngine`/`InferenceBackend`/`DictionaryProvider`；任何 API 破坏性变更单独 ADR 与大版本决策。
- 不将 Android ARM64 交叉编译当作可运行，不将 x86_64 AVD 性能当作物理手机性能。
- 不自动下载或打包模型权重；模型再分发许可证未明确前不发布含权重的安装包。
- 不绕开现有五条 release blocker，不用跳过测试换取全绿。

## 3. 技术边界与插件化约束

```text
Host / UI / CLI / Java-Kotlin
       |
       +--- translator-api ------------------------+
       |                                           |
       +--- translator-jni (ABI v1)                |
                |                                  |
                v                                  v
         Translator Facade --> Coordinator --> Plugin Registry
                                      |      |      |
                               Dictionary  NMT  Remote LLM
                                      |      |      |
                                      +--- Resource & Model Manager
                                                   |
                                   Versioned dictionary/rules/model packages

Platform modules: Linux / Windows / Android adapters
NMT backends: Bergamot worker (Linux verified) / ORT / future ncnn or Burn
```

- `translator-api` 不依赖 JNI、Android、Gradle、Tauri 或模型特定 C++ 类型。
- JNI 的业务方法通过 `nativeCall(method, payload)` 扩展；新增字段应保持向后兼容，不能悄悄改变 `protocol_version=1` 的既有语义。
- `AlreadyClosed` 是 JNI 绑定层错误，SDK 核心仍按现有 12 个业务错误码；测试必须同时验证两种错误空间。
- 资源内容身份不得只靠用户可重用的 `id@version` 猜测；复用、安装和缓存应采用已有的 revision/digest 机制，按实际已实现状态验证。
- 内存统计要分宿主进程与推理 worker；模拟器 J-14 的进程级值只能作为模拟器基线。

## 4. 实施计划

### P7.0 — 冻结基线、权限预检、测试矩阵

**交付**：`docs/43_P7.0_基线与测试矩阵报告.md`（建议文件名）；完整依赖/feature/ABI 状态清单。

- 记录 commit/tag、Rust/NDK/ORT/JNI 版本、模型资源 revision、测试设备及模拟器配置。
- 核对 Windows 的 `E:\augenstern\translate`、`D:\Anaconda3\python.exe`、`.build` 与 `.cargo` 定向；确认 `ORT_CACHE_DIR` 只指向工作区。
- Linux 侧在**执行前**确认工作副本与缓存均处于已授权路径。不得把旧报告的 `/tmp`、`/opt/rust` 当作本轮默认可写目录。
- 检查 `cargo tree`：核心默认无重型 runtime/JNI 反向依赖；编译期 feature 不意外引入网络或大模型。
- 锁定 J-07/J-10/J-14/J-15 的期望输出、失败码和失败注入方法；建立原始日志与 JSON 汇总 schema。

**Gate 7.0**：无环境越权写入；测试口径冻结；不修改既有 P6 历史报告。

### P7.1 — Android JNI 安全与资源全链路收口

**先做 J-07**（坏资源/路径穿越，优先级高于性能）：

1. 在工作区测试目录构造有合法 SHA/坏 SHA、缺文件、未知 manifest 版本、未知 payload 版本、`../` 路径和符号链接等夹具。
2. 用真实 JNI `nativeCreate`/`nativeCall("resources", ...)` 访问配置的 `resource_repo`；若 v1 只支持只读列表，需先**确认 API 真实提供的操作**，不可凭空调用 install。必要时通过已存在 CLI 安装后再由 JNI 读取。
3. 校验失败必须是稳定 JSON 错误，不出现 JNI panic、路径越界或损坏现有激活版本；自动检查工作区外文件的时间戳不变。
4. 异常清理与回滚后仍能访问旧的有效词库。

**J-10 补充**：超长文本、控制字符、畸形 JSON、超大数组、非法语言标签；对输入长度及 JSON 深度设上限，保持 `InvalidRequest`/可诊断错误，不让 Java 进程 OOM。

**J-15 生命周期**：

- 复用现有 AVD，重复 `create → lookup/translate(mock) → close → create`，测试同句柄并发 close、在飞请求、重复 close、失效 generation。
- 明确区分“SDK 句柄重新创建”和“同一 Android 进程内反复卸载/重新加载 `.so`”：后者通常由 ART 管理，**不应把 `System.loadLibrary` 人工强制卸载当作正常 API**；若报告要求 J-15 证明 `.so` 生命周期，需明确哪些是可测事实、哪些是 Android 类加载器限制，不能给出虚假 PASS。
- 故障注入不得在模拟器系统目录写入；只限经批准的测试私有区或 `/data/local/tmp/p7`。

**Gate 7.1**：J-07 / J-10 / J-15 分开给出 `PASS / PARTIAL / PENDING` 和原始日志；无越界写与 use-after-free。

### P7.2 — Android 模拟器低内存及延迟基线（J-14）

- 同一 x86_64 AVD、同一配置、同一词库、同一 JVM 启动方式，采集 30 次以上单次调用与连续调用数据；固定测试设备和是否热缓存。
- 指标：create 首次、首次 lookup、热 lookup p50/p95、detect p50/p95、close、空闲 RSS、请求峰值 RSS、并发关闭后 RSS；报告采样方法及分辨率。
- 优先读 Android `/proc/<pid>/status` 或 `dumpsys meminfo`（仅在允许的模拟器权限范围内）；记录 Java + native 同一进程口径，必要时拆出 SQLite 映射。
- 明确 JNI v1 默认不加载真实 NMT，因此这里的内存不代表真实 Android NMT 的内存预算。
- 与 `docs/36` 的 CLI 冷启动及 `docs/40` 的 JNI 功能测试分开标注，不比较不同测试形态的绝对数字。
- 避免在模拟器宿主外新增持久缓存；截图/日志放在已授权工作区。

**Gate 7.2**：可复现 JSON/Markdown 基线，含硬件/AVD、样本数、p50/p95、RSS 方法与局限。达不到目标要记录偏差，不得改数字。

### P7.3 — Linux / Windows 回归与构建发行候选

- `cargo fmt --all -- --check`、默认和 `--all-features` 的 test、clippy `-D warnings`、核心反向依赖检查。
- Windows 仍以已授权的项目目录为唯一构建与缓存写入地点；`ORT_CACHE_DIR` 指向 `.build\ort-cache`，`CARGO_HOME`、`CARGO_TARGET_DIR`、`TEMP`/`TMP` 按 P5 已验证配置。
- Linux 的 Bergamot worker 安全边界不退化；Windows `CapabilityUnavailable` 门禁必须保持，不能通过隐藏功能冒充可用。
- 模型/资源包只从确切锁定来源复现，逐文件 SHA-256；记录许可证及权重许可 `pending` 状态。
- 构建产物附加平台、架构、ABI、Rust 版本、feature、backend、runtime 变体信息。Windows ORT DirectML 静态变体与 Linux CPU 静态变体不做绝对速度倍数比较。
- 提供最小 Linux/Windows CLI 示例、JNI v1 Java 用法、资源安装/回滚操作说明；不要求 UI。
- 进行两次隔离构建（条件许可时）比较产物与依赖清单。不可复现时标原因与偏差，不宣称 reproducible。

**Gate 7.3**：P6 基线不回退；不同平台的 skipped/ignored/gated 测试按文件和机制解释。任何新的依赖、系统写入或外部服务变更另行批准。

### P7.4 — 五条发行阻断项专项闭环

**先读取真实台账，再制定逐条解决办法**：`fixtures/release-blockers.json`、相关 ADR、`check-release.py --release-mode` 的当前原始输出。不能仅凭本建议文档将五项改为关闭。

| Blocker | 已知事实 | 要求的动作/证据 |
|---|---|---|
| G12 | 模型权重许可未确认 | 固定具体权重 revision、来源、许可原文、再分发条件和法律/产品决策；确认前权重不随 SDK 分发 |
| G11 | CI 未在真实 runner 运行 | 在获批的 CI/runner 上做可复现构建与回归，保存日志与 commit SHA；未经许可不启用云端 CI 或上传代码 |
| G06 | 当前两份报告未说明内容 | **从阻断台账读取定义**后确定修复与证据；保持 open |
| G08 | 当前两份报告未说明内容 | 同上；保持 open |
| D-46 | 当前两份报告未说明内容 | 同上；保持 open |

- 对每个 blocker 写“原始问题 → 修复/豁免理由 → 可复现证据 → 审核人 → 日期”。
- 当任何 blocker 未关闭时，`--release-mode` 继续 FAIL，不能将该 FAIL 改成 warning。
- 如许可或 CI 条件暂时无法解决，可以发布**内部技术预览**（不含不确定权重），但不能称为已通过正式发行门禁。

**Gate 7.4**：每一项保持 `open` 或有独立验证记录转 `closed`；不允许“一键全过”。

### P7.5 — 发行候选、安全审计与验收报告

- 产出版本化 SDK 工件、SHA-256、依赖 SBOM/第三方许可证报告、`README`/API 示例、迁移说明、支持矩阵。
- 发布能力声明按组合：Linux 完整验证项、Windows ORT 能力、Android JNI 词典/路由/资源、未验证的 Android ARM64 和真实 Android NMT。
- 对模型与词典再分发单列审核；不因代码库许可证允许商业使用而推定权重/数据也可分发。
- 记录冷/热加载、实际 RSS、异常恢复、原生 worker 崩溃隔离、资源租约回滚在**各自已验证平台**的证据。
- `docs/4x_P7阶段总结与验收报告.md`（编号需先核对实际仓库是否占用）使用 ADR-051 的三分口径，列所有 `pending`。

**Gate 7.5**：只有发版阻断全闭合且工件/许可/测试齐备才是 `Release Ready`；否则最多为 `Conditional / Internal Preview`。

## 6. 权限与环境执行规范（硬约束）

### Windows

- 唯一默认可写路径：`E:\augenstern\translate`；项目内 `.build/`、`.cargo/`、日志、模型缓存可写。
- 项目外文件一律只读；**即使是非管理员修改也须审批**，包括删除 `%LOCALAPPDATA%\ort.pyke.io`。
- 不修改 `D:\Anaconda3` 的安装文件；Python 固定调用 `D:\Anaconda3\python.exe`。
- Rust 采用当前已安装、已验证工具链；不得自动 `rustup update` 或写用户级 toolchain 目录。
- 临时代理仅限当前命令或进程；不改注册表、全局 PATH、Defender 或服务。
- 运行 ORT 构建前显式指定 `ORT_CACHE_DIR=E:\augenstern\translate\.build\ort-cache`，并检查其他 toolchain 的写路径；仅设置 `CARGO_TARGET_DIR` 不足以阻止依赖下载器外写。

### Linux / Android 模拟器

- Linux 当前工程副本与构建缓存位置应由执行者在 P7.0 只读确认**是否获授权**；对工作区外任何修改均先征求用户同意。
- 已批准的 Android 模拟器测试数据限测试目录；如扩大到 Gradle、APK、其他 AVD 或系统镜像安装，属于新动作，需要再次批准。
- 绝不要求/使用 Android 物理设备。
- ARM64 AVD 在当前 x86_64 宿主未运行成功，不再次无目的安装新镜像；若以后可用 ARM64 虚拟宿主，仍需先获环境和写入审批。
- 临时外部文件与缓存的清理同样需要审批，不能把 `rm -rf /tmp/...` 视为当然许可。

## 7. 需要另行审批的动作

1. 删除 Windows `%LOCALAPPDATA%\ort.pyke.io` 的旧缓存（约 360.9 MB）；当前**不批准执行**。
2. 删除 Linux 旧 ARM64 镜像和 `arm64api24` AVD（约 3.1 GB）；当前**不批准执行**。
3. 创建/修改工作区外的 Gradle 缓存、用户级 SDK、工具链、全局 Git、注册表与系统配置。
4. 在 GitHub Actions 等外部 CI 运行、上传源码/工件或调整远端仓库设置。
5. 公开发布模型权重或第三方词库包，尤其许可尚未核准者。

2. **可复现测试结果**：命令、工具链、exit code、原始日志、测试数、ignored 理由、指标测量口径。
3. **与原设计偏差及原因**：明确主动取舍、未实现项、下一阶段条件。
4. **权限审计**：工作区外仅阅读还是存在意外写入；管理员操作是否发生；授权来源。
5. **发行状态**：五条阻断项逐项保留真实状态，P7 功能完成不自动等于 release-ready。

## 9. 建议开工顺序与阶段裁定

推荐 **P7.0 → P7.1（J-07/J-10/J-15）→ P7.2（J-14）→ P7.3（双平台回归）→ P7.4（阻断项）→ P7.5（收口）**。
