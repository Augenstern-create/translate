# P5.5 Android 模拟器验证报告

- 日期：2026-11-07
- 阶段：**P5.5**（`docs/32` §5 的 Android 面；按用户 2026-11-07 决定：**只用模拟器，不接真机**）
- 关联：`docs/30`（P5-01 工具链与 JNI 冒烟）、`docs/34`（Windows 侧）、`docs/35`（P5.4）、`docs/01` ADR-055/060
- 一句话结论：**真实 SDK（CLI，含 bundled SQLite、FST 词典、资源仓库、规则管线）在 Android x86_64 模拟器上
  真跑通了；ARM64 的"运行"验证在本机不可得——Android 模拟器明确不支持 arm64 CPU（`QEMU2 emulator does not
  support arm64 CPU architecture`），因此 ARM64 的证据止于**交叉编译 + ELF 合规**，移动端物理设备的性能
  一律标 `未验证`。**

---

## 1. 实际实现内容

### 1.1 用真 SDK 而不是冒烟代码

P5.1 的 JNI 冒烟用的是 20 行手写库，只能证明工具链。本轮换成**项目自己的产物**：
`apps/translator-cli`（依赖 `translator-api` = mocks + dictionary + rules + resource），
不新增 crate、不改任何依赖，直接交叉编译：

```bash
NDK=~/Android/Sdk/ndk/30.0.16248370/toolchains/llvm/prebuilt/linux-x86_64/bin
export CARGO_TARGET_X86_64_LINUX_ANDROID_LINKER=$NDK/x86_64-linux-android21-clang
export CC_x86_64_linux_android=$NDK/x86_64-linux-android21-clang
export AR_x86_64_linux_android=$NDK/llvm-ar
cargo build -p translator-cli --target x86_64-linux-android --release   # 58.4 s
```

同一个命令换 `aarch64-linux-android` + `CC_aarch64_linux_android` → **43.0 s**。
关键点：`rusqlite` 用的是 `bundled`（现场编 SQLite 的 C 源码），这两个目标下都由 NDK clang 编过——
**"Android 上没有系统 sqlite3 也能用"这件事是被真编真跑验证的**，不是假设。

| 产物 | 大小 | 类型 | `LOAD` 对齐 | `NEEDED` |
|---|---|---|---|---|
| `x86_64-linux-android/release/translator-cli` | 3,545,080 B | ELF64 PIE, x86-64, `/system/bin/linker64` | **0x4000**（16 KiB） | libdl, libm, libc |
| `aarch64-linux-android/release/translator-cli` | 3,540,456 B | ELF64 PIE, AArch64, `/system/bin/linker64` | **0x4000**（16 KiB） | libdl, libm, libc |

（`llvm-nm | grep -c sqlite3_open` = 3 → SQLite 静态链进二进制，没有外部 `.so` 依赖。）

### 1.3 ARM64：交叉编译通过，运行验证不可得

- 编译：`aarch64-linux-android` 43.0 s 成功，ELF/符号/16 KiB 对齐见 §1.1。
- 运行：
  1. 先查可用镜像 → 装了 `system-images;android-24;default;arm64-v8a`（3.1 GB），建 AVD `arm64api24`；
  2. 用 `-accel off`（宿主是 x86_64，只能全模拟）启动，**模拟器直接拒绝**：

     ```
     FATAL | QEMU2 emulator does not support arm64 CPU architecture
     ```

  3. 结论：**本机无法提供 ARM64 Android 运行环境**。这不是配置问题——新版 Android 模拟器（QEMU2）
     已不再支持跨架构系统模拟；要跑 ARM64 只能靠 aarch64 宿主或真机。
- 因此 ARM64 的运行证据 = **无**；能证明的是"编译合规"（符号、页对齐、无额外 `.so` 依赖）。

### 1.4 明确标注为"未验证"的项（用户要求）

| 项 | 状态 | 原因 |
|---|---|---|
| 真实 Android 设备上的翻译速度 | **未验证** | 无真机；模拟器数字不可外推 |
| 耗电 / 温度 | **未验证** | 模拟器没有这两个量 |
| 峰值内存（物理设备口径） | **未验证** | 模拟器 2.4 GiB 与真机差异大 |
| ARM64 **运行**（功能/兼容性） | **未验证** | 本机模拟器不支持 arm64 CPU |
| JNI 承载真实 SDK（非冒烟库） | **未做** | 见下 |

> **JNI 的边界要说清**：P5.1 的 JNI 冒烟证明的是"工具链能产 cdylib 且 ART 能加载"，
> 本轮证明的是"SDK 本体能在 Android 上跑"。**两者都还没有合起来**——把 `translator-api` 包成
> `translator-jni` cdylib 是 P6 的工作（需要 `jni` crate 或裸 JNI vtable + 字符串封送，
> 且要给 `licenses/` 增补依赖条目）。本轮**没有**为此新增 crate 或依赖。

## 2. 可复现的测试结果

```bash
# 1) 交叉编译（两个 ABI）
cd translator-sdk
NDK=~/Android/Sdk/ndk/30.0.16248370/toolchains/llvm/prebuilt/linux-x86_64/bin
CARGO_TARGET_X86_64_LINUX_ANDROID_LINKER=$NDK/x86_64-linux-android21-clang \
CC_x86_64_linux_android=$NDK/x86_64-linux-android21-clang \
AR_x86_64_linux_android=$NDK/llvm-ar \
  cargo build -p translator-cli --target x86_64-linux-android --release      # 58.4 s

CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER=$NDK/aarch64-linux-android21-clang \
CC_aarch64_linux_android=$NDK/aarch64-linux-android21-clang \
AR_aarch64_linux_android=$NDK/llvm-ar \
  cargo build -p translator-cli --target aarch64-linux-android --release     # 43.0 s

# 2) ELF 合规
$NDK/llvm-readelf -h  target/aarch64-linux-android/release/translator-cli   # ELF64 / AArch64 / DYN
$NDK/llvm-readelf -l  target/aarch64-linux-android/release/translator-cli | grep '^  LOAD'   # 0x4000
$NDK/llvm-readelf -d  target/aarch64-linux-android/release/translator-cli | grep NEEDED      # libdl/libm/libc

# 3) 模拟器上真跑
adb push target/x86_64-linux-android/release/translator-cli /data/local/tmp/
adb shell "chmod +x /data/local/tmp/translator-cli"
adb shell "/data/local/tmp/translator-cli capabilities"
adb shell "/data/local/tmp/translator-cli detect '你好世界'"
adb shell "/data/local/tmp/translator-cli --dict /data/local/tmp/dictpkg lookup 你好"
adb shell "cd /data/local/tmp && ./translator-cli resource install ./dictpkg"
adb shell "cd /data/local/tmp && ./translator-cli resource audit"
adb shell "cd /data/local/tmp && ./translator-cli resource uninstall dictionary.test.zh-en 0.1.0"   # 必须被拒

# 4) ARM64 运行尝试（预期失败，作为证据）
~/Android/Sdk/cmdline-tools/latest/bin/sdkmanager --install "system-images;android-24;default;arm64-v8a"
echo no | ~/Android/Sdk/cmdline-tools/latest/bin/avdmanager create avd -n arm64api24 \
  -k "system-images;android-24;default;arm64-v8a" --force
~/Android/Sdk/emulator/emulator -avd arm64api24 -no-window -no-audio -no-snapshot -no-boot-anim \
  -gpu swiftshader_indirect -accel off -port 5556
# → FATAL | QEMU2 emulator does not support arm64 CPU architecture
```

| 检查项 | 结果 |
|---|---|
| CLI 交叉编译（x86_64 / aarch64） | PASS（58.4 s / 43.0 s，含 boundled SQLite 的 C 编译） |
| ARM64 ELF 合规（类型/机别/16 KiB/依赖） | PASS |
| x86_64 AVD 上跑真 SDK（能力表/识别/翻译/词典/资源） | PASS |
| 资源不变量（激活版本拒绝卸载、audit 三方一致） | PASS |
| 规则管线可运行 | PASS（但改写正确性不可由 mock 证明，D-126） |
| ARM64 运行 | **不可得**（模拟器不支持 arm64 CPU） |
| 物理设备性能（速度/耗电/温度/峰值内存） | **未验证**（用户已同意不以真机为必过条件） |

## 3. 与原设计的偏差及原因

- **D-125：Android 证据从"JNI 冒烟"升级为"真 SDK 跑在 ART 上"，但没有 JNI 承载 SDK。**
  原因：时间与范围——把 `translator-api` 包成 cdylib 需要 `jni` crate（新依赖 + 许可证条目）或手写
  JNI vtable 的字符串封送。影响：`docs/01` §13 里"ARM64 JNI"这一交付面**仍只满足一半**
  （工具链 JNI ✅ / SDK 级 JNI ❌），已列入 P6 pending，不在此处含糊。
- **D-126：规则（保护跨度）在 Android 上只有"能跑"级证据。**
  原因：CLI 的 mock NMT 是回显引擎，无论规则是否生效输出都一样。影响：规则正确性仍以
  Linux/Windows 上的单测为准（`translator-rules` 与 `protect-seg-v1` 的用例），Android 侧写
  "管线可运行、正确性未单独验证"。
- **D-127：ARM64 的"虚拟环境"路线在本机被证伪，不是"没试"。**
  原因：`QEMU2 emulator does not support arm64 CPU architecture`（新版模拟器只支持与宿主同架构的系统镜像）。
  影响：`docs/32` 的"如果能在虚拟机里运行 ARM64 系统就继续做"这条**在本机不可能**；ARM64 运行证据
  只能等 aarch64 宿主或真机。安装了 3.1 GB 的 arm64 镜像（`system-images;android-24;default;arm64-v8a`）
  与 AVD `arm64api24` 作为尝试痕迹保留，未删除（都在 `~/Android/Sdk`、`~/.android` 这两个既有目录内，
  属本机既有工具链目录，不是项目工作区；是否清理由你决定）。
- **D-128：性能数字只给模拟器口径，且明确不可外推。**
  `capabilities` 16-17 ms 是 KVM 加速的 x86_64 模拟器上的冷启动，**不能**当作移动端性能。
  这与 ADR-052（数字必须带口径）和 ADR-054（证据分层）一致：模拟器 = 功能证据，不是性能证据。
- **D-129：本轮在 Linux 宿主上操作 Android 工具链，没有碰 Windows 工作区。**
  原因：NDK/AVD 在这台 Linux 机器上（`docs/30` §1）。影响：Windows 侧的 Android 交叉编译仍未验证
  （本来也不在 P5 范围：`docs/32` §4.2 明确"不在 Windows 上装 NDK"）。
