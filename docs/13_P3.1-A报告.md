## 0. 一句话结论与本轮边界

**P3.1-A 的验收对象是"进程边界能不能扛住 native 崩溃"，不是"真实模型能不能翻译"。**

本轮新增 crate `translator-runtime`，实现了：

1. `RuntimeTransport` trait + 基于**子进程**的 `ProcessTransport`；
2. 长度前缀帧协议（上限 8 MiB、版本号强制、帧坏可识别）、`request_id` + `worker epoch` + `model revision` 关联；
3. spawn / 请求超时 / 三级终止（shutdown 帧 → SIGTERM → SIGKILL）/ 无僵尸 / 受控重启用预算；
4. 加载前四文件校验（存在、非符号链接、大小、流式 SHA-256）与 `content_digest`；
5. 失败路径 → 对外错误码映射（逐条对应 `docs/12` §3.2 的表）；
6. `nmt-worker --mock`：可以真的 `abort()`、真的超时、真的吐坏帧的假 worker。

**没有做的（很重要）**：真实 Bergamot 接线（P3.1-B）、占位符保护（P3.1-C）、single-flight/租约/`ResolvedExecutionPlan`（P3.1-D）、Linux CI（P3.1-E）、`translator-api` 接线。

因此本报告**不能**用来佐证"真实模型已经能在 Rust SDK 里安全加载"，也不能用来更新内存预算。内存预算的唯一依据仍然是 `docs/11` 的实测值：**1 线程峰值 413.8 MiB / 2 线程 678.5 MiB**——本轮没有、也不应该改动这个口径，更不会出现"总进程内存 < 400 MB"这类说法。

## 1. 实际实现内容

### 1.1 新增 crate 与文件

```
translator-sdk/crates/translator-runtime/

├── src/lib.rs                # 模块声明与 re-export；crate 级 #![deny(unsafe_code)]
├── src/error.rs              # RuntimeError + 错误码映射 + 可重启性判断
├── src/protocol.rs           # 帧编解码 + Request/Response/Payload/WorkerErrorCode
├── src/model.rs              # FileRole/FileSpec/ModelManifest/ModelSpec + sha256 + RSS 采样
├── src/worker.rs             # 子进程生命周期：spawn / request / 超时 / 三级终止 / stderr 环形缓冲
├── src/transport.rs          # RuntimeTransport trait + ProcessTransport
├── src/bin/nmt-worker.rs     # mock worker（故障注入）

└── examples/p3_1a_evidence.rs# 可复现证据 harness（§2.4）

`translator-sdk/Cargo.toml` 增加 workspace 成员与内部依赖（path-only，不发布）。

### 1.2 进程模型：为什么是进程，不是线程

`docs/12` §2.1 的 P0 是"worker 必须是进程"。本轮把它写进代码注释与测试，而不是写在报告里就算完：

- `docs/11` 记录的两类原生失败是 **`abort()`（SIGABRT）** 与 **截断权重 SIGSEGV**；
- 工作区 release profile 是 `panic = "abort"`，所以 `catch_unwind` 连 Rust 侧的 panic 都拦不住，更不用说 C++ 的 SIGSEGV；
- 因此 `WorkerProcess` 的价值不在"包装"，而在**宿主与 native 不共享地址空间**。

`crates/translator-runtime/src/worker.rs` 的读帧线程、`pending` 表、`dead` 标志都围绕一条不变式：**任何一次读/写/超时异常都必须让 worker 进入"不可再用"状态，并且被回收**。

### 1.3 帧协议（`protocol.rs`）

| 项 | 取值 | 理由 |
|---|---|---|
| 长度前缀 | 4 字节大端 | 译文含换行是常态，按行切会把消息劈成两半 |
| 单帧上限 | 8 MiB | 没有上限的长度前缀 = 把"分配多大内存"的决定权交给对端 |
| 超限处理 | **在任何分配之前**返回 `InvalidData` | 有单测覆盖（`超限的帧在分配前被拒绝`） |
| 载荷 | JSON | 进程边界上可读性比几微秒编码开销值钱；只影响这一个文件 |
| 版本 | `PROTOCOL_VERSION = 1`，请求/响应双向校验 | 不匹配即拒绝，避免"看起来能连" |
| 通道分工 | stdout 只跑帧，stderr 只放诊断 | native 日志绝不能混进协议流 |

消息面：`Load{spec}` / `Translate{text,target}` / `Unload` / `Health` / `Shutdown`；响应为扁平结构（`id`/`epoch`/`protocol`/`ok`/`code`/`message`/`payload`），`payload` 用相邻标签（`type`/`data`）区分 `Loaded`/`Translated`/`Unloaded`/`Health`/`Empty`。

`docs/12` §2.1 要求"response 至少关联 `request_id`、状态码、耗时、worker epoch、model revision"：

- `request_id` → `Response.id`，与 `pending` 表配对；
- 状态码 → `ok` + `WorkerErrorCode`（只有 6 个受控取值，不接受 native 任意字符串）；
- 耗时 → `Payload::Translated.elapsed_ms`（worker 侧计时，不含 IPC）；
- `worker epoch` → 双向字段，宿主在 `request()` 里比对，不符即**丢弃该 worker**；
- `model revision` → `Payload::Loaded.model_revision`（= `content_digest`），随 `TranslationReply` 回到调用方。

### 1.4 worker 生命周期（`worker.rs` + `transport.rs`）

| 关注点 | 实现 |
|---|---|
| spawn | `Command` + 三个 piped 句柄；`spawn` 失败 → `InitFailed`（`RuntimeInitFailed`） |
| 请求超时 | 默认 10 s；超时 → `terminate()` + `Timeout{operation, waited_ms}` |
| 终止升级 | shutdown 帧（等 500 ms）→ `libc::kill(SIGTERM)`（等 500 ms）→ `SIGKILL` → `wait()` 收尸 |
| 僵尸 | 每条路径都会 `wait`/`try_wait`；辅助线程最多等 200 ms，超时**detach 而非 join**，不让宿主卡住 |
| `shutdown()` 幂等 | 重复调用直接返回 `Ok`；之后再发请求 → `CapabilityUnavailable` |
| 重启 | 只在**下一次请求**触发；`restart_budget`（本轮固定 1）用尽 → `CapabilityUnavailable("worker 重启预算耗尽…")` |
| 不静默重放 | 失败的请求**不重试**；崩溃后下一句返回 `RuntimeInitFailed("尚未加载模型…")`，要求显式重新 `load` |
| stderr | 环形缓冲 64 行、每行截断到 512 字节；只用于诊断，永不参与协议 |
| 世代号 | 父进程分配（`epoch` 从 1 递增），worker 原样回带；重启必换 pid 与 epoch |

`unsafe` 只有一处（`libc::kill` 发 SIGTERM），crate 级 `#![deny(unsafe_code)]` + 该函数上的 `#[allow]` + SAFETY 注释。其余全部安全 Rust。

### 1.5 加载前校验（`model.rs`）

`ModelManifest::verify()` 的顺序是刻意的：

1. 四个角色（model / src_vocab / trg_vocab / lex_shortlist）**必须齐全**，缺一即 `IntegrityFailure("模型集合不完整，缺少：…")`；
2. `symlink_metadata` 判断：符号链接直接拒绝（否则"校验的是链接目标、用的是被换掉的目标"）；非普通文件拒绝；
3. 大小比对（便宜的指标先挡住明显不对的输入）；
4. 最后才做流式 SHA-256（256 KiB 缓冲，44 MB 权重不进内存）。

另有 `ModelSpec::verify_paths()` 作为**极便宜的二次门禁**，在 `ProcessTransport::load()` 里 **spawn 之前** 调用。这条顺序是本轮唯一一次"宁愿重复检查"的地方：P3.0 的教训是缺文件会让 native `abort()`，代价是整进程。

`ModelManifest::content_digest()` = `"{package_id}@{version}#{权重 sha256 前 32 位 hex}"`，作为进入诊断/日志/未来缓存键的"模型身份"。**本轮不把它当作安全摘要**（见 §3 D-02）。

### 1.6 错误映射（逐条对 `docs/12` §3.2）

| 情形 | `RuntimeError` | 对外 `TranslationErrorCode` | 可否重启后重试 |
|---|---|---|---|
| 模型文件缺失/非普通文件 | `NotInstalled` | `ResourceNotInstalled` | 否（装好再手动重试） |
| 大小/摘要不符、清单不完整、符号链接 | `IntegrityFailure` | `IntegrityFailure` | 否 |
| 平台不支持、重启预算耗尽 | `CapabilityUnavailable` | `CapabilityUnavailable` | 否 |
| spawn 失败、未加载就翻译 | `InitFailed` | `RuntimeInitFailed` | 否（先修环境/先 load） |
| worker 崩溃、后端失败、帧坏 | `WorkerExited` / `BackendFailed` / `Protocol` | `BackendFailed` | `WorkerExited`/`BackendFailed` 允许，`Protocol` 不允许 |
| 请求超时 | `Timeout{operation, waited_ms}` | `Timeout` | 否（重试未必更好，交给宿主决定） |
| 调用方取消 | `Cancelled` | `Cancelled` | 否 |

`retryable_after_restart()` 保守到只有两种取值返回 `true`——摘要不符重试一万次也不会变好。

> 设计修正（测试逼出来的）：`ExitStatus::code()` 对被信号杀死的进程返回 `None`。最初只带 `code`，于是 `abort()` 的错误显示成"worker 进程已退出：…"——诊断信息全丢。现在 `WorkerExited` 同时带 `signal`，显示为"被信号 6 / SIGABRT 终止"。这不是锦上添花：P3.0 的两种崩溃（SIGABRT 6 / SIGSEGV 11）**只有信号号能区分**。

### 1.7 mock worker（`src/bin/nmt-worker.rs`）

默认 `--mock`，引擎 id `worker.mock`，译文格式 `[{target}] {text}`（与仓库里其它 mock 引擎一致，一眼能看出是假译文）。

故障注入开关（全部真实生效，不是返回错误码假装）：

| 参数 | 行为 |
|---|---|
| `--crash-on-load` / `--crash-on-translate` / `--crash-on-shutdown` | `std::process::abort()`（真 SIGABRT） |
| `--sleep-ms N` | 请求处理前 sleep，用于撞超时 |
| `--fail-on-translate` | 返回 `BackendFailed` 错误响应（进程不退） |
| `--emit-garbage-on-translate` | 写出长度合法、内容不是 JSON 的坏帧 |
| `--epoch N` | 故意回带错误的 epoch，测宿主丢弃逻辑 |
| `--noisy-stderr` | 刷 2000 行 stderr，测环形缓冲 |
| `--bergamot` | **有意**返回 `CapabilityUnavailable("P3.1-A 尚未接线真实 Bergamot（计划 P3.1-B）")` |

最后一条是本轮的诚实性开关：真实模型还没接进来，假装能跑比报错更危险。

### 1.8 平台门禁

`ProcessTransport::ensure_worker()` 第一步是 `ensure_platform()`：**非 Linux 直接返回 `CapabilityUnavailable`**，不放空实现、也不假装能用。这是临时门禁，P3.1-E 在 Linux CI 落地后再按平台逐个放开。

### 1.9 对公共 API 的约束（`docs/12` §3.1 自查）

| 要求 | 本轮状态 |
|---|---|
| 不向 `translator-api` 暴露 C++ 类型/pid/socket | 满足（本轮 `translator-api` **零改动**；`RuntimeTransport` 只出现 Rust 类型） |
| native 实现必须是可选插件 | 满足（依赖方向 `translator-runtime → translator-types`，无反向边） |
| 非 Linux 明确 `CapabilityUnavailable` | 满足（§1.8） |
| 不把原文/原始 stdout 写日志 | 满足（诊断只保留 stderr 尾部 + 匿名错误码；`TranslationReply` 不落盘） |
| `LocalOnly` 不自动联网 | 满足（本层没有任何网络代码；也没有"崩溃后改走远程"的分支） |

[崩溃隔离] worker pid=836121 在翻译中 abort()

宿主存活：能继续读指标 pid=None
崩溃后的下一次请求：运行时初始化失败：尚未加载模型（worker 可能已重启，需要重新 load） → RuntimeInitFailed

[受控重启] epoch 1 → 2，pid 836132 → 836143，respawns=1
[shutdown] 5.1 ms（含礼貌帧→SIGTERM→SIGKILL 的升级）
```

**这些数字怎么读（防止误用）：**

- **IPC 往返 p50 0.016 ms** 是 mock worker 的成本：它不做推理、不读权重。它能说明的是"帧协议本身的开销可以忽略"（相对 P3.0 实测的 12.82 ms 热翻译，量级差 2～3 个数量级），**不能**说明真实端到端延迟。
- **2.8 MiB + 2.1 MiB** 是空壳进程的 RSS，与模型无关。它**不能**用来支撑任何内存预算；预算口径仍是 P3.0 的 **413.8 MiB（1 线程峰值）/ 678.5 MiB（2 线程峰值）**。本轮唯一的结论是：**多一个进程本身几乎不要钱，贵的是权重**。
- **`shutdown` 5.1 ms** 是"worker 顺从地回 shutdown 帧并自行退出"的路径；真要升级到 SIGKILL 时上限是 500 ms + 500 ms（`shutdown_grace` + `term_grace`）。
- `p50/p95/p99` 是**宿主侧墙钟**（含 `write` + `recv_timeout` 唤醒），不是 worker 内部计时。

## 3. 与原设计的偏差及原因

编号沿用审查文档的 P30-xx 与本轮自编号 D-xx。**没有一项是为了省事**；每一项都写清代价与补做阶段。

### D-01（偏离 P30-02 的一半）校验与"快照绑定"只做了一半

- **原要求**：加载时使用已通过校验的**只读 snapshot**，而不是重新解析任意用户路径；并有租约期间禁止删除该 revision。
- **本轮实际**：`ModelManifest::verify()` + `ModelSpec::verify_paths()` 都是**路径上的检查**，检查完到 native `open()` 之间仍存在 **TOCTOU 窗口**（`docs/12` §2.2 末尾已经预告了这个窗口）。没有只读快照，没有租约绑定。
- **原因**：快照/租约属于 `translator-resource`（P2 的 `ResourceLease`）与 P3.1-D 的执行计划；在 A 阶段引入会同时动三个 crate，且真实 worker 还没接（B）。用一个没有 native 侧的 snapshot 机制"看起来完成"是本末倒置。
- **代价**：本轮的校验只保证"我检查的那一刻是对的"，不保证"native 打开的那一刻还是同一个文件"。**不是安全边界**，报告与代码注释都按这个口径写。
- **补做**：P3.1-B（真模型加载前核验 + 只读打开/句柄绑定）、P3.1-D（租约期间禁止删除 revision）。

### D-02（偏离 P30-02 的另一半）`content_digest` 只取权重 sha256 前 32 位

- **原要求**：`ResolvedExecutionPlan` 记录 engine id、runtime build、model 内容摘要、Tokenizer/短名单摘要、生成参数、术语/规则版本、隐私域，且**不能只用 `model_id@version`**。
- **本轮实际**：`content_digest = package@version#权重sha256[..32]`，比"只用 id@version"强，但**不含** runtime build / tokenizer 摘要 / 生成参数 / 规则版本。
- **原因**：这七项里有一半（runtime build、规则版本、隐私域）在 A 阶段还没有来源；先拼一个"看起来很全"的字符串，等 D 阶段接真来源时必然要改格式，不如留一个诚实的最小值 + 明确的补做点。
- **代价**：现在这个 digest **不能**当缓存键用（会串味）。代码注释里已经写明"等 P3.1-D 的 `ResolvedExecutionPlan` 上来后再按需扩展成全字段哈希"。
- **补做**：P3.1-D。

### D-03（偏离 N-05/N-06）没有 single-flight、没有租约、没有排队超时

- **原要求**：N-05 重复加载只加载一次；N-06 持有租约时拒绝卸载；§3.2 有"请求排队超时 → `Timeout`"。
- **本轮实际**：`ProcessTransport` 用**一把互斥锁**串行化所有请求，天然"同一时刻只有一个请求"，因此不存在并发加载两次的问题——但这不等于 single-flight，只是并发度为 1；`unload` 不检查租约；排队超时不存在（没有队列，只有 in-flight 超时）。
- **原因**：这三项都属于 P3.1-D 的"生命周期与一致性"，需要一个"谁在用这个模型实例"的概念（lease/plan），而 A 阶段连调用方都没接上（见 D-05）。
- **代价**：默认并发 1 是**策略**而非**机制**：如果将来有人把锁收窄，single-flight 不会自动出现。这一点在 `transport.rs` 顶部注释里写明"默认并发 1 是 P3.0 实测的结论，不是协议限制"。
- **补做**：P3.1-D。

### D-04（偏离 P30-05/P30-09 的测量深度）只有 RSS，没有 PSS/VmHWM/分阶段峰值

- **原要求**：`docs/12` §2.4 要求分开采集 host/worker/combined，且 `/proc/<pid>/smaps_rollup` 的 PSS、`VmHWM`、加载前/后/热推理/卸载后的分项。
- **本轮实际**：`process_rss_bytes()` / `rss_bytes_of()` 只读 `VmRSS`；`TransportMetrics::combined_rss_bytes()` 明确标注"相加≠物理增量"。
- **原因**：mock worker 没有权重，分阶段峰值测了也没有信息量；PSS 采样要和真实模型一起做才有意义。
- **代价**：本轮的内存数字不能进预算，只能证明"多一个进程的固定开销很小"。
- **补做**：P3.1-B（真模型 + `VmHWM`）、P3.1-D（加载/卸载前后差值）、P3.3（PSS 与多轮趋势）。

### D-05（本轮范围裁剪）没有把 `translator-runtime` 接进 `translator-api` / `translator-cli`

- **原要求**：审查的路线图里 `translator-api → Coordinator/LocalNmtEngine → RuntimeTransport`。
- **本轮实际**：crate 独立存在，只有测试与 harness 在用；`translator-api`、`translator-cli` 零改动。
- **原因**：现在接进去会立刻面对"选哪个模型、租约从哪来、执行计划怎么记、失败怎么向用户表达"——正是 D 阶段的内容。而 A 阶段的目的是**先把边界钉死**，用 mock 把崩溃/超时/坏帧/重启全部跑一遍；过早接线会把 D 阶段的临时决定固化进 API。
- **代价**：`translator-runtime` 目前**不是任何用户可见路径的一部分**。这一点在 README 与本节都明说，避免"新增 crate = 功能可用"的误读。
- **补做**：P3.1-D（接线）、P3.1-E（`translate()` 走真实译文 + CLI + CI）。

### D-06（新增的临时门禁）非 Linux 一律 `CapabilityUnavailable`

- **原要求**：§3.1"非 Linux 返回明确的 `CapabilityUnavailable`，不放空实现"。
- **本轮实际**：`ensure_platform()` 硬编码"只有 Linux 可用"。代码本身是 `std::process` 写的、理论上能编译到其它平台，但**一次都没编译/运行过**。
- **原因与代价**：按审查要求先给明确失败，而不是给一个没证据的实现。代价是将来上 macOS 时要主动拆这道门。**本轮不声称任何跨平台可用性**。
- **补做**：P3.1-E 之后按平台逐个放开，每个平台都要有自己的终止策略证据（Windows 没有 SIGTERM 语义）。

### D-07（协议实现细节）重启预算是构造参数、且没有退避

- **本轮实际**：`ProcessTransport::new(config, restart_budget)`，测试用 1；没有指数退避、没有"连续失败就在 N 秒内不再重启"的熔断。
- **原因**：`docs/12` §2.1 只要求"可受控重启，不自动无限重试"。预算 + "只在下一请求重启"已经满足这条；退避需要时间源与策略配置，属于 D 阶段。
- **代价**：快速失败的场景下，每个新请求会各撞一次重启预算（最多 1 次 spawn），不会雪崩，但也没有节流。

### D-08（协议实现细节）`translate` 超时后 worker 直接被杀，不尝试取消

- **本轮实际**：超时 = 独占 worker 已被污染 = 终止。这与 §3.2"推理超时且 native 不可中断 → 需终止独占 worker"一致；但意味着**一次慢请求会连带丢掉已加载的模型**（下一次请求要重新 `load`）。
- **原因**：Bergamot 的推理没有取消点（P3.0 未发现任何中断接口）。假装发个"cancel"再等，只会把失败拖成两次失败。
- **代价**：冷启动成本会重复支付。这一点必须在 D 阶段用"加载与推理分离的 worker 池"或"可复用模型实例"来缓解，而不是靠偷偷不杀。

### D-09（措辞纪律）报告与代码里没有任何"内存 < 400 MB"的表述

- 全仓库检索确认：本轮没有新增任何把总内存说成"< 400 MB"或"~200 MB 可达"的句子；`TransportMetrics` 文档注释直接写"相加不是物理增量"。

## 4. 本轮明确**未**证明的事

按"宁可少说"的原则列出，评审可以直接拿这张表当缺口清单：

1. 真实 Bergamot 进程 worker 能不能跑起来、能不能译出 `你好,世界!`（P3.1-B）；
2. 真实模型在**缺文件/截断权重**时宿主是否仍然存活（P3.0 只在参考 CLI 上验证过"会崩"，本轮只在 mock 上验证了"崩了不影响宿主"）(P3.1-B)；
3. 加载前校验与 native `open()` 之间的 TOCTOU 是否可消除（P3.1-B/D）；
4. `{name}`/`{order_id}`/反引号在真实 NMT 下能否保住（P3.1-C，SP-01～08）；
5. 并发 > 1 时的行为、single-flight、租约、排队超时（P3.1-D）；
6. 加载/卸载多轮后的 RSS 收敛、PSS、`VmHWM`（P3.1-D / P3.3）；
7. Linux CI、重复多轮基准与置信区间（P3.1-E / P3.3）；
8. 任何非 Linux 平台（本轮由 D-06 直接拒绝）；
9. 权重再分发许可证（P3.4，仍为发布阻断项；本轮未分发任何权重）。
