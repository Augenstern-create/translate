## 3. 与原设计的偏差及原因

- **D-101：可写工作区从 `D:\dev\translate-workspace` 改为 `E:\augenstern\translate`。**
  原因：`docs/32` §0 的硬约束（你的最新要求）。影响：`docs/31` §4 的 P0-2/D-98、`docs/30` §4 的路径全部作废，
  后续一切命令以 `E:\augenstern\translate` 为准；`E:` 剩 133.7 GiB（比 D 的 120.2 还多）。
- **D-102：Rust 从 1.97.0 变为 1.99.1（你已升级），我不再安装或切换工具链。**
  原因：`docs/32` §0.4。影响：`docs/31` 的 **R13 WARN 消失**，`cargo fmt --check` 与 Linux 的比对口径
  从"有工具链差异"变成"应当完全一致"——如果 W2 出现格式差异，那就是**代码问题**，不能再以版本不同解释。
  这条对结论有利，但口径要跟着收紧。
- **D-103：更正 `docs/31` 关于 `cdn.pyke.io` 的结论——不是"直连不可达"，而是"直连极慢且不稳"。**
  原因：v2 里那次"20 s 超时"是我用 `--max-time 20` 截断一个 32.4 MB 下载造成的假象（`curl` 退出码 28 是
  "操作超时"，不是"连接被拒"）。本轮用 HEAD + 有界采样重测：HEAD 直连 12 s 超时、经代理 200；
  采样直连 20 s 只拿到 4,483 B（≈224 B/s），代理下 256 KiB 用时 6.4 s（≈40 KB/s）。
  **同时更正体积**：该包是 **32,457,673 B（32.4 MB）**，不是我此前估的"100–200 MB"。
  影响：W6 的下载策略不变（走进程级代理），但理由从"不通"改成"直连慢到不可用"，而且体积比预估小 3–6 倍。
- **D-104：Python 固定为 `D:\Anaconda3\python.exe`（3.13.5），`py -3`/`D:\python` 不再作默认。**
  原因：`docs/32` §0.3。影响：所有 Python 工具调用改成绝对路径；裸 `python`（MSYS2 3.12.11）仍然存在，
  记录在案但不用——因为 MSYS2 版 Python 的路径/编码行为与原生 CPython 不同，混用会让"Windows 特有失败"
  无法归因。
- **D-105：`git --global`/`--system`、Defender 排除、PATH、服务一律不再申请。**
  原因：`docs/32` §2 与 §7。影响：`core.autocrlf` 改为**项目内** `--local` 覆盖（工作区内，无需审批）；
  Defender 的 40 s 编译代价改为**接受并如实记录**（它会污染性能对比，所以 Windows 侧的性能数字必须标注
  "Defender 未排除"）。
- **D-106：文档编号顺延——`docs/32` 被审查稿占用，"Windows/Linux 并排对比报告"顺延为 `docs/34`。**
  原因：编号规则是"下一个未占用号"，审查稿按既有惯例先归档。`docs/33` 是本报告；对比报告等 W 矩阵跑完再写。
- **D-107：采集脚本在真机上暴露三处缺陷，已修复并重跑（这也是为什么必须先跑一遍再交报告）。**
  ① **`$args` 是 PowerShell 自动变量**：函数参数若命名为 `$args`，`& $exe $arg` 会静默退化成"不带参数执行"，
  症状是 `cargo -V` 输出 "Rust's package manager"、`git --version` 输出 usage、`python --version` 直接开 REPL；
  ② **PowerShell 变量大小写不敏感**：`$py`（hashtable）与 `$PY`（解释器路径）是同一个变量，赋值后路径被覆盖，
  表现为"Python 路径存在但版本为 null"；
  ③ **脚本必须全 ASCII**：v1 里有一句中文注释和一个 `§`，经 `ssh`+`-Command -` 传输时按 ACP 936 解码，
  整个脚本无输出（不是报错，是静默不执行）。三条都写进脚本注释，避免下一个人再踩。
  影响：这三个坑都不是"环境问题"，而是**我自己的工具缺陷**，若没在真机跑一遍就会被误记成"Windows 环境异常"。

按 `docs/32` §7 的格式（目标/写入量/命令/影响/回滚）：

| # | 动作 | 目标与写入量 | 命令（要点） | 影响 / 回滚 |
|---|---|---|---|---|
| A | **把仓库导入工作区** | `E:\augenstern\translate` 内约 30 MB（源码 + `.git`，含全部 tag） | Linux：`git bundle create /tmp/tw.bundle --all`（约 5.5 MB）→ `scp` → Windows：`git clone <bundle> E:\augenstern\translate` | 当前目录为空，不覆盖任何东西；回滚 = 删除该目录内文件（工作区内） |
| B | **创建 `.build` 隔离目录** | 初期 < 1 MB（空目录树） | `New-Item -ItemType Directory` 建 `target/cargo-home/temp/python-cache/model-cache/ort-dist/reports` | 全部在工作区内；回滚 = 删 `.build` |
| C | **进程级环境隔离**（每次会话） | 无持久写入 | `$env:CARGO_TARGET_DIR/.CARGO_HOME/TEMP/TMP/TMPDIR/PIP_CACHE_DIR/PYTHONPYCACHEPREFIX/HF_HOME` 指向 `.build`；`RUSTUP_HOME` 保持指向现有 `C:\Users\25026\.rustup`（只读使用） | 只影响当前进程；**代价**：新建 `CARGO_HOME` 会让依赖全量重新下载（约 1 GB 级、十几分钟） |
| D | **W6 下载 ORT 包**（32.4 MB） | 落 `.build/ort-dist`，模型另计 110 MB | 构建时临时 `$env:HTTP_PROXY/$env:HTTPS_PROXY`；`cargo build --features nmt-ort-runtime` | 只在 P5.3 发生；回滚 = 删 `.build` 内对应目录 |

另外两个**不需要批准但需要你知道**的口径决定：

1. **`CARGO_HOME` 落工作区**意味着重新下载全部 crate。替代方案是用现有的 `C:\Users\25026\.cargo`
   （已缓存过部分 crate），但那要往工作区外写 → 需要单独批准。我建议先按"工作区内、干净重下"走，
   拿到干净的依赖快照；若你嫌慢，再批 `CARGO_HOME` 复用。
2. **Defender 未排除**，构建会显著变慢（hello-world 曾 40.1 s）。所有 Windows 耗时数字都会标注
   "Defender 实时保护开启、未排除"，不与 Linux 并排算倍数。
