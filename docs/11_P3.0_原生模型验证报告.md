# 11 — P3.0 原生模型验证报告（Linux x86_64 / CPU）

> 对象：`docs/10` 的 **P3.0**（"确认模型与参考运行时确实可用"）。
> 结论：**通过**——在 Ubuntu 24.04 x86_64 CPU 上，用 Mozilla 官方 en→zh-Hans 权重 + Bergamot 原生 CLI
> 跑出了真实译文（不是 Mock 标记输出），并记录了冷/热延迟、峰值 RSS 与失败样本。
> 本文只对**真实跑过的范围**签字：Windows / macOS / Android、Rust FFI、真实卸载后 RSS **均未做**，见 §3.3。

## 1. 实际实现内容

### 1.1 模型选型（锁定到校验和，不是"某个名字"）

|---|---|---|---:|---:|---:|---|
| 主模型 | `model.enzh.intgemm.alphas.bin` | 3.0 | `base-memory` | 32,923,790 B | 43,849,787 B | `4e5accc1…c2157c` |
| 源词表 | `srcvocab.enzh.spm` | 3.0 | — | 348,078 B | 806,952 B | `bd9b6550…97c8c5` |
| 目标词表 | `trgvocab.enzh.spm` | 3.0 | — | 354,994 B | 772,004 B | `aded6993…df223d` |
| 词法短名单 | `lex.50.50.enzh.s2t.bin` | 3.0 | — | 2,499,275 B | 6,506,248 B | `4a5e5827…b68c055` |

选择理由（可复核）：该方向在注册表里存在、质量档是 `base-memory`（不是最重的 `base`）、
`filter_expression` 为空（桌面/Android 都发布）、四个文件构成完整可用集合（模型 + 双词表 + 短名单）。

> **反例记录**：P3.0 不臆造"官方推荐路径"。注册表里没有"文件路径/体积"字段可抄，
> 上面的 location 是从 `records` JSON 里读出来的 CDN 相对路径，脚本按 lock 文件重放。

### 1.4 为什么给参考 CLI 打补丁（必须说清楚）

原版 `app/bergamot.cpp` 的行为是：`readFromStdin()` 读**整个 stdin**，翻译一次，打印**一个**
结果（连换行都没有）。用它无法回答"同一进程内连续 100 次翻译的 p50"——而这是 `docs/10` §3.3 的
硬性验收项。

补丁只做了三件事（`tools/p3/bergamot-cli-lines.patch`，109 行 diff）：

1. 读环境变量 `BERGAMOT_STDIN_LINES`，为真时按行循环（默认行为完全不变）；
2. 循环里逐条调用 `service.translate(...)` 并用 `steady_clock` 计时，输出 `{"ms":…,"text":"…"}`；
3. 启动时先输出一行 `{"load_ms":…}`（模型加载耗时）。

**翻译路径（`AsyncService` / `TranslationModel` / config 解析）一行未改**。这个补丁是测量工具，
不是产品代码；它同时也预示了 P3.1 的 FFI 形状：一次加载 + 多请求 + 单 worker 串行。

### 2.4 延迟与内存（本机，`--cpu-threads 2`，beam=1）

| 指标 | 值 | 说明 |
|---|---:|---|
| 模型加载（`load_ms`） | **190.3 ms** | 页缓存已热；`mmap` + intgemm 预处理 |
| 进程首次请求 | **415.6 ms** | 含线程池/工作区首次分配 |
| 冷到首行（`load + first`） | **605.9 ms** | 这是用户开箱体验的真实值 |
| 热翻译 p50 | **12.82 ms** | 同一进程第 4 次请求起 |
| 热翻译 p95 | 14.38 ms | 100 次样本 |
| 热翻译 p99 | 27.98 ms | 长尾来自偶发调度 |
| 热翻译 min / max / mean / σ | 12.57 / 31.31 / 13.37 / 2.52 ms | — |
| 峰值 RSS（`VmHWM`） | **678.5 MiB** | 2 个 worker，含 intgemm 预处理副本与页缓存映射 |
| 稳态 RSS（`VmRSS`） | 610.3 MiB | — |

**并发 1 vs 2 的对照（同一批样本，`--cpu-threads 1`，50 次热翻译）**：

| 配置 | 热 p50 | 热 p95 | 冷到首行 | 峰值 RSS | 稳态 RSS |
|---|---:|---:|---:|---:|---:|
| threads=2 | 12.82 ms | 14.38 ms | 605.9 ms | 678.5 MiB | 610.3 MiB |
| threads=1 | 13.08 ms | 15.10 ms | 608.5 ms | **413.8 MiB** | **341.5 MiB** |

**结论（重要）**：在这颗 4 核 U 系列 CPU 上，多 worker **不降延迟**（p50 差 0.26 ms，噪音级别），
但**内存几乎翻倍**。P3.1 的默认并发应当是 **1**，把"并发 2"作为显式选项。
这与 `docs/10` §5.2 的"默认单模型常驻、推理并发 1"一致，但现在是**有本机数据支撑**的，不是照抄。

**与目标的关系（诚实）**：`docs/01` §9.3 给"桌面 Lite NMT 活跃"的初始目标是额外 300–400 MB。
本模型 **threads=1 时峰值 413.8 MiB 刚好压线**、threads=2 时 **678.5 MiB 明显超出**。
所以：目标不是"达标"，而是"用 1 线程可以接受、2 线程需要解释"。要么限制并发，要么换更小的模型，
要么接受这个数字并把预算改写成实测值——**不能把 678 MB 写成 400 MB**。

### 2.5 稳定性与错误路径

| 测试 | 结果 |
|---|---|
| 单进程连续 124 次请求（24 golden + 3 warmup + 100 次热翻译 + 提前的冷请求） | 无崩溃、无错误输出（`--log-level critical` 下 stderr 为空） |
| 确定性：3 个独立进程各翻同 3 句 | 文本 md5 **完全一致**（beam=1 贪心） |
| 缺模型文件 | 退出码 134（SIGABRT），消息清楚：`Model file does not exist: …/model.missing.bin` + `Aborted from marian::ConfigValidator::validateOptionsTranslation()` |
| 缺词表文件 | 退出码 134，`Vocabulary file does not exist: …/srcvocab.missing.spm` |
| **截断的模型文件**（只留前 1 MB） | 退出码 134，消息是 **`Segmentation fault`** 后由信号处理器 abort |

两条都是"明确失败"，但方式都不能直接搬到 SDK 里：
**参考链路用 `abort()` 与 SIGSEGV 结束进程**。P3.1 必须在进入 native 之前做
「sha256 + 大小」校验（`models.lock.json` 已经给了依据），并把 native 崩溃隔离在 worker 里，
不能让宿主进程跟着死。

## 3. 与原设计的偏差及原因

### 3.1 构建过程中的四个真实坑（都不是"设计"）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | `configure` 报 `Cannot find pcre2 libraries. Terminating.` | 本机没有 root，装不了 `libpcre2-dev`（只有运行时 `libpcre2-8-0`） | 用 `-DSSPLIT_USE_INTERNAL_PCRE2=ON` 让 ssplit 自己下载编译 pcre2 10.39。**文档里写明这是构建妥协，不是产品方案** |
| 2 | 首次跑起来 `Aborted from sgemm(...)`：`Marian must be compiled with a BLAS library` | 构建时 `find_package(BLAS)` 失败被静默放过 → `BLAS_FOUND` 未定义，`sgemm` 走 ABORT 分支（编译能过、运行必崩） | 从 Ubuntu deb 里解包 OpenBLAS 0.3.26 + libgfortran5 + netlib `cblas.h` 到本地 sysroot，显式传 `-DBLAS_LIBRARIES/-DCBLAS_LIBRARIES/-DCBLAS_INCLUDE_DIR` 重新配置 |
| 3 | OpenBLAS 官方 `cblas.h` 编不过（`common.h` 找不到） | 仓库根目录的 `cblas.h` 是**构建树内部**头文件，不是安装后的公开头 | 改用 Reference-LAPACK v3.12.0 的 CBLAS 头（ABI 相同，且自带 `cblas_mangling.h`） |
| 4 | 运行时 `libgfortran.so.5: cannot open shared object file` | 可执行文件的 `RUNPATH` 不作用于**传递依赖**（libopenblas → libgfortran） | 运行时用 `LD_LIBRARY_PATH` 指向 sysroot；P3.4 打包时必须改成正确的 rpath/`$ORIGIN` 布局 |

这些坑的共同点：**失败是静默或误导的**（"Could NOT find BLAS" 不致命 → 运行期才炸；
截断模型 → SIGSEGV）。所以 P3.1 的 FFI 必须自己做前置校验，不能把 native 当"可信组件"。

## 4. 对 P3.1 的直接输入（结论，不是计划）

1. **并发默认 1**：2 个 worker 不降延迟、内存翻倍（§2.4 实测）。
2. **占位符必须先保护再翻译**：`{name}` 会被模型吞掉（§2.3 var-01）。P3.1 的调用顺序应是
   `protected_spans → 占位符替换 → NMT → 还原 → 术语约束（ADR-015/020）`，且要有 A/B 金样本。
3. **native 不可信**：缺文件 → `abort()`，截断权重 → SIGSEGV。因此：
   - 进 native 前必须做 sha256 + 大小校验（`models.lock.json` 已是依据）；
   - 崩溃必须隔离在 worker 进程/线程边界内（`docs/10` §4.3 的"异常不穿越 FFI"）；
   - 错误映射：`ResourceNotInstalled`（缺文件）/ `RuntimeInitFailed`（加载失败）/ `BackendFailed`（推理失败）。
4. **卸载后 RSS 只能靠 Rust 侧测**：CLI 进程退出即释放，P3.0 无法给这个数字，P3.1 必须补。
5. **内存基线先按 413.8 MiB（1 线程）记账**，并把"2 线程 678.5 MiB"写进预算文档，
   不得向下取整成 400 MB。
