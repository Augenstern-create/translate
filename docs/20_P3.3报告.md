## 0. 结论与边界

本轮把 `docs/17` §6.1 的九个场景量成了可复现的 JSON（`fixtures/nmt/baseline-p33-*.json`），
并顺手修掉了三个**测量过程中暴露出来的实现问题**（§1.3）：

| 指标（1 线程 / beam=1 / release / 热态 / 缓存关闭） | 测值 |
|---|---:|
| 空 SDK 初始化 | **0.01 ms**，进程 RSS 3.16 MiB / PSS 0.73 MiB |
| 字典查询（crate 级 / 门面级）p50 | **0.02 ms / 0.18 ms** |
| worker IPC 往返 p50 / p95 | **0.04 / 0.07 ms**（n=200，无模型） |
| 模型加载（含快照） | **647.3 ms**，首句 **408.8 ms** |
| 热翻译 17 / 94 / 499 字 p50 | **6.78 / 25.05 / 175.67 ms** |
| 分段模式（63 字 / 2 个受保护跨度 / 3 次 native 调用）p50 | **19.95 ms** |
| 缓存命中 p50 | **≈0.00 ms**（n=100，全命中） |
| 并发 1 / 2 / 10 的吞吐 | **39.3 / 37.3 / 31.0 rps**（**不随并发上升**） |
| 卸载 | **33.0 ms**，全树 PSS **334.7 → 2.13 MiB** |
| 质量（结构精确 / 事实保留） | **22/22 适用样本通过**（2 条空/空白输入按设计拒绝，计不适用） |

**三件必须说清的事**：

1. **"真冷盘"没有测**。清 page cache 需要 root（`echo 3 > /proc/sys/vm/drop_caches`），本机没有权限。
   下面所有加载数字都在**页缓存未清**的口径下，不能当冷启动承诺。
2. **可读性没有被机器评分**。结构（字节级）与事实（数字串启发式）可以自动判；"这句话念起来顺不顺"
   不行。§2.10 给了人工抽样的结论，其中 `mix-01` 是一个**机器全绿但人读起来是错的**样本
   （`参须` 应为 `参数须`）——这正是 `docs/17` §6.2 要求把两者分开的原因。
3. **并发不是"越好越多"**。单 worker、单 in-flight 是既定基线（ADR-031）；并发 10 时吞吐**下降**、
   p95 到秒级。这是限制，不是特性，也不构成任何"横向扩展"证据。

## 1. 实际实现内容

### 1.1 测量工具：`tools/p33-bench`（新 crate）

一个只做测量、不做业务的命令行工具。设计原则：**每个数字都带口径**，输出 JSON（可 `--out` 落盘）：

```text
p33-bench empty | dictionary --dir | worker --bin | load | nmt --n | concurrency --levels | unload | sustain | quality
```

- `src/metrics.rs`：`/proc/<pid>/status`（RSS/VmHWM）+ `/proc/<pid>/smaps_rollup`（**PSS**），
  并按 `/proc/<pid>/status` 的 `PPid` 建进程树，报告"自己 + 所有子孙"——因为 native 是
  worker 的子进程，不看进程树就会把 342 MiB 漏掉。
  RSS 与 PSS 的差别在报告里写明：**RSS 相加会重复计共享页，PSS 相加才近似物理增量**（ADR-021）。
- `src/stats.rs`：分位数用**最近秩法**（不做线性插值），所以 `p95` 就是"第 95 个排序样本"，
  人能手工复核。
- `src/corpus.rs`：20/100/500 字语料按词边界截断生成，**固定、不随机**。
- `src/quality.rs`：结构评分 + 事实评分 + 代理指标（§1.2）。
- 每个 JSON 都有 `caliber` 字段说明"含不含加载、含不含缓存、RSS 还是 PSS"。**没有 `caliber` 的
  延迟数字在本项目里视为无效。**

### 1.2 质量评分器：三层分离

| 层 | 判据 | 能否自动判 |
|---|---|---|
| **结构精确** | 受保护跨度（URL / 邮箱 / 反引号代码 / 模板变量）逐字节出现、次数正确、顺序不乱 | 能（字节级） |
| **事实保留** | 源文里的数字串必须出现在译文里（启发式） | 能（有误报） |
| **可读性** | 是否自然、术语是否正确、语序是否合理 | **不能**，只能人工 |

代理指标（`cjk_ratio` / `length_ratio` / `source_residue`）**只作观察**，不合成质量分。
`docs/17` §6.2 明确要求"不要用 `must_contain` 判断代码围栏或反引号正确"——本评分器用的是
`count + 有序查找`，不是"包含即通过"。

空/纯空白输入按引擎既定行为返回 `InvalidRequest`，在评分里记为 `not_applicable`，
**不算**结构失败（这是本轮修掉的一个评分口径 bug：第一版把它们算成 2 条失败）。

### 1.3 测量过程中修掉的三个实现问题

1. **BLAS/OpenMP 线程超订**（影响并发与长句）。`native --cpu-threads 1` 只约束 Marian 自己的线程池，
   OpenBLAS 会另外起一堆线程。实测：并发 10 时吞吐 **15.0 → 31.0 rps**、p50 **139 → 35 ms**；
   499 字单句 p50 **340.3 → 175.7 ms**。
   修法：worker 在 spawn native 时设 `OPENBLAS_NUM_THREADS` / `OMP_NUM_THREADS` 为 native 线程数，
   **宿主显式设过则不覆盖**。
2. **排队等待的轮询粒度**。原来固定 1 ms `sleep` 轮询状态锁；改成 20 µs 起翻倍、500 µs 封顶的指数退避，
   语义（到期返回 `Timeout{operation:"queue"}`）不变。实测对吞吐影响在噪声范围内，但对 p95 有小幅改善。
3. **容量 0 的缓存仍记"未命中"**。`PlanCache::get` 在容量 0（关闭）时也会累加 `misses`，
   导致报告里出现"403 次未命中、0 条目"的噪声。改成关闭态既不命中也不计数。

### 1.4 文件清单

新增：`tools/p33-bench/`（`Cargo.toml` + `src/{main.rs,metrics.rs,stats.rs,corpus.rs,quality.rs}`，约 900 行）、
`fixtures/nmt/baseline-p33-{empty,dictionary,worker,load,nmt,concurrency,unload,quality-linux-x86_64}.json`。

修改：`crates/translator-runtime/src/bin/nmt-worker.rs`（BLAS 线程环境变量）、
`crates/translator-runtime/src/transport.rs`（指数退避）、`crates/translator-core/src/plan_cache.rs`（关闭态不计数）、
`Cargo.toml`（workspace 成员）。

口径：只有 Mock 插件，无资源、无子进程。这是"默认依赖树到底有多轻"的基线。

### 2.3 字典 Ready（`baseline-p33-dictionary.json`）


### 2.4 Worker 无模型（`baseline-p33-worker.json`）

```text
ipc_rtt_ms  p50 0.04 / p95 0.07 / p99 0.20 / max 0.97（n=200，health 往返）

worker      RSS 2.26 MiB / PSS 0.45 MiB

```

这些是**空壳**数字，不含权重，**不能当内存预算**（ADR-031 已写明）。

### 2.5 模型加载（`baseline-p33-load.json`）

```text
model_bytes 51,936,351（49.5 MiB，五文件）
runtime bergamot-cli / revision nmt.enzh.mozilla@3.0#4e5accc141373565ddc8fa1565bceaa8
load_ms 647.32           ← 含快照复制 + 校验 + native 启动 + 模型加载
first_sentence_ms 408.75 ← 含首次 native 推理
native(bergamot) RSS 340.80 / VmHWM 413.41 / PSS 332.56 MiB
worker(nmt-worker) RSS 2.76 / PSS 0.75 MiB
全树              RSS 347.50 / PSS 334.66 MiB
```

P3.1-B 同机同模型报的是 **718.9 ms 加载 / 416.7 ms 首句**（见 `baseline-p3.1b-*.json`），
本轮为 **647.3 / 408.8 ms**，差 **11%**，落在 §3 D-41 说的跨运行波动范围内——**不构成"变快了 10%"的结论**。

**PSS 的新信息**（本轮首次采集）：native 的 RSS 340.80 与 PSS 332.56 差 **8.2 MiB（2.4%）**，
也就是说"RSS 相加会高估"在这条链路上只高估约 2%——因为 native 几乎独占自己的页，
只有 libc/BLAS 那些共享库会被重复计入。这个数字支持"讨论内存以 PSS 为准"，
但也说明**用 RSS 做粗略账并不离谱**（2% 量级）。

**真冷盘未测**：`echo 3 > /proc/sys/vm/drop_caches` 需要 root。上表是"页缓存较热"的口径。

### 2.6 热翻译（`baseline-p33-nmt.json`）

缓存关闭（`cache_capacity=0`），n=100，单位毫秒，最近秩分位：

| 源文长度 | p50 | p95 | p99 | min | max |
|---|---:|---:|---:|---:|---:|
| 17 字 | **6.78** | 6.96 | 7.21 | 6.64 | 7.86 |
| 94 字 | **25.05** | 26.89 | 28.18 | 24.53 | 35.42 |
| 499 字 | **175.67** | 179.18 | 182.86 | 172.02 | 184.69 |
| 63 字 / 2 个受保护跨度（分段 3 次调用） | **19.95** | 22.01 | 23.78 | 19.35 | 26.08 |
| 100 字 / 缓存命中 | **0.00** | 0.00 | 0.00 | 0.00 | 0.01 |

- 499 字这一行在**修掉 BLAS 线程超订之前 p50 是 340.30 ms**（同一台机器、同一句话，
  只差 worker 有没有设 `OPENBLAS_NUM_THREADS`/`OMP_NUM_THREADS`）。这是一次**同会话 A/B**，
  没有单独存成基线文件，所以只报 p50 这一个我确定记得的对比值。
  结论写进 ADR-031：**报单句延迟必须说明 native 侧线程配置**。
- 17 字与 P3.1-B 的 13.17 ms 不同，原因是 P3.1-B 那次测的是 `Hello world!` 走完整 worker 往返且
  worker 为 debug 构建；本轮是 release + 同进程直调引擎。**两者不可直接比较**，只能各自作为基线。
- 分段模式的 19.95 ms ≈ 3 × 单次调用（3 个纯文本段），与 §2.7 的线性关系一致。

### 2.7 长时间稳定性（10 分钟）

见 `fixtures/nmt/baseline-p33-sustain.json`（600 秒、每 10 秒采样一次、每轮 50 句且互不相同）：

```text
seconds 600 / interval_s 10 / total_requests 3000 / errors 0
latency(n=3000)  p50 26.92 / p95 32.61 / p99 40.50 / mean 28.20 / min 22.12 / max 1081.85
全树 RSS 348.52 → 349.76 MiB（+1.24 MiB，+0.36%）
全树 PSS 341.32 → 342.56 MiB（+1.24 MiB）
```

RSS 的形状（每 100 秒取一个点）：`348.52 → 349.21 → 349.24 → 349.24 → 349.24 → 349.55 → 349.76`。
**先爬 100 秒、然后 300 秒完全平、最后两个点各跳 0.3 MiB**——这是分配器/arena 的台阶式增长，
不是线性泄漏（线性泄漏 10 分钟至少是几十 MiB 量级）。

诚实说明两点：

1. **"10 分钟不涨"不等于"没有泄漏"**。要判泄漏需要小时级运行 + 强制重载循环。
   本轮只给出"600 秒内 +1.24 MiB、形态是台阶"这个事实，不宣称 leak-free。
2. **max 1081.85 ms 是 3000 次里的 1 次离群**（p99 只有 40.5 ms）。采样文件里没有逐请求时间戳，
   所以定位不到是哪个窗口；而这段时间本机**还跑着其他 cargo 任务**（同一会话的开发动作），
   不排除 CPU 争抢。这条要在独占机器上复测，不能当作引擎的固有尾部。

### 2.8 并发 1 / 2 / 10（`baseline-p33-concurrency.json`）

预热后（加载不计入），每一层用**互不重叠**的文本（避免上一层的结果被缓存命中）：

| 并发 | 请求数 | 墙钟 ms | 吞吐 rps | p50 | p95 | p99 | 错误 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 20 | 509.4 | **39.3** | 25.32 | 26.89 | 28.14 | 0 |
| 2 | 40 | 1071.3 | **37.3** | 26.47 | 30.32 | 562.57 | 0 |
| 10 | 200 | 6457.9 | **31.0** | 35.35 | 1181.77 | 2163.10 | 0 |

**BLAS 修复前的同一组测量**（同会话 A/B，未单独入库）：并发 10 → 吞吐 **15.0 rps**、p50 **138.98**、
p95 **2067**。修复后同一层是 **31.0 rps / 35.35 / 1181.77**：吞吐约 **2.06×**、p50 约 **3.9×**。

读法（三条都要说）：

1. 吞吐**不随并发上升**（39.3 → 37.3 → 31.0）。这是单 worker / 单 in-flight 的必然结果（ADR-031），
   不是缺陷也不是失败；任何"再加线程会更快"的说法都没有数据支持。
2. p95 在并发 10 时达到 **1.18 s**：请求在队列里等，而当前排队是**非公平**的（`try_lock` 竞争），
   所以尾部会被饿。修法是 FIFO 票据 + 条件变量，属于下一阶段（§4）。
3. 0 错误、0 超时：默认 15 s 的翻译截止时间在这组负载下没有被触发。

### 2.9 卸载/回收（`baseline-p33-unload.json`）

```text
first_translate_ms 1076.03（含加载）
unload_ms 42.87
全树 PSS 340.30 → 3.07 MiB（-337.23，-99.1%）
全树 RSS 347.51 → 6.89 MiB
进程数 3 → 2（native 退出，worker 保留）
残留快照目录 0
```

native 那 337 MiB 在卸载后**真的还回去了**，这是 P3.1-B 只报 RSS 时无法确认的事。

**一个被自己抓到的测量 bug**：第一次跑这一项时 `snapshot_dirs_left` 报 **1**。
查下去发现残留目录是 `snap-1014258-…`，pid 属于**同一时刻在后台跑 sustain 的那个进程**——
两个测量共用了一个 `NMT_SNAPSHOT_ROOT`。改用独立目录重跑后为 **0**。
这说明两件事：(a) 数字要用干净环境复测；(b) `snapshot` 目录名里的 pid 让人能一眼看出"这是谁留下的"。

### 2.10 质量（`baseline-p33-quality-linux-x86_64.json`）

```text
金样本 24 条：适用 22、不适用 2（empty-01 空串、space-01 纯空白 → 按设计 InvalidRequest）
结构精确 22/22      事实保留（数字）22/22
```

结构与事实都满分的样本里，仍有**人读起来是错的**：

| 样本 | 机器结论 | 人工结论 |
|---|---|---|
| `mix-01`（"The API response time should be under 100 ms." 之类混排） | 结构 ✅ 事实 ✅ 代理指标正常 | **不可接受**：译文 `API 响应时间 延迟 参须低于 100 毫秒` —— `参须`（人参根）应为 `参数须`，且"响应时间 延迟"重复 |
| `code-01` | 结构 ✅ 事实 ✅ | 语序不顺：`跑步 \`cargo test --all-features\` 在承诺之前。` |
| `var-01` | 结构 ✅ 事实 ✅ | 标记都在，但断句丢了：`你好 {name}您的订单 {order_id} 已经发货了。` |
| `multi-01` | 结构 ✅ 事实 ✅ | URL / 邮箱 / `{plan}` 都在，句子绕：`…发送电子邮件至我们 hi@example.com 关于 {plan}。` |
| `email-01` | 结构 ✅ 事实 ✅ | `联系 support@example.com 如果错误仍然存在。` 语序是英文的 |
| 其余 17 条 | 结构 ✅ 事实 ✅ | 可读（人工抽样通读，见 §5 的评分表） |

结论：**代理指标全绿 ≠ 质量合格**。要判可读性必须有人读（§5 给了固定评分表）。

## 3. 与原设计的偏差及原因

### D-40（测量）真冷盘未测

需要 root 清 page cache。本机没有权限，也没有第二台干净机器。替代做法是"进程内首次加载"，
并在报告里标注"页缓存较热"。**不把它叫作冷启动。**

### D-41（测量）共享机器上的数字有波动

i5-8250U 是共享机器（同期负载 1–3）。所有分位数都来自 n=100/200 的同一次运行，
但**跨运行的绝对值会有 ±10% 级波动**。报告里给了 min/max 供判断离散程度，没有做"多次运行取中位数"
——那会让复现成本翻倍。比较不同实现时应当**同一次会话内**交替采样，而不是拿两天前的数字比。

### D-42（并发）单 in-flight 不扩展，也没有做 FIFO 排队

吞吐 39 → 31 rps、p95 1.18 s。要改就得把状态锁换成"票据队列 + 条件变量"，
但那是并发语义的重新设计（谁先谁后、超时如何取消排队者），不属于"验收"而属于"新功能"。
本轮只把最刺眼的 BLAS 超订修掉，并在 §4 明确列为 pending。

### D-43（质量）事实评分只覆盖数字

"否定词是否保留""单位是否换算""专有名词是否一致"都没有自动判据，强行做会变成一堆
`must_contain` 式的假阳性。因此 `facts_pass` 只声明"数字串保留"，其余交给人工。

### D-44（工具）`p33-bench` 是独立 crate，不是测试

性能测量不适合放进 `cargo test`（跑一次 10 分钟、且数字强依赖机器状态）。做成工具 + JSON 基线，
CI 里只做"基线存在性"与"回归阈值"检查（P3.4）。

### D-45（修改）为了通过验收而改了实现（BLAS 线程与轮询退避）

这是本轮唯一"测量影响实现"的地方。判断依据：这两处改动都不改变对外语义
（线程环境变量只在宿主未设时生效；退避不改变超时语义），且收益可测量。

## 5. 人工可读性评分表（模板 + 本轮结论）

评分口径（每条样本独立打分，不互相参照）：

| 分 | 含义 |
|---:|---|
| 3 | 自然、术语正确、可直接发布 |
| 2 | 可理解，但有语序/用词瑕疵 |
| 1 | 能看出大意，但明显错误（术语错、重复、断句错） |
| 0 | 不可读 / 事实错误 |

本轮抽样（22 条适用样本，1 名评分者通读）：

| 分 | 条数 | 代表样本 |
|---:|---:|---|
| 3 | 17 | `greet-01` `stmt-01` `neg-01` `num-02` `long-01` `punct-01` … |
| 2 | 4 | `code-01` `var-01` `multi-01` `email-01`（都是语序/断句，不是内容错） |
| 1 | 1 | `mix-01`（`参须` / 重复） |
| 0 | 0 | — |

诚实说明：只有 1 名评分者、没有双人一致性校验，**这不是"质量分数"，是抽样结论**。
下一阶段若要做质量门禁，需要固定评分者、双人打分 + 不一致仲裁。
