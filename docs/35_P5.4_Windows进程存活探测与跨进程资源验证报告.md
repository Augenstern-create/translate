## 1. 实际实现内容

### 1.1 Windows 存活探测（`translator-resource/src/leases.rs`）

新增 `#[cfg(windows)] mod win_probe`，只用 **`kernel32` 的四个函数**，**不加任何依赖**：

| 函数 | 用途 |
|---|---|
| `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, 0, pid)` | 拿句柄；不需要 `PROCESS_VM_*` 等高危权限 |
| `GetExitCodeProcess` | `STILL_ACTIVE (259)` → 活着；其它值 → 已退出 |
| `GetProcessTimes` | 取创建时间（`FILETIME`，100ns 精度）当**启动标识**，等价 Linux `/proc/<pid>/stat` 的 starttime |
| `CloseHandle` | 每条返回路径都关句柄（含错误分支） |

判定表（`probe(pid)`）：

| 情况 | 返回 | 依据 |
|---|---|---|
| `pid == 0` | `Dead` | 平台无关的前置规则（本来就是无效 pid） |
| `OpenProcess` 返回空 + `GetLastError()==87`（`ERROR_INVALID_PARAMETER`） | **`Dead`** | pid 不存在 —— 这是"崩溃残留能被回收"的关键 |
| `OpenProcess` 返回空 + `5`（`ERROR_ACCESS_DENIED`） | `Unknown` | 进程存在但拒绝查询（系统进程/权限不足），不猜 |
| 句柄有效但 `GetExitCodeProcess` 失败 | `Unknown` | 拿不到答案就不猜 |
| 退出码 ≠ `STILL_ACTIVE` | **`Dead`** | 已退出（句柄被持有时也走这条，即"僵尸"） |
| 存活 + `GetProcessTimes` 成功 | `Alive(Some(creation_time))` | 可识别 pid 复用 |
| 存活 + `GetProcessTimes` 失败 | `Alive(None)` | 知道活着，但无法识别复用（退回 pid-only 判定） |

`process_start_id(pid)` 在 Windows 上复用同一探测：`Alive(Some(start))` → `Some(start)`，其余 → `None`。

**为什么不加 `windows-sys` 依赖**：这是 P3 冻结区里的文件，加一条依赖边会牵动 `Cargo.lock`、MSRV 与
供应链审计（ADR-028 要求逐包 SPDX）。四个裸声明比一整套 feature 组合更容易审阅，也不会因为上游
版本变化被动漂移。代价是类型定义要自己写（`FileTime` 结构 + 两个常量），但只有 12 行。

**已知平台怪癖（写进代码注释）**：`STILL_ACTIVE == 259` 与"正常退出码 259"无法区分（微软文档的老问题）。
这里接受该风险：真出现"以 259 退出且句柄仍被持有"的进程，会被判成存活——方向保守（不误删），符合既有语义。

### 1.2 测试口径同步（**不是放宽**）

| 测试 | 改动 | 理由 |
|---|---|---|
| `leases::tests::当前进程必然存活` | Linux → `linux|windows` 都断言 `Some(true)` | Windows 现在真的能给出确定答案 |
| `leases::tests::不存在的pid视为已死` | 从 Linux 扩到 `linux|windows` | `OpenProcess` 对不存在的 pid 返回 87 |
| `lockfile::tests::死进程的锁会被回收` | 非 Linux 分支从"必须超时"改成"必须回收" | 旧断言编码的是 `probe()` 恒 `Unknown` 的旧语义 |
| `store.rs::recover回收死进程的租约` | 同上 | 崩溃残留租约必须被回收 |
| `p32_lifecycle.rs::lc08_安装关键点崩溃后仓库仍可修复` | **删掉 `cfg_attr(windows, ignore)`** | 5 个崩溃点（after-staging / before-rename / after-rename / before-state / after-state）现在两平台真跑 |
| `tests/cross_process.rs` | 去掉 `#![cfg(target_os = "linux")]`，改 `linux|windows` | 文件机制（重新执行自身 + stdout 握手 + `process::exit` 模拟崩溃）本来就跨平台；只有存活判定是 Linux 专属，现已补齐 |

**新增 3 条探测级用例**（两平台都跑）：

1. `已退出的子进程被判定为已死` —— 起 `cmd /c exit 0`（Linux 用 `true`），`wait()` 后 `probe(pid) == Some(false)`。
2. `启动标识不一致时视为不同进程` —— 同一 pid 配上 `start+1` 必须判 `record_is_live == false`（pid 复用检测的机制）。
3. `活着的子进程被判定为存活` —— 起 `ping -n 30`（Linux 用 `sleep 30`），必须 `Alive(_)`，然后 kill。

> 第 2 条替代了我一开始写的"父子进程 start_id 必不同"——那条**在 Linux 上是错的**：
> jiffies 只有 10ms 粒度，同 tick 内起的两个进程会拿到相同 starttime（实测双双 `19734338`）。
> 这是必须记下来的教训：**断言要钉"机制"（start_id 不等 ⇒ 判为不同进程），不要钉"现象"**。

### 1.3 `cross_process.rs` 里那个"子进程 panic"是**故意的**

Windows 日志里能看到：

```
thread 'child_uninstall' panicked at cross_process.rs:258:10:
子进程应能卸载 1.0.0: NotFound("dictionary.test")
```

它不是缺陷，而是 `子进程拿到的是同一把跨进程锁` 这条**元测试**的预期结果：父进程在一个**空仓库**上启动子进程
`child_uninstall`，断言子进程**必须失败**（`!wait_exit().success()`），以此证明子进程不是"自说自话成功"、
确实共享同一个仓库根。所以该 panic 是证据链的一部分；对应父测试 `ok`。

### 1.4 D-115 调查结论（只读，已结案）：`ort-sys` **支持**官方缓存重定向

`ort-sys 2.0.0-rc.15` 的 `src/internal/dirs.rs:129-134`：

```rust
pub fn cache_dir() -> Option<PathBuf> {
    std::env::var_os("ORT_CACHE_DIR").map(PathBuf::from).or_else(cache_dir_default)
}
```

- 优先级：**`ORT_CACHE_DIR`（环境变量）> 平台默认缓存目录**（Windows 即 `%LOCALAPPDATA%`）。
- 目录结构：`<cache_dir>/ort.pyke.io/dfbin/<target>/<dist-sha256>/`（`PYKE_ROOT = "ort.pyke.io"`）。
- 结论：**不需要**改注册表、不需要 junction/symlink、不需要系统环境变量——
  只要在**构建进程内**设 `$env:ORT_CACHE_DIR = 'E:\augenstern\translate\.build\ort-cache'` 即可。
- 现状：`C:\Users\25026\AppData\Local\ort.pyke.io`（360.9 MB）按你的决定**原样保留**，未删除、未移动；
  本轮也没有再跑任何可能写它的 ORT 构建（P5.4 的测试都不碰 ORT）。
- 待办：下一次 ORT 构建前先设 `ORT_CACHE_DIR`，构建后核对"新目录有内容 + 旧目录 mtime 不变"；
  确认后再决定是否删旧缓存（删除属工作区外操作，需你另行批准）。

## 3. 与原设计的偏差及原因

- **D-118：删掉了一条我自己写的错误断言（"父子进程 start_id 必不同"）。**
  原因：Linux 的 `starttime` 单位是 jiffies（10ms），同 tick 内起的两个进程会拿到同一个值——实测父子都是
  `19734338`。改成钉机制（`record_is_live(pid, start+1) == false`）后两平台都稳定。
  影响：这条也解释了为什么"看起来显然"的断言必须先跑过再写进报告。
- **D-119：`cross_process.rs` 的"Windows 等价测试尚未编写、未验证"这段注释作废。**
  原因：现在它有等价实现且真跑（6 passed）。注释同步改写，避免下一个人按旧注释以为 Windows 没覆盖。
- **D-120：`store.rs` 的租约回收断言从"非 Linux 必须保留"改成"linux|windows 必须回收"。**
  原因：旧断言编码的是 `probe()` 恒 `Unknown` 的**旧**语义；实现变了断言必须跟着变，否则测试会锁死旧行为。
  这是"平台行为不同的地方用独立实现 + 同等测试语义验证"的具体落地（用户要求）。
- **D-121：D-115 结案方式改为"用官方环境变量"，不是"目录隔离"或"符号链接"。**
  依据：`ort-sys` 的 `cache_dir()` 先读 `ORT_CACHE_DIR`。影响：不需要任何系统级改动，
  后续 ORT 构建只要在进程内设该变量即可把缓存落到 `.build\ort-cache`；旧缓存 360.9 MB 保留待你决定。
- **D-122：计数口径再次变化（375 vs 333，差 42）。**
  原因：`cross_process`（6）在 Windows 解 gate、`store` 多 1 条回收断言，同时 Linux 因新增 3 条探测用例从 372→375。
  影响：`docs/34` §2.1 的"差 50"已过期，本报告给出新口径；ADR-058 要求每次变更都更新这张表。
- **D-123：本轮没有新增"组合型"故障注入（例如崩溃同时留下锁+租约+半个 staging）。**
  原因：现有 5 个崩溃点已经覆盖 staging/rename/state 三个阶段的残留，再叠加组合场景收益有限而成本高。
  影响：列为 pending；若要补，最自然的做法是在 `lc08` 的 `points` 数组里加新点，而不是另写一套夹具。
- **D-124：Windows 上"pid 复用"只有机制级验证，没有场景级验证。**
  原因：要构造"同一 pid 被另一个进程复用"需要长时间窗口或注入，测试会很脆。
  影响：`record_is_live` 的判定逻辑有单测，但"真实复用发生时的行为"记为未验证（Linux 侧有一条用 `sleep` 的
  变体，Windows 未写）。
