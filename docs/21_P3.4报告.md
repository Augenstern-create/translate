## 0. 结论与边界

P3.4 的任务不是"加功能"，而是回答三件发行前必须回答的事：
**包里有什么（许可）、红线守不守（权重）、别人拿到能不能复现（CI / 打包 / 文档）**。

| 立项问题 | 本轮答案 | 证据 |
|---|---|---|
| 发行包里有哪些第三方代码、各是什么许可 | 53 个 Cargo 依赖全部登记并通过宽松许可策略；权重与 native 二进制**不在包内** | `licenses/third-party.json`、`THIRD_PARTY_NOTICES.md`、`license-audit.py --check` |
| 权重会不会被误打进仓库/制品 | 7 项红线检查全绿；CI 每次提交都跑 | `tools/check-release.py`、`.github/workflows/ci.yml#release-redline` |
| Linux CI 能不能跑 | **workflow 已写、本地等价命令全绿，但没在真实 runner 上跑过** | §2.8、D-47 |
| 权重许可结论 | **仍是"未确认"**，因此不打包、不宣称可分发的离线模型包 | `licenses/model-assets.json`、§4 G12 |

**必须说清的一点**：本轮**没有**把 P3 标成"完全通过"。`docs/17` §7.2 的 G12（许可证）依然是阻断项，
G06/G08（取消、真实 kill -9）仍是"模拟到位、真机未做"，G11（CI）是"文件与本地验证到位、runner 未跑"。
把这三条写成"通过"会让这份报告失去价值。§4 逐条给了裁定与理由。

## 1. 实际实现内容

### 1.1 许可清单：三层，机器可读优先

| 文件 | 作用 | 谁维护 |
|---|---|---|
| `licenses/third-party.json` | 53 个 Cargo 依赖：名称、版本、SPDX 表达式、归一化表达式、checksum、`legacy_notation` | `tools/license-audit.py --write`（**入库，可 diff**） |
| `licenses/model-assets.json` | 模型权重与 Bergamot 二进制的坐标、SHA-256、许可状态、再分发结论、红线文案 | 人工，随 `models.lock.json` 一起评审 |
| `THIRD_PARTY_NOTICES.md` | 人可读声明（发行物的一部分）：许可表 + 需要留意的几条 + 复核命令 | 由清单生成表格，正文手写 |

**为什么清单要入库而不是每次现算**：发行时"带了哪些许可"必须可审计、可 diff。
现算的结果只活在 CI 日志里，事后无法证明当时打的是什么。

**判定策略**（`license-audit.py`）：

- 只允许宽松许可（MIT / Apache-2.0 / BSD-2/3 / ISC / 0BSD / Unlicense / Zlib / CC0 / Unicode-3.0 / MPL-2.0）；
- SPDX 表达式按 `OR`=任一、`AND`=全部求值。所以 `r-efi` 的 `MIT OR Apache-2.0 OR LGPL-2.1-or-later`
  可以选 MIT 通过，而**单独的** LGPL 会被拒——判定看表达式结构，不看字符串里有没有 "LGPL"；
- 6 个老 crate 用非 SPDX 的 `MIT/Apache-2.0` 写法。工具按历史约定当 `OR` 处理，
  但在清单里打 `legacy_notation: true`，**不悄悄改掉**（审计要能看出"这条判定建立在一次解释之上"）；
- 只解析一层括号；更复杂的表达式直接报错要求人工处理（猜错方向比报错更危险）。

### 1.2 发行红线：7 项机器检查

`tools/check-release.py`（无需网络、无需权重即可跑）：

| 项 | 判据 | 为什么需要 |
|---|---|---|
| C1 | 已跟踪文件里没有权重/二进制/大文件（扩展名 + 5 MiB 上限） | "权重不入库"是最容易被 `git add .` 破坏的一条 |
| C2 | 许可清单与当前依赖树一致（调用 `license-audit.py --check`） | 依赖升级会悄悄带进新许可 |
| C3 | 模型坐标三方一致：`model-assets.json` ↔ `models.lock.json` ↔ `baseline-p33-load.json` | 三处任一被改都会让"可追溯"失真 |
| C4 | 每个 crate 的文件列表不含权重；`publish` 必须显式声明；真实 `cargo package` 只有预期内失败 | 防止"打包时把权重带进去" |
| C5 | `.gitignore` 覆盖 `resources` / `models` / `target` | 上面几条的第一道闸 |
| C6 | 红线文案与清单文件存在（`不入库` / `不分发` / `prohibited-until-confirmed`） | 防止"删掉文档就算通过" |
| C7 | 若设了 `NMT_MODEL_DIR`，逐个校验 5 个文件 SHA-256；未设则 SKIP | 让"我本地跑的是哪版权重"可证 |

C3 里那条"权重再分发状态必须是 `prohibited-until-confirmed`"是**故意写死的**：
谁把它改成 `allowed`，CI 立刻红。

### 1.3 CI 分流：默认门禁 vs 真实模型

`.github/workflows/ci.yml`：

- `default-gate`：fmt → clippy（`-D warnings`，全 target 全 feature）→ 默认测试 → 全 feature 测试 →
  **默认依赖树里不许出现 `translator-runtime`**（用 `cargo tree` 断言）→ rustdoc（`-D warnings`）→
  性能冒烟（`p33-bench empty/dictionary/worker` + `bench-gate.py`）→ 文档编号检查 → 上传基线；
- `release-redline`：许可清单校验 + `check-release.py` + "所有可打包 crate 都不含权重"再证一次。

`.github/workflows/real-model.yml`：`workflow_dispatch` + `runs-on: [self-hosted, linux, x64, nmt]`。
第一步就是前置检查：缺 `NMT_BERGAMOT_BIN` / `NMT_MODEL_DIR` 就**明确报错退出**，
而不是"悄悄跳过然后显示绿色"——后者会让"真实模型已验证"变成一句没有证据的话。

### 1.4 性能门禁：只抓数量级退化

`tools/bench-gate.py` + `fixtures/nmt/gate-ci.json`：对 `empty` / `dictionary` / `worker` 三个不需要
权重的场景设**宽松绝对上限**（如 `empty.init_ms ≤ 50 ms`、`dictionary.lookup_crate_ms.p50 ≤ 2 ms`、
`worker.ipc_rtt_ms.p95 ≤ 25 ms`），只用于发现"debug 构建混进来""BLAS 线程超订回来"这类数量级退化。

**它不是性能验收**：跨机器比较延迟没有意义（`docs/20` D-41），性能验收仍在固定机器上按
`fixtures/nmt/baseline-p33-*.json` 做。

### 1.5 打包与元数据

- 所有 14 个 crate 加 `publish = false`（workspace 里声明，成员 `publish.workspace = true` 继承）：
  仓库 URL 还是占位符、内部依赖是 path-only，**不允许**出现"某个 crate 被误发到 crates.io"。
- 实测 `cargo package`：只有 `translator-types`（零依赖）与 `translator-resource` 能真正打成 `.crate`，
  其余 12 个因 **path-only 内部依赖**被 cargo 拒绝（`all dependencies must have a version requirement`）。
  这是既定设计（`[workspace.dependencies]` 里内部 crate 一律无版本号），代价是**不能逐 crate 发布**，
  已在 §3 D-48 记录。
- 二进制发布方式：`cargo build --release` 产物 + 文档说明，而不是 crates.io 分发。

### 1.6 非 Linux 行为：从"cfg 分支"变成"可测的判定表"

原实现把平台判断写成 `#[cfg(target_os = "linux")]` 两条分支——在 Linux 上编译时，
非 Linux 分支**直接被裁掉**，于是"非 Linux 会报 `CapabilityUnavailable`"这句话没有任何测试覆盖。

新增 `crates/translator-runtime/src/platform.rs`：

```rust
pub const VERIFIED_PLATFORMS: &[&str] = &["linux"];
pub fn support_for(os: &str) -> PlatformSupport;      // Verified / Unverified { os }
pub fn ensure_supported_on(os: &str) -> Result<(), RuntimeError>;
pub fn ensure_supported() -> Result<(), RuntimeError>; // 走 std::env::consts::OS
```

`ProcessTransport::ensure_worker()` 改为调用 `platform::ensure_supported()`；
错误信息现在带上**具体平台名**（`windows` / `macos` / `android` …）。
CLI 的 `--diagnose` 增加一行"平台"，把"当前平台是否被验证过 + 为什么"直接打出来。

判定表是**证据表**：`std::process` 到处都能编译，但终止升级、`/proc` 采样、`kill -9` 恢复
只在 Linux 实测过（`docs/12` §3.1）。收紧 `VERIFIED_PLATFORMS` 等于"宣布支持新平台"，必须附带真机证据。

### 1.7 文档

- `CHANGELOG.md`（新）：P0→P3.4 每阶段的变更与证据位置，tag 名与阶段名一一对应。
- `README.md`：状态行、尚未实现清单、许可证章节按 P3 实际进展重写。
- 本文件 + `docs/01` 升版（ADR-040～043）。

## 3. 与原设计的偏差及原因

### D-46 `LICENSE-MIT` / `LICENSE-APACHE` 正文未入库

各 `Cargo.toml` 只声明 SPDX `Apache-2.0 OR MIT`，仓库里没有许可正文。
原因：正文需要逐字精确（11 KB 级），本轮不冒险手打；而仓库 URL 还是占位符，本来也不能对外发布。
**影响**：源码可用、`cargo` 元数据正确，但"发行物附带许可正文"这条不满足。
**处置**：对外发布前必须补两个文件（内容从 apache.org / opensource.org 取官方文本），
并在 `cargo package` 的清单里确认包含。

### D-47 CI 未在真实 runner 上运行

只能交付"可运行的 workflow + 本地等价验证"。**不宣称"Linux CI 通过"**，只宣称"CI 定义完成、命令在本地全绿"。
G11 因此判 Conditional。

### D-48 只有 2 个 crate 能 `cargo package`

内部依赖是 path-only（`[workspace.dependencies]` 里刻意不写版本号，避免漂移）。
cargo 打包要求"每个依赖都有版本号"，于是 12 个 crate 打不了包。
**这是设计取舍**：本项目的分发单位是**二进制 + 源码仓库**，不是 crates.io 包。
若将来要发布到 crates.io，需要给内部依赖同时写 `version`，并接受"版本一致性由人工维护"的成本。

### D-49 非 Linux 只有门禁、没有实现

`VERIFIED_PLATFORMS = ["linux"]` 是**证据表**，不是"编译开关"。
非 Linux 上真实 NMT 一律 `CapabilityUnavailable`，不给未验证的实现（`docs/12` §3.1 的要求）。
代价：Windows/macOS 用户只能跑 Mock/词典路径。这是 P5 的工作。

### D-50 真实模型 CI job 未运行

权重不可分发 → 只能自托管 + 手动触发 → 本轮没有这样的 runner。
job 里做了**快速失败**：缺前置就红，不会假装通过。

### D-51 权重许可仍是"未确认"，且不因本轮结束而放宽

`licenses/model-assets.json` 里 `redistribution: prohibited-until-confirmed`，
`reviewed_by: null`。没有任何法务结论，本轮**不代替法务做判断**，也不把"我们没分发"当成"可以分发"。
这一条直接决定 P3 只能判 Conditional。

### D-52 性能门禁的阈值是"宽松上限"，不是回归门禁

见 §1.4。真正的回归判断需要在固定机器上跑 `baseline-p33-*` 全套并人工比对。

### D-53 崩溃注入仍是 `abort()` 而不是真 `kill -9`（沿用 P3.2 的 D-35）

`TRANSLATOR_TEST_CRASH_POINT` 用 `abort()` 制造"进程在任意点死掉"，
没有用外部 `kill -9`。对"留下半成品目录"的语义等价，但对"信号处理/时序"不完全等价。
G08 因此仍标 Conditional。

## 7. P3 收口与 P4 入口

- P3 的产物：真实本地 NMT（分层保护 + 执行计划 + 生命周期 + 缓存）、可复现的性能/质量基线、
  许可与红线的机器检查、CI 定义、发行文档。
- P3 没做完的四件事已列在 §4.1，全部**不影响**"继续开发"，但**影响"发行"**。
- P4 的第一件事应该是 `docs/17` §9 说的：**Bergamot 与 ncnn/ORT 的插件替换对照**。
  替换能否成立，判据应当是同一份 `TranslationEngine` 契约 + 同一批金样本 + 同一套基线脚本，
  而不是"新后端快多少"。
