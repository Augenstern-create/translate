## 2. T4 — Precise / Fast 模式

### 2.1 API

- 新类型 `TranslationMode { Precise, Fast }`，`Default = Precise`。
- Builder：`Translator::builder().translation_mode(TranslationMode::Fast)`。
- 单请求覆盖（不破坏旧结构体字面量）：
  - `Translator::translate_with_mode(&req, mode)`
  - `Translator::translate_with_diagnostics_mode(&req, mode)`
  - Coordinator 对应 `translate_with_mode` / `translate_with_diagnostics_mode` / cancellellable 变体。
- `TranslateRequest` **没有**新增字段；测试 `旧结构体字面量仍然编译` 是兼容性合同本身。
- CLI：`--mode precise|fast`。
- 诊断：`TranslationDiagnostics.mode` 与 `quality` 字段；`summary()` 打印模式与译后检查条数。

### 2.2 缓存身份

`CacheKey.mode` 进入键；`CacheKey::new` 保留旧签名并默认 `Precise`，真实执行路径走 `new_with_mode`。
测试 `两种模式不共享缓存` 验证：Precise 首次未命中、Fast 不命中 Precise 的缓存、Precise 二次命中。

### 2.3 模式行为（当前阶段）

| 检查 | Precise | Fast |
|---|---|---|
| 空输出 / 占位符标记残留 | 是（致命） | 是（致命） |
| 关键数字丢失 | 是（致命，可关） | 是（致命，可关） |
| 否定丢失 / 连续重复 / 目标语言 / 原文原样 | 是（诊断） | 否 |
| 术语约束 | 是 | 是 |
| NMT 解码配置 | 当前与 Fast 相同 | 当前与 Precise 相同 |

因此**当前 Fast 不是“更快的模型”**，只是更短的检查路径；不宣称延迟收益。未来 Fast 若改解码参数，必须把模式加入 engine cache identity（Q-019）。

### 3.4 行为修复

- 英语查询大小写不敏感：`i` → `I`、`january` → `January`、`javascript` → `JavaScript`（SQLite `lower(headword)` 表达式索引，仅 FST 未命中时回退）。

- 词形候选：`running` 在只有 `run` 的包里也能命中（`EnglishLemmatizer` 现在把大小写归一作为首个候选）。

## 4. T2 — 规则、术语与译后检查

### 4.1 结构化保护交接（真实缺陷修复）

P3.0 已实测 `{name}` 会被模型吞掉；但协调器此前会先把 URL/变量换成 `⟦Pn⟧`，真实 NMT 后端再用 `ProtectionPlan` 分段时，模型看到的是它不认识的标记——同一层保护被做两次，第二次反而破坏第一次。

- 新契约：`TranslationEngine::handles_protected_spans()`，默认 `false`。
- Bergamot / ORT 返回 `true`：协调器交出**原文**，由后端 `ProtectionPlan` 分段/还原。
- 通用后端仍走 `⟦Pn⟧` 标记化 + 还原。
- 测试：`crates/translator-core/tests/protection_handshake.rs`（3 条：结构化拿到原文且无标记、通用后端可还原、取消仍生效）。

### 4.2 译后完整性检查

`translator-core::quality`：

| 检查 | 级别 | 默认行为 |
|---|---|---|
| 空输出 | Critical | `IntegrityFailure` |
| 占位符标记残留 | Critical | `IntegrityFailure` |
| 关键数字丢失（≥2 位/小数/百分号） | Critical | `IntegrityFailure` |
| 个位数丢失 | Major | 诊断 |
| 译文多出数字 | Minor | 诊断 |
| 否定丢失 | Major | 诊断（Precise） |
| 连续重复句段 | Major | 诊断（Precise） |
| 目标语言明显不符 | Critical/Major | 诊断（Precise） |
| 原文原样返回 | Major | 诊断（Precise） |

数字规范化覆盖：千分位逗号/空格（`1,250` / `1 250`）、前导零（`07:15` / `7: 15`）、百分号空格（`15 %`）、全角数字、序数词（`3rd` 不强制出现 `3`）。这避免了把“格式差异”误报为数字丢失。

`strict_integrity` 默认 `true`；测试 `quality_gate` 3 条验证关键数字丢失拒绝返回、关闭后只写诊断、数字完整正常返回。

### 4.3 规则包

- 默认 `fixtures/rules/en-zh.quality.json`（v2，4 条）：NFKC + 弯引号/弯撇号归一；**全部无损**，每条带金样本。
- 实验 `fixtures/rules/en-zh.contractions.experimental.json`（32 条）：缩写展开。12 条规则样本对照 chrF **+0.0155**、BLEU **−0.0414**，且 `I don't know.` 从“我不知道,我说不定”退化为“我不知道。 。 如何。”——**默认不加载**。这是本轮“规则不得造成明显退化”的实际执行结果（Q-008）。
- 默认包在 320 条金样本上没有触发（样本不含全角/弯引号）；规则效果由 `rules-cases.jsonl` 单独度量（NFKC 把 `ｃａｔ and ｄｏｇ` 从 `,和,` 修复为 `猫和狗`）。

### 4.4 术语表

- `fixtures/terms/en-zh.technical.json`：49 条，带 `source_variants`，只在源文触发时检查；默认策略仍是 `Warn`（P2-S 的安全默认），`Enforce` 显式开启。
- 真实模型在 320 条金样本上触发 **7 处**术语变体（垃圾收集、缓冲溢出、开放源码、单位测试、负载平衡器、虚拟机器），`terms-enforce` 会实际改写为 preferred；`Warn` 只报告。术语表不能修复任意错译（Q-009）。

## 5. T3 — 真实模型质量

### 5.1 模型与口径

- 模型：Xenova/opus-mt-en-zh（Helsinki-NLP/opus-mt-en-zh 的 ONNX int8 导出），Apache-2.0；encoder/decoder 哈希与 Windows P10 模型一致。
- 运行时：ORT 2.0.0-rc.15 prebuilt，ONNX Runtime API 1.31，release，intra-op=1，greedy + no-repeat-3gram + stop-on-3-run。
- 坐标/哈希/本地 tokenizer 补丁：`fixtures/quality/model-lock.json`。
- 本机 Linux x86_64；Windows 侧无可用执行环境，沿用 P4/P7/P10 的 Windows 记录，不把 Linux 数字冒充 Windows。

### 5.2 基线（320 条，Precise，policy=local，无词典/规则/术语）

| 指标 | 值 |
|---|---|
| chrF-zh（去空白、字符 1–6-gram、β=2） | **0.4577** |
| BLEU-zh（字符级 BLEU-4，辅助） | **0.4546** |
| 错误率 | 0/320 |
| 致命完整性（数字/标记/空） | **4** |
| 数字保真 | **0.8983** |
| 占位符/URL | 1.0 / 1.0 |
| 否定保真 | 1.0 |
| 目标语言 | 1.0 |

4 条致命错误都是真实模型问题：`50%` 丢失、`15%` 丢失、`0x80070005` 少一位、`11 PM` 所在句被截断。严格模式会拒绝这 4 条（见 `docs/61`）。

### 5.3 同集对照

- `fast`、`rules`、`terms`、`full`、`full-fast`、`baseline-96/256`、`terms-enforce`、`full-enforce` 全部在**同一 320 条**上跑完。
- `fast`/`rules`/`terms`/`full` 在整集上与 baseline 文本完全相同（本集没有单字/短语/全角/缩写触发；术语只触发 7 处 Warn）；chrF 无变化——这不是“配置无效”，而是**本集没有可触发的样本**。
- `terms-enforce`/`full-enforce` 修复 7 处术语变体：整体 chrF **0.4577 → 0.4604（+0.0027）**、BLEU **+0.0033**，technical 类 chrF **0.4781 → 0.4954（+0.0173）**；无新增致命、无回归样本。
- `baseline-96/256` 与默认 192 文本完全相同：本集最长句未触及 token cap，不能据此推断解码上界无关。
- **结论：当前模型是质量瓶颈。** 规则/术语只能做局部约束，不能把 chrF 0.46 的模型变成高质量翻译；T3 的“自然度/完整性实际改善”未达成。下一步应优先模型替换/通用 ONNX 架构与 beam/长句切分（Q-005～Q-007），而不是继续堆规则。
