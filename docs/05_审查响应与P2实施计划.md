## 1. R-01（高）：规则误改 URL / 代码 / 占位符 —— **已修**

### 1.1 审查意见（接受）

> 规则改写发生在占位符保护之前，`https://example.com/LLM` 会被 `LLM → large language model` 改坏。

这是**真实缺陷**，不是理论风险。修复前的流水线顺序：

```text
规范化 → 语言识别 → 【规则作用于整段原文】 → 占位符保护 → …
```

### 1.2 修复方案

引入**唯一扫描器** `translator_core::text::split_protected()`，把输入切成
`Segment::Plain` / `Segment::Protected`；`protect()` 与"规则只作用于纯文本"共用它，
避免两套识别逻辑各自演化：

```rust
pub enum Segment<'a> { Plain(&'a str), Protected(&'a str) }

// coordinator::apply_rules
for segment in text::split_protected(text) {
    match segment {
        Segment::Plain(plain) => { /* 规则在此生效 */ }
        Segment::Protected(p) => out.push_str(p),   // 字节级原样保留
    }
}
```

新流水线：

```text
校验 → 规范化 → 语言识别 → 切分受保护跨度 → 【规则只作用于纯文本】 → 占位符保护
     → 缓存 → 路由 → 执行 → 还原 → 结果
```

### 1.3 同时落地的两项约束

1. **邮箱纳入保护**：`local@domain.tld`（TLD ≥ 2 字母）识别为受保护片段，
   并有反例测试（`a@b`、`a@b.c`、`价格 100@50` 不得被误判）。
2. **`pipeline_version` 显式化**（审查要求"不能偷偷改变旧规则行为"）：
   - 当前执行语义 `CURRENT_PIPELINE_VERSION = 2`（跳过受保护跨度）；
   - 规则包声明 `pipeline_version: 1` 会被**直接拒收**，并提示补金样本后迁移；
   - 省略该字段视为 `2`。目前没有外部规则包，因此不提供兼容模式（记录为有意取舍）。

### 1.4 回归证据

| 测试 | 断言 |
|---|---|
| `规则不得改写url里的内容` | URL 含 `LLM` 时译文包含原 URL，且预览 `applied` 为空 |
| `规则不得改写邮箱里的内容` | `LLM@example.com` 原样保留；对照组 `mail the LLM now` 仍被改写 |
| `切分受保护片段` | URL / 邮箱 / `{token}` / `` `code_x` `` 四类全部受保护，拼回无损 |
| `邮箱识别不应误伤普通文本` | `a@b`、`a@b.c`、`价格 100@50` 仍是纯文本 |
| `旧执行语义版本被拒绝` | `pipeline_version: 1` → `UnsupportedPipeline(1)` |

CLI 复现：

```text
$ translator-cli --rules fixtures/rules/minimal.json translate "see https://example.com/LLM for details" --explain
  生效      （无）                    ← URL 内的 LLM 不被改写

$ translator-cli --rules fixtures/rules/minimal.json translate "see the LLM docs" --explain
  生效      term.llm
  处理后    see the large language model docs
```

### 1.5 未按审查建议做的部分（需你确认）

审查建议"用跨度标记或结构化 token 保存 URL/代码，不依赖简单文本占位符"。
本轮只做到"规则不碰受保护跨度"，**没有替换占位符机制本身**：`protect()` 仍用
`⟦P0⟧` 形式的标记穿过引擎。原因是替换占位符要动 NMT 侧契约（引擎必须知道什么是受保护跨度），
属于 P3 的接口设计。风险留档：若引擎把标记改写/复制，`restore` 会报 `PlaceholderRestoreFailed`，
不会静默丢内容——这是当前的兜底。

### 2.1 关于 R-02 为什么不在 P1 抢做

`ResolvedExecutionPlan` 会同时改动 `CacheKey`（内部 crate，可改）和"缓存命中后仍要核对资源是否撤销"的
语义（要资源管理器先存在）。P1 没做资源管理，抢做等于写一个没有主体的空壳。
现在 `CacheKey` 已有 `glossary_id` / `rules_version` 占位，字段扩展是加法，不阻塞后续。

### 2.2 关于 R-03 与"8–9 μs"

同意审查意见：**8–9 μs 是估算，不是结果**。P0/P1 报告中所有延迟数字都标注了"本机实测"与构建 profile，
没有把估算写成已实现。P2.5 的决策门槛采纳审查写法：只有实测收益覆盖迁移复杂度才升级默认 schema。

## 3. 对审查两处技术判断的回应

### 3.1 正则：接受纠正，修正理由（不修正结论）

审查指出：

> 不能把"不做正则"的理由写成"正则普遍需要回溯并可能灾难性爆炸"。Rust `regex` 的标准匹配机制
> 避免传统回溯式性能问题。

**这条纠正是对的**，我方此前表述不严谨。Rust `regex` 用有限自动机（DFA/NFA 混合）保证线性时间，
不存在 PCRE 那种回溯爆炸；它的真实限制是需要一次性编译出较大状态机（可选 `regex-automata` 惰性 DFA）。

因此"不做正则 DSL"的**结论保留，理由改写为**：

1. 规则语言越通用，越难审计"这条规则会不会改变语义"；
2. 规则包是**数据**，不希望它具备任意匹配能力（也就不会被当作脚本入口）；
3. 需要可控的输入长度、匹配次数与单次输出尺寸上限，这些约束在没有真实需求前无法量化；
4. 目前两类动作（NFKC、术语替换）已覆盖实际需求，加入正则属过度设计。

已同步修正 `04` 报告 §5.1 的表述。`PatternMatcher` 扩展点按审查建议预留（P2.4 之后再评估）。

### 3.2 诊断接口：接受批评，本轮已缩小差距

审查指出：

> `explain_rules()` 适合预览，但如果调用时重新执行规则，无法保证它与某次真实翻译请求完全一致。

这条批评成立。本轮做了一半修正：`explain_rules` 现在**与真实翻译走同一条 `apply_rules` 路径**
（含受保护跨度跳过），因此不会再出现"预览说生效、实际没生效"这类偏差。
但它仍不是**同一请求的快照**（时间点不同、且不覆盖语言识别结果）。

`translate_with_diagnostics()` 按审查建议列入 P2.4，接口草案采纳审查给的形状
（`request_id` / `execution_plan_id` / `applied_rule_ids` / `constraint_results` / `warnings`），
硬约束：**诊断默认不记录完整用户文本**。
