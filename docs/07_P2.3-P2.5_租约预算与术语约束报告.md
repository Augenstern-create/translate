## 2. 实际实现内容

### 2.1 P2.3 内存预算（`translator-core::budget`）

新增模块 `crates/translator-core/src/budget.rs`：

- `MemoryBudget`：`Arc` 共享的记账池，上限可选（`None` = 只记账不拒绝）；
- `try_reserve(label, bytes) -> Result<BudgetReservation, BudgetError>`：用 **CAS 循环**判定 + 计费，
  不是"先加再检查"——后者在多线程装配时会短暂越界，让两个资源都以为自己拿到了预算；
- `BudgetReservation`：`Drop` 即归还；刻意不实现 `Clone`（凭据可复制就等于可多算）；
- `MemoryReport`：上限 / 已用 / 逐项明细，`summary()` 供 CLI 与日志直接打印；
- `impl From<BudgetError> for TranslationError`：映射到**P0 就固定**的错误码 `OutOfBudget`
  （这个码此前一直没被任何代码路径使用）。

预算的数值来源刻意做成一张明账（`docs/01` §9.3 同步更新）：

| 项 | 来源 | 与真实 RSS 的关系 |
|---|---|---|
| FST 索引 | `index.fst` 文件大小 | 上界（页可能从未换入） |
| SQLite 页缓存 | `PRAGMA cache_size` 配置值（`SQLITE_CACHE_KIB = 2000`） | 精确 |
| 连接/语句/分配器 | 常量 `SQLITE_CONNECTION_OVERHEAD_BYTES = 256 KiB` | **猜的**，已在注释里标明"无实测依据" |
| 释义库 mmap | 只进 `ceiling_bytes`（最坏情况），不进记账 | 取决于触达页数 |

`DictionaryPackage::memory_footprint()` 返回 `MemoryFootprint`
（`index_bytes` / `page_cache_bytes` / `overhead_bytes` / `ceiling_bytes` / `db_file_bytes`），
`accounting_bytes()` 是记账用的下界，`Display` 直接给出可读分解。

`pack-dictionary` 与打开路径共用 `SQLITE_CACHE_KIB` 常量——之前"打开时配置的值"和"估算里假设的值"
是两处独立的魔法数，一旦漂移，估算就等于撒谎。

### 2.2 P2.3 资源租约（`translator-resource::leases`）

目录布局新增 `leases/<id>/<version>/<pid>-<nonce>.json`，每个使用方一个文件。

| API | 语义 |
|---|---|
| `ResourceStore::acquire_lease(id, version, holder)` | 确认版本已安装 → 写自己的租约文件（`create_new`，不覆盖） |
| `ResourceLease::release()` / `Drop` | 删文件 + 顺手清理空目录 |
| `ResourceStore::leases(id, version)` / `all_leases()` | 列出租约（含已失效的，带 `alive: Option<bool>`） |
| `ResourceStore::reclaim_stale_leases()` | 只回收"确定进程已死"的租约 |
| `uninstall` / `cleanup` | 有有效租约 → `ResourceLeased { holders }`（`cleanup` 改为跳过并如实报告） |

关键判定：`process_alive(pid)` 在 Linux 上用 `/proc/<pid>`，其它平台返回 `None`。
`LeaseInfo::is_active()` 的规则是 `alive != Some(false)`——**无法判定时按占用处理**。
代价是偶尔要多一步人工 `reclaim`，收益是绝不会删掉正在被 mmap 的目录。

`translator-api` 增加了把仓库和租约连起来的入口：

```rust
Translator::builder()
    .dictionary_from_store(&store, "dictionary.cc-cedict.zh-en")  // 持租约挂载激活版本
    .build()
```

租约在 `dictionary_from_store` 调用时就登记（早期失败优于延迟失败），由 `Translator` 持有，
`Translator` 存活期间该版本跨进程也删不掉；`drop(translator)` 立刻释放。

### 2.3 P2.3 跨进程状态锁（`translator-resource::lockfile`）

`state.lock` 用 `OpenOptions::create_new(true)`（`O_CREAT|O_EXCL`）做排他创建，
内容写入 `pid=` / `unix=` / `holder=`。等待超时默认 5 秒（`DEFAULT_LOCK_TIMEOUT`），
超时返回 `LockTimeout { path, holder }`，错误信息里**直接给出持锁者与锁文件路径**。

三处细节值得记录：

1. **锁粒度收窄**：`install_from_dir` 拆成"无锁复制校验（最慢）+ 持锁落位记账"两段。
   把 18 MB 的复制放在跨进程锁里，会让一次安装期间所有进程都卡住。
2. **持锁后必须重检**：复制期间别的进程可能已经装好同一版本，所以 `AlreadyInstalled` 检查做两遍。
3. **不猜别人的锁**：读不出 `pid=` 的锁文件永不自动删除（可能是别人的格式），只超时报错。

### 2.4 P2.4 输出侧术语约束（`translator-core::terms` + `translator-rules::terms`）

核心侧只定义契约，实现放在 `translator-rules`（都在 feature 后面，默认依赖树不变）：

- `TargetTermGuard { id, version, apply(text, source, target) -> TermOutcome }`；
- `TermOutcome { text, violations }`、`TermViolation { preferred, found, offset }`（UTF-8 字节偏移，指向**输出**文本）；
- `TermPolicy::{Off, Warn, Enforce}`，默认 `Enforce`（宿主显式给了术语表，通常就是要它生效；
  想先看效果写 `.term_policy(TermPolicy::Warn)`）。

术语表编译（`TargetTermTable::from_json`）的校验与匹配规则：

| 规则 | 做法 | 理由 |
|---|---|---|
| schema 版本 | 必须等于 `1`，否则 `UnsupportedSchema` | 不理解就拒绝 |
| 未知字段 | `deny_unknown_fields` | 拼错的字段不能静默忽略 |
| 同语言同变体映射到两个规范词 | **拒绝编译** | "该替换成哪个"必须唯一 |
| 变体 == 规范词 | **拒绝编译** | 替换成自己 = 永远违规，属于配置错 |
| 大小写 | 仅 ASCII 不敏感，其余按码点精确 | 不做 locale case folding，避免"土耳其语 i"类暗坑 |
| 整词 | 变体首尾都是 ASCII 字母数字时要求词边界 | `AI` 不命中 `RAIL`/`AIs`/`AI_x` |
| 重叠 | 最长优先 + 左到右贪心 | 结果与输入顺序无关，完全确定 |
| 复检 | 单次扫描，替换结果不再被检查 | 否则互相包含的术语会来回替换成环 |
| 受保护跨度 | 用与规则引擎**同一个** `text::protected_spans` 切分后跳过 | 一套扫描器，不会"规则认得、术语表不认得" |
| 规模 | `MAX_TERMS = 4096`、变体总字节 `256 KiB`，超限拒绝编译 | 匹配是 `O(文本 × 变体)`，不给上限就是留了个拖慢每次翻译的入口 |

### 2.5 P2.4 结构化诊断（`translator-core::diagnostics`）

```rust
pub struct TranslateOutput { pub result: TranslationResult, pub diagnostics: TranslationDiagnostics }
pub struct TranslationDiagnostics {
    engine_id, capability, route_reason, cache_hit, source_assumed,
    rules_version, resource_fingerprint,
    rules: Option<RuleTrace>,            // id / version / applied[]
    protected_spans: Vec<ProtectedSpan>, // UTF-8 字节偏移
    restore_missing: Vec<String>,
    term: Option<TermTrace>,             // id / version / policy / replaced / violations[]
}
```

- 入口是 `Translator::translate_with_diagnostics()`，与 `translate()` **共用同一段实现**
  （`Coordinator::run` 返回 `TranslateOutput`，`translate` 只取 `.result`），因此不可能给出不同译文；
- **没有**新增 `TranslationWarning` 变体（ADR-008 继续成立）。术语不一致只发既有的
  `TermMismatch`（常量级事实），结构化明细走诊断；
- 缓存条目从 `TranslationResult` 改成 `CacheEntry { result, diagnostics }`：
  否则会出现"第一次报术语违规、第二次不报"的假象；
- 诊断里含用户原文片段（URL / 模板变量），文档与类型注释都写明"只回给发起请求的调用方，不要写进集中式日志"（`docs/01` §4.1）。

### 2.6 P2.5 `dictionary.sqlite.v2`

| | v1 | v2 |
|---|---|---|
| 表 | `entries` + `senses` 两张 | `entries` 一张（释义内联） |
| 读一个词条 | 2 次 B-tree 查找（`entries` + `senses`） | 1 次 |
| 释义分隔 | 独立行 `(entry_id, idx)` | `entries.senses` 用 U+001F 连接 |
| 自报版本 | `PRAGMA user_version = 0` | `PRAGMA user_version = 2` |
| 清单 | `schema_version: 1` | `manifest_schema_version: 2` + `payload_schema_version: "dictionary.sqlite.v2"` |

- 写入侧：`pack-dictionary --payload-schema dictionary.sqlite.v2`（**默认已是 v2**，
  `--payload-schema dictionary.sqlite.v1` 可复现历史包）；
- 读取侧：`DictionaryPackage::open` 先看清单声明，再看库文件 `PRAGMA user_version`，
  **两者不一致就拒绝打开**（最容易犯的错：改了打包参数忘了同步清单，结果"读得到词条但释义为空"）；
- 释义里出现 U+001F 时打包直接失败（选了 C0 控制符做分隔，就不允许语料里自然出现它）；
- `translator-resource` 的 `PayloadSchema` 增加 `DictionarySqliteV2`，`HostSupport::current()` 同步；
- v1 保持完全可读，旧包不需要重打（CLI 演示里两个版本共存于同一仓库，一个 v1 一个 v2）。

### 3.2 P2.5 实测：v1 vs v2（真实 CC-CEDICT）

```bash
CEDICT_SOURCE=/tmp/cedict cargo test --release -p translator-dictionary \
    --test bench_d02 -- --ignored --nocapture
```

```
解析            113 ms，125365 条词条（跳过畸形行 0）

--- dictionary.sqlite.v1 ---
打包            1636 ms（121584 记录 / 197593 键）
index.fst       1695.1 KB
entries.sqlite  18.2 MB
精确查询 p50 17.36 µs  p95 23.22 µs  p99 28.59 µs  均值 18.39 µs

--- dictionary.sqlite.v2 ---
打包            1000 ms（121584 记录 / 197593 键）
index.fst       1695.1 KB
entries.sqlite  13.6 MB
精确查询 p50  8.98 µs  p95 12.54 µs  p99 16.70 µs  均值  9.84 µs

===== 对比 =====
p50 变化         -48.3%（v2 相对 v1）
库体积变化       -25.1%
```

两点交叉验证：

- v2 的 8.98 µs 与 D-01 里"单条 SQL 7.0 µs + FST 查找"的数量级吻合，
  说明 v2 基本吃掉了原来第二条 `senses` 查询的成本（`docs/04` §6.3 的 `裸 SQLite p50 14.1 µs / 单条 SQL 7.0 µs`）；
- 打包耗时同时从 1636 ms 降到 1000 ms（每词条少一次 `INSERT`）。

历史基线可复现：`bench_d01` 固定用 v1，重跑仍是 `精确查询 p50 16.67 µs / 前缀 p50 19.32 µs / 裸 SQLite 14.12 µs`，
与 `docs/04` 记录的 16.9–17.1 µs 一致（差异在机器噪声范围内）。

最后一组是 P2.4 最该被验证的场景：**同一句里三个 `AI` 都落在受保护跨度内**，

## 4. 与原设计的偏差及原因

### 4.1 主动偏差（做了不同选择，并说明理由）

| # | 设计/预期 | 实际 | 原因 |
|---|---|---|---|
| 1 | R-04 要求"暴露匿名 RSS / 文件映射 RSS / 峰值" | 只暴露**下界估计**与分解，不读任何系统 RSS | 读 `/proc/self/statm` 或 `GetProcessMemoryInfo` 需要平台层，`translator-core` 不允许引平台依赖；且"预算归属"本来就跨不过 SQLite 页缓存与分配器碎片。宁可给可解释的下界，也不给一个看起来精确的假数字 |
| 2 | `cleanup(id, keep) -> Vec<String>` | 改成 `-> CleanupReport { removed, kept_leased }` | 有租约的版本会被跳过。如果仍返回 `Vec<String>`，"跳过了谁、为什么"就没有出口——静默保留与静默删除一样有害 |
| 3 | 缓存存 `TranslationResult` | 存 `CacheEntry { result, diagnostics }` | 不缓存诊断会让"第一次报违规、第二次不报"，读起来像问题自愈了 |
| 4 | `DictionaryManifest.schema_version: u32` | 改为 `Option<u32>` + 两个新 `Option` 字段 | v1/v2 清单字段名不同。用"先按 v2 试、失败再按 v1 试"会把字段拼错的 v2 静默降级成 v1，属于猜——本 SDK 不做 |
| 5 | P2.5 预期用 `WITHOUT ROWID` 等结构优化 | 只做"释义内联"，`entries` 仍是普通 rowid 表 | `id INTEGER PRIMARY KEY` 的 rowid 表本来就是单次 B-tree 直取；`WITHOUT ROWID` 的收益主要在非整数主键。既然收益点不在这里，就不顺手改一个没有测量支撑的结构 |
| 6 | P2.3 计划里的 "single-flight" | 未实现 | P2 没有"按需加载"路径：资源在 `build()` 一次性绑定，"同一次加载被多线程同时触发"这个场景不存在。安装路径的并发由"持锁 + 落位前重检"处理，并有 `并发安装同一版本只有一次成功` 测试 |
| 7 | P2.3 计划里的 "引用计数 / TTL / LRU" | 未实现（只有租约 + 预算准入） | 这两者是**模型热卸载**的机制。P2 没有真实模型、没有卸载动作，实现出来只能是一个永远不会被调用的空壳 |
| 8 | 跨进程锁可用 `flock`/`LockFileEx` 做强保证 | 用 `O_EXCL` 锁文件 | 不引 `libc`/`windows-sys`（`translator-resource` 刻意只依赖 `serde`/`serde_json`/`sha2`）；`flock` 在 NFS 上语义不保证，而 `O_EXCL` 至少会明确失败。取舍见 ADR-017 |
| 9 | 租约可用内核强制锁 | 协作式文件租约 | Windows 上"强制共享"与"多进程只读共享"直接冲突；Unix 的 advisory 锁绕开同样无效。选择"可见的协作式 + 明确拒绝删除"，见 ADR-018 |
| 10 | 术语匹配可用 Aho-Corasick | 朴素多模式扫描 + 编译期上限 | 引新依赖换"几千条术语时快几毫秒"，在 P2 没有真实负载支撑；改用一个**可解释的上限**（4096 条 / 256 KiB）挡住异常输入，实测常见规模在亚微秒级 |
| 11 | `translate_with_diagnostics` 建议字段含 `request_id` / `execution_plan_id` | 未提供 | `request_id` 需要全局自增或 UUID 依赖，且宿主要的是"这次调用的快照"，它自己就能持有；`execution_plan_id` 属 ADR-011（仍未落地）。**不预留空字段**，避免让人以为有计划实体 |
| 12 | ADR-011（执行计划哈希进缓存键） | 仍未落地，指纹仍是 `id@version` 字符串（现在含规则包与术语表版本） | 计划形状要等 P3 真实后端（tokenizer / 模型变体）接入后才稳定，现在定死会立刻返工 |

### 4.2 本轮发现的、已修正的问题

| 问题 | 症状 | 修正 |
|---|---|---|
| `bench_d01` 直接查 `senses` 表 | 切到 v2 后报 `no such table: senses`，基准挂掉 | 把 D-01 **固定**在 v1（它是 `docs/04` 的历史基线，必须可复现）；v1/v2 对比另开 `bench_d02` |
| 清单与库文件格式可任意错配 | "读得到词条但释义为空"这种沉默错误 | 打开时校验 `PRAGMA user_version` 必须与清单声明一致，否则拒绝打开 + 专门测试 |
| 预算里"打开时配置的页缓存"与"估算假设的页缓存"是两处魔法数 | 一旦漂移，估算就是错的 | 抽出 `SQLITE_CACHE_KIB` 常量，两处共用 |
| `cleanup` 遇到被租用版本 | 原本会直接删（P2.2 没有租约概念） | 改为跳过 + 记入 `kept_leased`，并有测试 |
| `install_from_dir` 全程持锁 | 一次 18 MB 安装会让所有进程等几秒 | 拆成"无锁复制校验 + 持锁落位记账" |

## 6. 明确未实现（不预留空实现）

| 项 | 为什么没做 |
|---|---|
| 运行期内存硬上限 / RSS 监控 | 需平台层，且 ADR-013 明确"不得宣传为硬上限" |
| GPU / native 分配器记账 | P3 才有真实后端 |
| single-flight、引用计数、TTL/LRU 卸载 | P2 无"按需加载 / 卸载"路径 |
| `ResolvedExecutionPlan` 与计划哈希 | 等 P3 后端形状稳定（ADR-011） |
| 术语表与 `glossary_id` 联动 | `glossary_id` 目前只是缓存键维度，真正的多术语表选择属宿主策略；把它接进来需要先定"一个请求能否带多张表" |
| 术语表编译产物（二进制格式） | 术语表规模小、解析很快；没有测量支撑就不加格式 |
| 输出侧术语约束作用于 `lookup()` | 查词返回的是词条结构（多释义 + 出处），不是一段文本，"约束哪一条释义"是产品语义问题，不在 P2 |
| v1 → v2 的重打包迁移工具 | 从源词表重打（1636→1000 ms）比"就地改库"更可靠；源数据才是唯一真相 |
| 租约心跳 / 过期 | 心跳会引入后台线程与超时语义；当前"pid 存活"判定已够用，代价是进程挂死时需人工 `reclaim` |
| Windows 上"删除已被 mmap 的文件"实测 | 本机没有 Windows 环境；代码路径保守（拒绝删除而不是试着删），但没有跨平台实测，不得声称已验证 |

## 7. 下一步（P3 之前需要决策的事）

1. **术语表与 `glossary_id` 的关系**：是"一个请求一张表"还是"多表叠加"？两者对匹配与冲突消解的要求不同。
2. **`AutoLocalFirst` 下词典命中是否也要过术语约束**：现在是"只有整句译文过"，单词直译出来的释义不受约束。
3. **v2 是否成为唯一写入格式**：读取侧双格式共存成本很低，但要不要在 P3 前把 v1 写入路径标记为 deprecated？
4. **P3 的模型装载需要真预算**：真实模型自报的 `estimated_peak_ram_bytes` 一旦出现，
   `MemoryBudget` 的下界估计问题会从"能接受"变成"必须正视"（那时可能要接受平台层依赖）。
