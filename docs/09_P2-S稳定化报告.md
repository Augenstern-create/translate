### 1.2 S-01：租约登记与卸载的原子性（C-01）

**修复前的真实缺陷**（代码核对而非猜测）：

```text
A(acquire_lease): 读 state → 1.0.0 已安装
B(uninstall)    : 拿锁 → 检查租约(无) → 删目录 → 写 state → 放锁
A               : 写租约 → 成功      ← 租约指向一个已经不存在的版本
```

`acquire_lease` 当时只做"读状态 + 写租约文件"，两次 I/O 之间没有任何排他。

**修复**：`acquire_lease` 现在与 `uninstall` / `cleanup` 使用**同一把进程内 `Mutex` + 同一个跨进程 `state.lock`**，并在锁内**重新读状态**再判断；加锁顺序两处一致（先 Mutex 后文件锁），因此不会互相死锁。

代价：登记租约要多拿一次跨进程锁。挂载是构建期动作（`build()` 内逐个资源），不在热路径上，这个代价可接受。

对 C-01 的验证分两层：

1. **结果不变量**（跨进程、确定性）：另一个进程卸载后，本进程再登记同一版本必须报 `NotInstalled`，且**不留下租约文件**，`audit()` 三方对账为干净（`别的进程卸载后租约登记被拒`）。
2. **机制不变量**：修复后的临界区真的跨进程了——子进程持锁期间父进程的动作必须超时而不是"抢走"（`跨进程持有锁时不会被误抢`）。

诚实说明：本轮**没有**做"随机交错 + 反复重放"的压测，也没有做确定性调度屏障（需要给 store 注入测试用的 barrier 钩子）。也就是说，C-01 的**结果**被确定性验证了，**竞态本身**没有被"人为制造并观察失败"。这一点写在 §3.3。

### 1.3 S-02：进程身份、锁回收与 PID 复用（C-04）

问题：`O_CREAT|O_EXCL` 的锁文件在持有者崩溃后会留下；只看 pid 会两头出错——pid 被复用 → 死锁永远等不到；误判 → 删掉活锁。

实现：

- `probe(pid) -> ProcessLiveness{Alive(Option<u64>), Dead, Unknown}`：Linux 读 `/proc/<pid>` 并解析 `stat` 的 starttime（jiffies）；非 Linux 返回 `Unknown`。
- `process_start_id(pid)`：先定位 `/proc/<pid>/stat` 最后一个 `)`，再数到第 22 个字段（`comm` 可含空格与括号，不能按空白切）。
- `record_is_live(pid, recorded_start)`：`Dead` → 失效；`Unknown` → **按存活处理**（保守）；`Alive` 且两边都有 starttime → 必须相等。
- 锁文件写入 `pid=` / `start=` / `unix=` / `holder=`；`lock_is_stale` 用同一判定；`LockTimeout` 带上锁文件路径与持有者名字。
- 租约文件新增可选 `start_id`（`serde(default)`）：旧格式租约仍可读，按"只知道 pid"处理。

**故意不做的事**：无法判定存活时**不**判死。代价是偶尔需要人工 `reclaim`，收益是绝不删除别人正在 mmap 的目录。非 Linux 上所有租约都会显示"无法判定"，因此**跨进程测试整个文件 `#![cfg(target_os = "linux")]`**——不假装别的平台跑过。

### 1.4 S-03：术语安全默认值 + 源文触发

三处行为变更：

1. **默认策略 `Warn`**：`TermPolicy` 的 `Default` 从 `Enforce` 改为 `Warn`。这是**破坏性变更**（见 §3.2 偏差 1），理由：术语表可能来自第三方，误改用户译文属于"不可见的产品行为变更"；`Warn` 仍然把违规位置交出，由宿主决定。
2. **源文触发**：术语规则新增 `source_variants: Vec<String>`。规则声明了触发条件时，只有**源文命中**才验证/改写译文；未声明则维持原语义（只看译文）。契约新增 `TargetTermGuard::apply_with_context(&TermContext)`，默认实现退化为 `apply`——旧实现方不需要改代码就不会编译失败。
3. **字典直出不受改写**：`lookup()` 保持原样；`translate()` 的词典直出不套用强制替换（ADR-020）。本轮只做"不接"这一半，**没有**实现"源文命中但译文缺失"的重译建议（见 §3.3）。

为什么源文触发是必要的（审查 §3.4 的例子）：

```text
术语：calculator ← computer（触发词：计算器）
源文「这台 computer 不错」→ 译文中出现 computer，但源文没有"计算器"
  只看译文：误判为术语违规并改写成 calculator（错）
  源文触发：跳过该规则（对）
```

CLI 实测见 §2.4，三档结果刚好覆盖"默认不改 / 显式改 / 条件不满足不改"。

### 1.5 S-04：缓存与资源指纹

`Coordinator::bind_resource_fingerprint()` 的语义是"绑定即失效"：写入新指纹并清空缓存。本轮补的是**证明**而不是实现：

- `资源指纹变化必须重新执行`：用一个每次调用都换标记的测试引擎，断言调用次数从 1 变 2 且译文文本变化——证明是"真的重新跑"，不是"命中后换了个警告"。
- `诊断里能读到本次使用的资源指纹`：诊断必须报出真正进键的指纹，否则用户无法排查"这条译文是哪份资源算的"。
- `空指纹不会抹掉已绑定的指纹`：空串表示"没绑定"，不是"绑定为空"。

仍未做：`content_digest`（审查 D-01）与 `ResolvedExecutionPlan` 稳定哈希（ADR-011/023）——见 §3.3。

### 1.6 S-05：三方对账与恢复

`StateAudit` 是**只读快照**，回答"state / installed / staging / 租约 是否自洽"：

| 字段 | 含义 | 能否自动修 |
|---|---|---|
| `missing_dirs` | state 里有记录、磁盘没目录 | ❌ 不删记录（数据丢失方向，由人决定重装还是清记录） |
| `orphan_dirs` | 磁盘有目录、state 没记录 | ✅ 但必须**显式** `prune_orphans()` |
| `active_missing` | 激活版本目录缺失（最严重：任何挂载都会失败） | ❌ |
| `staging_dirs` / `stale_tmp_files` | 半成品（按定义可清） | ✅ `recover()` |
| `lease_files` / `stale_leases` | 租约总数 / 其中已失效数 | ✅ `reclaim_stale_leases()` |

`prune_orphans()` 仍然尊重租约：被租用的孤儿目录**不删**（另一个进程可能正 mmap 它）。

CLI：`resource audit`（只报告，有需要人介入的项时退出码 1）与 `resource audit --prune`。

## 3. 与原设计的偏差及原因

### 3.1 审查 §2.2 风险表：逐条裁定

| 等级 | 审查提出的风险 | 本轮裁定 | 依据 |
|---|---|---|---|
| **P0** | `acquire_lease()` 与 `uninstall()` 竞态 | ✅ **确认存在并已修复** | 修复前代码路径核对（§1.2）+ `别的进程卸载后租约登记被拒` |
| **P0** | 活跃版本切换与应用持有的句柄 | ✅ **已确认边界**：`dictionary_from_store` 走租约（`acquire_lease` → `Translator._leases` 持有到门面释放）；`dictionary_package(dir)` 直连目录**不受仓库保护**，这是设计选择并已在文档写明 | `从仓库挂载的版本在存活期间删不掉`；`lib.rs` 注释 |
| **P0** | 锁文件陈旧恢复 / PID 复用 | ✅ **已实现**（进程启动标识 + 保守判定） | 4 条单元 + 3 条跨进程 |
| P1 | `state.json` 与目录的断电一致性 | ⛔ **未解决**：只做文件级 `sync_all()` + `rename`，**没有** fsync 父目录、也没有 fsync 已安装目录树；Windows 语义未验证 | `store.rs::write_state` |
| P1 | 同版本目录的不可变性 | ⛔ **部分**：安装时校验并拒绝重复安装；**加载前不重新校验**内容（trust-on-install），外部篡改不会被发现 | 无 verify-on-load 代码 |
| P1 | 依赖与清理 | ⛔ **未解决**：安装时检查依赖存在（`compat::check`），但**没有反向引用检查**，`cleanup`/`uninstall` 可能删掉别人依赖的版本 | `compat.rs` 只有正向检查 |
| P1 | Linux/Windows 跨进程兼容 | ⛔ **pending**：只在 Ubuntu 实测 | §1.8 |
| P2 | 精确版本依赖（无 semver 范围） | ✅ 保持现状（审查同意） | — |

### 3.2 偏差列表

| # | 偏差 | 原因 | 影响 / 处置 |
|---|---|---|---|
| 1 | `TermPolicy` 默认从 `Enforce` 改为 `Warn` | 审查 D-02/§3.4 拍板；P2.4 的默认值是"悄悄改用户译文"，属于产品语义风险 | **破坏性**；`p24_terms_diagnostics` 中 2 条断言改写的用例补了显式 `Enforce`，并新增 `默认策略只报告不改写` 锁死新默认值 |
| 2 | 术语表新增 `source_variants`，但 `schema_version` 仍是 1 | 字段可选、缺省语义不变（"只看译文"），不值得为此抬版本号打断已有表 | 旧表零改动可用；新表被旧版 SDK 读取会因 `deny_unknown_fields` 拒收——这是**有意**的（宁可拒收，不静默忽略约束） |
| 3 | 跨进程测试用"重执行本测试二进制 + `--exact` 点名 + stdout 握手" | 不引入 `assert_cmd`/独立测试二进制，零新依赖；子角色用 `#[ignore]` 隔离，正常 `cargo test` 不受影响 | 代价：父测试必须自己解析子进程输出（libtest 会先打 `test <name> ... ` 不带换行，故用后缀匹配 `READY`）；整个文件 `#![cfg(target_os = "linux")]` |
| 4 | `audit()` 不加锁 | 加锁会让对账阻塞安装，且仍无法真正给出一致快照（读 state 与列目录之间仍可变） | 文档写明"只读快照"；`prune_orphans()` 才在锁内动手 |
| 5 | `resource audit` 在需要人介入时退出码 1 | 沿用 `fsck` 惯例（有问题即非零），而不是"sdk 崩了才非零" | 帮助文本与 `docs/09` 都写明；脚本可据此判断 |
| 6 | ADR-021（预算/观测分离）标 Accepted 但 `ProcessMetricsProvider` **没实现** | 本轮只做"把话说清楚 + 禁止互相冒充"，provider 需要各平台 API 与真机数据 | 已在 ADR 与本文 §3.3 标注未实现；不宣称"已有 RSS 观测" |
| 7 | ADR-019 的 `content_digest` 未实现，缓存仍用 `id@version` | 内容摘要要跟执行计划一起进键才有意义（ADR-011/023） | 已在 ADR-019 里写明"部分落地" |
| 8 | 逐词/短语的"源文命中但译文缺失 → 建议重译"未做 | 需要重译策略与代价模型，属 P3 产品决策 | 只做了"不误改"的一半 |
| 9 | 没有做崩溃注入（C-03 只覆盖残留状态） | 需要在 `commit_install`/`write_state` 注入 kill 点，属测试基础设施投入 | 明确 pending |
| 10 | `LeaseInfo` 新增字段未加 `#[non_exhaustive]` | 保持内部结构简单；本项目无外部构造方 | 若未来公开为稳定 API，应补 |

### 3.4 对 P3 的准入结论

按审查 §5 的门槛，本轮给出的答案是：

- **可以进入 P3.1**：P0 的三项已收口（两项修复 + 一项边界确认并写入文档），C-01/C-02/C-04 有跨进程证据，术语默认值已不再"悄悄改译文"。
- **进入 P3.1 时必须同时做**：ADR-023 的 four-piece（single-flight、热模型租约、`ResolvedExecutionPlan`、revision 隔离）+ 崩溃注入 + 依赖反向引用。
- **P3.2 之前不得**声称任何跨平台或移动端内存结论；`docs/01` §9.3 的预算数字仍只是目标值。
