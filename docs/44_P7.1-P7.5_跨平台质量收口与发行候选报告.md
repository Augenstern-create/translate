## 1. 实际实现内容

### 1.1 G06：取消在途请求（唯一真功能缺口）

台账要求的不是"支持 timeout"，而是**单 in-flight 与排队中两种状态下都能取消，且不留 zombie/native 孤儿**。本轮按这个判据实现，未新增业务错误码（继续使用既有 12 码中的 `Cancelled`）。

| 层 | 文件 | 改动 |
|---|---|---|
| 类型 | `crates/translator-types/src/lib.rs` | 新增 `CancelToken`（`Arc<AtomicBool>`，可跨线程克隆）；`TranslationError::cancelled()` |
| 插件契约 | `crates/translator-plugin-api/src/lib.rs` | `TranslationEngine::translate_cancellable` 默认实现（忽略令牌、调用 `translate`），可中断后端覆盖 |
| 协调器 | `crates/translator-core/src/coordinator.rs` | `translate_cancellable` / `translate_with_diagnostics_cancellable`；在入口、路由前、引擎调用前、引擎返回后检查令牌；取消不写缓存 |
| 门面 | `crates/translator-api/src/lib.rs` | `Translator::translate_cancellable`、`translate_with_diagnostics_cancellable` |
| 运行时传输 | `crates/translator-runtime/src/transport.rs` | `translate_with_deadline_and_cancel`；排队等待锁时每轮检查令牌，取消**不 spawn、不 kill**，立即 `Cancelled` |
| worker | `crates/translator-runtime/src/worker.rs` | `request_with_timeout_and_cancel`：20 ms 分片等待，取消时终止独占 worker；spawn 时 `process_group(0)`，终止时对**整个进程组**发 SIGTERM/SIGKILL，避免 native 子进程成为孤儿 |
| Bergamot 引擎 | `crates/translator-nmt-bergamot/src/lib.rs` | 覆盖 `translate_cancellable`；分段保护的多段调用之间也检查令牌 |
| JNI | `bindings/translator-jni/src/lib.rs` | `translate` 支持可选 `request_id`；新增 `nativeCall(handle,"cancel",{"request_id":...})`；预取消/在飞取消都映射为 `Cancelled` |

语义边界（必须对宿主说清）：

1. **取消是协作式的**。SDK 在阶段边界检查；真正阻塞在 native 解码里的调用不可中断，Bergamot 后端的做法是**终止独占 worker 进程组**，因此取消后模型需要重新 `load`，且**不会静默重放**上一条请求。
2. 排队中取消只设置标志，不触碰 worker；`metrics.spawns` 不变。
3. 关闭（`nativeClose`）语义**未改**：关闭拒绝新请求，在飞请求继续持有 `Arc` 安全跑完（P6 J-15b）。关闭不取消在飞请求，取消必须显式调用 `cancel`。
4. `translate` 不带 `request_id` 时行为与 P6 完全一致。

### 1.2 G08：安装恢复改为外部 `kill -9`

原实现用 `crash_point()` 里的 `std::process::abort()` 模拟崩溃；台账要求**独立进程在指定安装关键点被外部 SIGKILL**。

- `crates/translator-resource/src/store.rs`：`crash_point()` 在设置 `TRANSLATOR_TEST_CRASH_MARKER` 时先写标记文件，然后停在原地等外部信号；30 s 内无人杀才退化为 `abort()`（防止测试挂死）。生产路径仍只是读一次环境变量。
- `crates/translator-resource/tests/p32_lifecycle.rs`：父测试 `spawn` 子进程，等 marker 出现后用 `libc::kill(pid, SIGKILL)` 从**外部**杀死；Unix 断言 `ExitStatusExt::signal() == Some(9)`；Windows 用 `TerminateProcess` 等价路径并只断言非正常退出。
- 测试同时验证"旧版本不损坏"：先装好并激活 v1，再在 5 个关键点（`after-staging` / `before-rename` / `after-rename` / `before-state` / `after-state`）崩溃安装 v2；`recover()` 后 `audit` 干净、v1 仍是激活版本、逐文件 sha256 校验通过。

### 1.3 J-10：输入边界与资源上限

JNI 边界新增明确上限，超限返回 `InvalidRequest`，不把内存交给调用方：

| 项 | 上限 | 行为 |
|---|---|---|
| 单条文本 | 64 KiB（UTF-8 字节） | 超限拒绝；64 KiB 可正常处理 |
| 整个 payload | 256 KiB | 超限拒绝（解析前） |
| JSON 深度 | `serde_json` 默认 128 层 | 更深返回 `InvalidRequest`（不自己写第二套深度检查） |
| payload 形状 | 必须是 JSON 对象 | 数组/标量拒绝 |
| `lookup.limit` | 1000 | 超限拒绝 |
| 控制字符 | 拒绝 C0（保留 TAB/LF/CR）与 DEL | 明确拒绝，不允许静默改写 |

`payload` 缺失/畸形、未知 method、缺 `target` 等仍按 P6 行为返回稳定错误信封。
