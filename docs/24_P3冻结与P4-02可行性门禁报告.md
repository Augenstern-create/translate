## 1. 实际实现内容

### 1.1 P3 冻结：把"冻结"变成可校验的东西

`docs/23` §2.2 要求"冻结清单"，但没规定放哪。本项目规定**所有文档在 `docs/` 下编号**，
所以清单放在 `fixtures/p3-freeze/manifest.json`（机器可读证据，不是文档），由 `tools/freeze-manifest.py` 生成与校验。

```text
$ python3 tools/freeze-manifest.py --write
已写入 fixtures/p3-freeze/manifest.json
  冻结提交：318aed727d2c（tag p3.4）
  基线文件：13 个
  模型文件：5/5 在本机存在
$ python3 tools/freeze-manifest.py --check
PASS 冻结基线未被改动（commit 318aed727d2c，13 个基线文件，5 条 release-blockers）
```

`--check` 的判据是**会真的失败**的那些：tag `p3.4` 是否被移动、`p3-frozen` 是否还指向它、
`Cargo.lock` 与 13 个基线 JSON 的 sha256 是否变了、模型文件哈希、台账条目是否被悄悄删掉。
一个只会打印"OK"的冻结清单没有意义。

清单内容：

| 工具链 | rustc 1.99.1 / cargo 1.99.1 / Python 3.12.3 / Linux 7.0.0-42-generic |
| `Cargo.lock` sha256 | `4da7d9e5c952b5ae…` |
| Bergamot | commit `9271618…`，二进制路径与 sha256（本机存在时记录） |
| 模型 5 文件 | 逐个记录 `expected_sha256` 与实际值 |
| 基线文件 | 13 个（`baseline-p33-*.json` + `baseline-p3.1b-*` + `gate-ci.json`） |

| 裁定 | Conditional（发行受 release-blockers 中 open 项阻断） |

### 1.2 release-blockers 台账 + 检查器改造

`fixtures/release-blockers.json`（schema `sdk-release-blockers/v1`）登记五项：
G12 权重许可、G11 真实 runner、G06 取消在途、G08 外部 SIGKILL、D-46 许可正文。
每条有 `blocks_development=false` / `blocks_release=true`、`evidence_required`、`current_evidence`、`mitigation`。

`check-release.py` 因此多两项行为：

- **C8 台账检查**：schema、id 唯一、`status ∈ {open, closed}`、**closed 必须带 `closed_at` + `closed_evidence`**、
  open 必须写清 `evidence_required`；
- **`--release-mode`**：在上述基础上，只要还有 `open ∧ blocks_release` 的条目就 **FAIL**。

```text
$ python3 tools/check-release.py | tail -2
C8 发行阻断台账      PASS  5 项，open 且阻断发行：['G12', 'G11', 'G06', 'G08', 'D-46']（开发模式，不阻断 CI）
结论：PASS（8 项，1 项 SKIP）

$ python3 tools/check-release.py --release-mode | tail -2
C8 发行阻断台账      FAIL  --release-mode 下仍有 open 且阻断发行的项：['G12', 'G11', 'G06', 'G08', 'D-46']
结论：FAIL（1 项）—— 发行红线未满足
```

**为什么默认模式不 FAIL**：CI 每个提交都会跑 `check-release.py`，若开放条目直接让检查红，红线会变成
"永远红 → 大家开始加 `|| true`"，那才是真正的失守。发行时必须显式加 `--release-mode`，
这一条写进了 `docs/21` 的发布检查清单。

### 1.3 权重许可状态机（采纳 `docs/23` §8 的建议）

原来只有 `status: unconfirmed` + `redistribution: prohibited-until-confirmed` 两个字符串。
现在改成显式状态机，C3 逐条校验：

| status | 允许的 redistribution | 额外要求 |
|---|---|---|
| `pending` | 只能是 `prohibited-until-confirmed` | — |
| `reviewed_allowed` | `allowed` / `allowed-with-attribution` | `review.reviewed_by/reviewed_at/scope/evidence` **四项齐全** |
| `reviewed_denied` | 只能是 `prohibited` | — |

也就是说："想解除禁发"必须同时填审核人、时间、适用范围、证据——**改一个字符串是解除不了的**。

### 1.4 P4-02：候选锁定与三个 ONNX 陷阱

候选：`ort + opus-mt-en-zh`（MarianMT 6+6 层，d_model 512，int8 动态量化 ONNX）。
锁定文件 `fixtures/p4/candidate.lock.json`：9 个文件的字节数与 sha256、ONNX 输入输出签名、
分词桥接规则、已验证译文、实测延迟/内存、门禁结论。

**模型资产总量 116,343,524 字节（111.0 MiB）**——是 Bergamot 那份 51,936,351 字节的 **2.24 倍**。

#### 陷阱 1：`source.spm` 的 id **不是**模型要的 id

`source.spm` 是 32,000 piece 的 SentencePiece；模型的 id 空间是 `vocab.json`（65,001 项联合词表）。
直接用 spm id 喂模型**不会报错**，只会输出通顺但完全无关的中文：

```text
Hello world!  (spm id)  [1506, 280, 46]  →  和 大说
Hello world!  (joint id)[3828, 431, 50]  →  世间好!
```

正确路径：`spm 分词 → piece → vocab.json 查 id → 模型`；输出 `id → vocab.json 反查 piece → target.spm 还原`。
本轮还验证了 Rust 侧可行做法：按 `vocab.json` 顺序构造 Unigram 词表（id 与联合空间对齐）+ Metaspace
预分词/解码，Python 侧构造后 ids 与参考分词器完全一致（`3828/431/50`）。

#### 陷阱 2：merged decoder 首步的 encoder 侧 K/V 必须给真实长度

`use_cache_branch=false` 时 decoder 侧 past 长度是 0，但 **encoder 侧 K/V 必须给 `src_len`**，
否则 ORT 在 cross-attention 的 Reshape 上直接失败：

```text
The dimension with value zero exceeds the dimension size of the input tensor
```

#### 陷阱 3：带缓存步输出的 `present.encoder.*` 是 0 长度占位

`use_cache_branch=true` 时模型不重算 encoder K/V，对应输出是空张量；把它回喂下一步就会崩。
encoder 缓存只在首步之后固定一次，之后只更新 decoder 侧。

这三条都写进了 `candidate.lock.json` 的 `onnx_signature.gotcha` 与 `tokenizer_bridge`——
P4-03 的 Rust 实现不需要再踩一遍。

### 2.4 性能与内存（B 类比较，必须这样读）

| 场景（1 线程，热态，缓存关闭） | ORT + opus-mt q8 | Bergamot（`docs/20`） | 比值 |
|---|---:|---:|---:|
| 17 字 p50 | 118.64 ms | 6.78 ms | **17.5×** |
| 94 字 p50 | 647.59 ms | 25.05 ms | **25.9×** |
| 499 字 p50 | 830.75 ms | 175.67 ms | **4.7×** |
| 进程内存（VmRSS/PSS） | 909 / 885 MiB | 340.80 / 332.56 MiB | **2.7×** |
| 模型文件 | 111.0 MiB | 49.5 MiB | 2.24× |

补充观测：

- 4 线程几乎没有改善（17 字 125.1 ms、94 字 612.6 ms）：**解码是逐 token 串行的**，int8 动态量化
  在每步都要做 dequantize，线程加不上去也没用；
- merged 与 split 两种 decoder 图在 94 字上都是 **651 ms**，所以为了体积选 merged（60.2 MB vs 116.4 MB）。

**口径声明**（写在 `candidate.lock.json` 里）：这是 **B 类比较**——不同模型、不同量化、不同运行时，
且内存数字来自 **Python 宿主进程**（含解释器与 ORT 运行库）。因此：

- **不能**说"ORT 比 Bergamot 慢 26 倍"（包含了模型差异）；
- **不能**用这组内存数字预测 Rust 插件的内存；
- 只能说："在这个候选组合上，本机的性能与内存都明显不如现有基线"。

## 3. 与原设计的偏差及原因

### D-54 冻结清单放在 `fixtures/` 而不是 `docs/`

`docs/23` 建议 `docs/p3-freeze-manifest.json`，本项目规定文档必须编号，且清单是**证据**不是文档。
放 `fixtures/p3-freeze/manifest.json`，由 `docs/24` 引用。

### D-55 PoC 是 Python，不是 Rust 插件

本轮只到 P4-02（候选与门禁）。Rust 绑定（`ort` crate）、进程隔离、插件注册、替换合同测试都还没做，
因此 **P4-G01/G02/G03/G06/G07 一律未满足**。§4 给了实施清单。

### D-56 候选与基线模型不同 → 只能做 B 类比较

`docs/23` §3.3 的 A 类（同模型同精度比 runtime）在当前资产上**不可能**：
Mozilla 的 intgemm 权重无法被 ORT 直接执行，而上游也没有同族的 ONNX 导出。
所以本报告只做 B 类，并且明确不把差异归因于 runtime。

### D-57 `tokenizer.json`（3.8 MB）不入库

分词桥接在 Rust 侧需要一份 Unigram 词表；它是**从 vocab.json + spm 派生**的（可复现），
所以不入库，由 `tools/p4`（P4-03 落地）在建包时生成并校验哈希。

### D-58 C8 在开发模式下不阻断

见 §1.2。发行必须显式 `--release-mode`；这一条同时写进了 `docs/21` 的发布检查清单。

### D-59 4 线程没有收益

`docs/23` §7.2 要求"明确线程配置"。实测 1 线程与 4 线程差异在噪声内（17 字 118.6 → 125.1 ms），
说明这条链路的瓶颈是**逐 token 串行**而不是矩阵乘。P4-03 若继续，应优先评估静态量化/更强 CPU 而非加线程。

## 4. 下一步：P4-03/04 实施清单（尚未开始）

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1 | `tools/p4/build-tokenizer.py`：spm + vocab.json → `tokenizer.json`（Unigram，id 对齐联合空间） | ids 与参考分词器一致（3828/431/50） |

| 4 | `translator-api`：`TranslatorBuilder::nmt_ort(config)`，`supports()` 明确语言对与格式；默认 feature 不引入 ORT | 默认依赖树无 ORT（`cargo tree` 断言） |
