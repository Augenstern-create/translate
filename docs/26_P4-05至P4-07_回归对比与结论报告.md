### 1.2 本轮修掉的一个真缺陷：分词器把词表外字符**静默丢掉**

`sp10`（emoji + 中日韩混排）第一次跑就失败，错误是 `InvalidRequest`。根因不在 emoji 本身：

- `tokenizer.json` 里 `model.unk_id = None`。Unigram 没有 `unk_id` 时，**词表外字符被直接丢弃**，
  于是"只剩 emoji 的片段"变成**空 token 序列** → 引擎按"空文本"报 `InvalidRequest`；
- 更危险的是**不报错的那一半**：含一个 emoji 的正常句子只会少几个字符，译文看起来完全正常。

修法：`tools/p4/build-tokenizer.py` 里把 `unk_id` 固定为 **1**（`<unk>`），并把这个决定写进脚本注释
（`docs/25` §1.6 那个工具的产出因此变了一次，摘要记在 `fixtures/p4/derived-tokenizer.json`：
工具 `7854a649…`、产物 `801802e7…`、65,001 词条）。

修完的表现：`Deploy 🚀 to 東京 and {env} 🎯 now.` → `部署 至 _______{env}现在`
——不再报错、结构完好，但 emoji 变成下划线（这是**模型词表里没有 emoji**，见 D-71）。

### 2.2 P4-06 对比基准（同机、release、1 线程、无缓存）

热路径（`p4_bench`，10 次重采样，文本与 Python 参考逐字相同）：

| 字符数 | p50 | 首次调用（含图优化/arena 预热） |
|---|---|---|
| 17 | **118 ms** | 177 ms |
| 94 | **657 ms** | 751 ms |
| 499 | **2763 ms** | 2759 ms（长句首次≈均值，说明预热成本被解码步数摊平） |

内存（同一进程）：加载前 RSS 8.5 → 加载后 313.8 → 跑完三档 **RSS 578.3 / PSS 575.0 MiB**；单次加载 1.3 s。

加载/卸载循环 + 长稳（`p4_soak`，5 轮 + 100 次）：

| 阶段 | RSS（MiB） | PSS（MiB） |
|---|---|---|
| 第 1 轮卸载后 | 282.8 | 279.5 |
| 第 5 轮卸载后 | 249.0 | 245.7 |
| 持续翻译第 20 次 | 598.0 | 594.7 |
| 持续翻译第 100 次 | 598.0 | 594.7 |
| 卸载后 | 249.0 | 245.7 |

结论：**卸载能真的把 arena 还回去**（282 → 249 MiB），**持续翻译在 20 次后完全持平**（598.0 一直不变，
不是"涨得慢"而是"不涨了"）；100 次混合长度翻译 p50 340 ms / p95 666 ms，总墙钟 37.4 s。

A/B 分类（P4-G08 要求逐项标注）：

| 维度 | 本后端 | P3 基线（Bergamot） | 可比性 |
|---|---|---|---|
| 模型 | opus-mt-en-zh（Marian 6+6 层） | Bergamot/Marian 同族但**不同权重** | **B 类**，不同模型 |
| 精度 | int8 dynamic 量化 | fp32（Bergamot 打包权重） | 不同精度 |
| 机器 | i5-8250U / 单线程 | 同机 / 单线程 | 同机器 |

## 3. 与原设计的偏差及原因

| 编号 | 偏差 | 原因 / 影响 |
|---|---|---|
| **D-71** | **词表外字符（emoji、生僻字）不保证保留**，实测退化成 `_______` | 候选词表 65,001 项里没有 emoji，只能走 `<unk>`。要修只有两条：标记模式（本后端不支持，D-61）或改核心保护策略（`docs/23` 已冻结保护语义，ADR-044）。P3 的 Bergamot 能原样带出这些字符，所以这是**本候选的退化**。测试 `d71_词表外字符不保证保留` 把它钉成可执行事实 |
| **D-72** | LC-04/05/07/08 四条**不适用** | 没有 worker 进程、没有安装流程、没有租约。表格写在 §1.3，并因此让 **P4-G06 只能"部分通过"** |
| **D-73** | `tokenizer.json` 重建（`unk_id: None → 1`），模型身份随之变化 | 见 §1.2。旧产物会把词表外字符静默丢掉；新产物摘要记在 `fixtures/p4/derived-tokenizer.json`。因为它是**派生资产**而不是上游资产，没有写进 `candidate.lock.json` 的 `files` 列表（那份列表是上游坐标） |
| **D-74** | 长稳只做了 **5 轮加载/卸载 + 100 次翻译**（约 40 秒） | 这不是"长稳承诺"，只是把"会不会越跑越胖"这个最容易翻车的点先量一次。真正的长稳（小时级、含内存压力、含并发）需要独立台架，属 P5/P6 |
| **D-75** | 质量结论是 **C 类**（无人工评测） | 只有"机器对照 + 人工一眼看的错译清单"（§2.1）。`docs/23` P4-G08 要求的就是标注清楚，不是要求做人工评测；但"能不能替换"的最终判断必须写清楚是**基于 C 类证据** |
| **D-76** | 首个 499 字用例的首次调用 ≈ 均值（2759 vs 2763 ms） | 说明预热成本（图优化/arena）被解码步数摊平；这也意味着"首次调用慢"只对小输入明显（17 字：177 vs 118 ms）。记录以免被误读成"长句首次更慢" |

### 4.3 P4-07 结论及回退

**判定：`conditional-go`。**

- **P4 的目标（留下一个可运行的第二引擎插件 + 对照证据）：go。** 插件能装、能卸、能翻、结构保真、
  默认构建零污染、门禁全绿。
- **"用这个候选替换 P3 的 Bergamot 后端"：no-go。** 依据三条：延迟 15.7～26.1×、内存 1.7×、
  长句译文不可用（`model weights`→`模型重量`、`load time`→`负载时间`、单个 `!` 片段幻觉成脏话）。
  这不是"再调调参数就能好"的量级，属于模型能力问题。
- **回退方案（默认状态即回退）**：`nmt-ort` 与 `nmt-ort-runtime` 仍然**默认关闭**，
  P3 的 Bergamot 链路一行未改，默认构建的依赖图与二进制里没有 ORT（`cargo tree` 19 行、`ort` 0 次）。
  即"删掉这个 feature 就等于回到 p3.4 的行为"。
- **适配成本记录**（供后续选型参考）：把一个新后端接进 `Translator` 契约，本轮实际工作量集中在
  ① 分词桥接（id 空间，1 天量级的排障）、② 解码循环（merged decoder 两个坑）、③ 退化抑制（必须做，
  否则碎片会跑满 token 上限）。**契约层几乎为零改动**——这是"插件替换可行"最直接的证据。

## 5. 下一阶段建议

1. **不要把 ORT 设成默认后端**。它现在唯一的价值是"证明契约可换 + 提供一个廉价的第二实现"。
2. P4-G05（计划摘要覆盖第二 runtime）应在**开缓存之前**做完，否则第一次开缓存就会串味。
3. 若要继续这条候选线，优先解决 **D-71（词表外字符）** 与**片段级幻觉**：
   后者本质是"整句 + 哨兵"路线，而哨兵漂移（D-61）是前置问题。
4. **C 类质量证据要升级**：目前所有质量判断都是"机器对照 + 人工一眼看"。要谈"能不能上线"，
   必须先有一套固定金样本 + 人工评分口径（P6 议题）。
5. 长稳（D-74）与并发（本轮并发只测了"加载去重"和"卸载不死锁"）应一起进 P5 的台架。
