## 1. 实际实现内容

### 1.1 资源反向依赖（LC-07）

新增 `ResourceStore::dependents_of(state, id, version)`，语义明确写死：

| 依赖声明 | 何时算"被依赖" |
|---|---|
| `{ "id": "X", "version": "1.0.0" }` | 只有当被删的是 **1.0.0** 时才算 |
| `{ "id": "X" }`（任意版本） | 只有删到 X **一个版本都不剩**时才算 |

三处消费：

1. `uninstall()`：激活检查 → 租约检查 → **反向依赖检查** → 才动磁盘。错误是新增的
   `ResourceError::ReversedDependency { id, version, dependents }`，消息里列出所有依赖方
   （`dictionary.dependent@1.0.0` 这种形式），而不是笼统的"在使用中"。
2. `cleanup()`：**不报错、保留**，记入 `CleanupReport::kept_dependents`。
   理由与租约一致：清理是"腾空间"，不该因为别人依赖就整次失败，但被跳过的版本必须**可见**。
3. `audit()`：新增 `broken_dependencies`，报告"已安装包的依赖声明是否还能被满足"。
   判定要求**记录在 + 目录在**：只看 `state.json` 会把外部误删当成成功（这是本轮修掉的一个真 bug，
   见 §2.5 的实测）。

### 1.2 安装关键点崩溃注入 + `audit`/`recover`（LC-08）

**注入机制**：`store.rs` 里一个 `crash_point(name)`，读 `TRANSLATOR_TEST_CRASH_POINT`，
匹配就 `std::process::abort()`——不析构、不 flush、不写日志，磁盘上留下那一刻的半成品。
五个注入点覆盖"复制 → rename → 写状态"全链路：

```text
install_from_dir         after-staging      （staging 复制并校验完）
commit_install           before-rename      （持锁、目标目录还没出现）
                         after-rename       （目录就位，state 还没写）
                         before-state       （state 已构造、还没落盘）
                         after-state        （state 已落盘，函数还没返回）
```

**持久化保证**（Linux）：文件 `sync_all()` + **父目录 fsync**。
新增 `sync_dir()`：`write_state` 在 `rename` 之后 fsync 仓库根；`commit_install` 在
`rename(staging → installed/<id>/<version>)` 之后 fsync `installed/<id>`。这样：
"内容在、名字不在"和"名字在、内容不在"两类断电半成品都被排除。非 Unix 平台没有可移植的
目录 fsync，`sync_dir()` 显式跳过（**不假装**跨平台持久化已保证）。

**`recover()` 从"只清半成品"扩展为"让仓库回到一致状态"**，新增两类动作：

| 残留 | 处理 | 安全论证 |
|---|---|---|
| `installed/<id>/<version>` 存在、state 无记录（rename 后崩溃） | 删目录，计入 `removed_orphans` | 合法安装必然"先写状态再返回成功"；写状态失败时 `commit_install` 自己会删目录，所以这种目录按定义不是有效安装 |
| state 有记录、目录不在 | 丢掉记录，计入 `dropped_records`；激活版本丢失时退回 history 里还在的版本 | 记录指向打不开的资源只会让后续挂载报错；重建目录不可能，只能收敛到"没有这个版本" |

`audit()` 仍然是**只读**的（这条边界没变），`recover()` 是唯一会动手的入口。

### 1.3 崩溃残留回收 + 进程身份核实（§4.1.6）

新增 `translator-runtime::reclaim`：

```text
sweep_snapshots(root)      → SweepReport { removed, kept_alive, unverifiable }
sweep_worker_dirs(root)    → 同上（nmt-worker-<pid>-<epoch>/ 配置目录）
```

判定用的是**身份而不是 pid**：

1. `ModelSnapshot::materialize` 在快照目录里写 `.owner`（`pid=<n>`、`start=<n>`，
   后者是 `/proc/<pid>/stat` 的 starttime）；
2. 回收时：`/proc/<pid>` 不存在 → **死**；存在但 starttime 与 `.owner` 不符 → **PID 被复用**，
   目录属于旧持有者 → **删**；一致 → **活**，保留；
3. 没有 `.owner` 的老目录、或非 Linux（读不到 starttime）→ **判定不了就不删**。

调用点两个：`ProcessTransport` 第一次 `load_from_manifest` 前扫一次快照根
（结果进 `TransportMetrics::stale_snapshots_removed/kept`）；`nmt-worker` 启动时扫一次自己的
工作目录根。

### 1.4 真实 NMT 的缓存：计划摘要作键（§4.1.1 / ADR-038）

新增 `translator-core::plan_cache`：

- `PlanCacheKey { plan_digest, target, text_digest }`——`plan_digest` 是
  `ResolvedExecutionPlan::digest()`（含 engine / runtime / runtime build / **模型五文件摘要** /
  语言对 / beam / 线程 / 保护策略 / 规则与术语 / 隐私域）；
- `PlanCache`：**有界 FIFO**（容量 0 = 关闭），只缓存成功结果，`stats()` 给出命中/未命中/条目/淘汰；
- 键里**不存原文**（用 sha256），与"诊断不写受保护原文"同一条原则。

引擎侧接线（`BergamotNmtEngine`）：

- `load()` 时算一次计划摘要并存进 `plan_digest`；
- 翻译前**先查缓存**（此时不需要加载模型）→ 命中直接返回，`elapsed_ms` 如实报告取缓存耗时；
- **卸载不清 `plan_digest`**：模型内容没变，摘要就不该变；清掉只会让"卸载后重查同一句"白跑一次
  342 MiB 的加载（实测从 715 ms 变成 0 ms，见 §2.6）。

两层缓存的关系（写进注释与报告，避免误解）：门面层按"请求指纹"缓存，引擎层按"执行计划摘要"缓存；
相同请求第二次直接在门面层命中，**根本不会进引擎**——这是正确的，不是"引擎缓存没生效"。

### 1.5 空闲回收与内存准入（§4.1.8）

- `BergamotNmtEngine::state()` → `LoadState::Unloaded | Loaded { identity, snapshot_bytes, preparation_ms, uptime_ms }`；
- `evict_if_idle(ttl)`：**有在飞请求一律不动**（`transport.active_requests() > 0` → `Ok(false)`），
  已空闲且超过 TTL 才 `unload()`；`idle_ttl` 可在配置里给，`evict_if_idle_configured()` 用配置值；
- `memory_footprint_bytes()` = 实测稳态 `NATIVE_STEADY_BYTES`（341.9 MiB）+ 模型文件字节，
  作为**下界**估计；`NATIVE_PEAK_BYTES`（413.8 MiB）单独暴露，不当上限宣传；
- `TranslatorBuilder::nmt_bergamot()` 现在会把这笔估计**记进内存预算池**：超限在 `build()` 阶段
  返回 `OutOfBudget`，不会带着"大概放不下"的状态跑起来；
- SDK 侧观测：`Translator::nmt_states()` / `nmt_cache_stats()` / `evict_idle_nmt()` / `unload_nmt()`。

### 2.5 LC-08 实测（安装关键点崩溃）

父测试用 `std::env::current_exe()` 重新执行本测试二进制（真·独立进程），子进程在被注入的
位置 `abort()`；父进程随后 `audit → recover → audit → 重装`：

| 注入点 | 崩溃后对账 | `recover()` | 修复后 | 重装 |
|---|---|---|---|---|
| `after-staging` | 1 个 staging 残留 | `removed_staging: 1` | 三方一致 | Ok |
| `before-rename` | 1 个 staging 残留 | `removed_staging: 1` | 三方一致 | Ok |
| `after-rename` | 1 个目录无记录（孤儿） | `removed_orphans: 1` | 三方一致 | Ok |
| `before-state` | 1 个目录无记录（孤儿） | `removed_orphans: 1` | 三方一致 | Ok |
| `after-state` | **三方一致**（安装其实已提交） | 无动作 | 三方一致 | `AlreadyInstalled`（如实） |

最后一行是这条测试的价值所在：如果 `after-state` 也报"孤儿"，就说明我们把一次**成功的安装**
当成残留删掉了——那是数据丢失，不是清理。

d02 模型内容变化 → 计划摘要变，但 model_id 不变

  B（改了 nonbreaking_prefix.en）
                   计划摘要 4eba81edf7d9941b   model_id nmt.enzh.mozilla@3.0#4e5accc1…  ← 一样！
  B 的缓存命中 0（全新引擎，没有跨内容版本的旧结果）

  翻译 → evict_if_idle(0) = true → state = Unloaded
  再翻译：0 ms，命中 1，模型状态仍是 Unloaded（没有为了答案重新加载 342 MiB）

e02 加载状态可观测
  快照 49 MiB / 准备 261 ms / 模型 nmt.enzh.mozilla@3.0#4e5accc1…

**d02 是本轮最重要的实测发现**：`model_id`（= `content_digest`）只覆盖**权重**文件；
换 tokenizer / 短名单 / prefix 表时它**不变**。这正是 ADR-026 写的"`content_digest` 不能当缓存键"。
现在把它写成了一条**断言**（`assert_eq!(out_a.model_id, out_b.model_id)`）：
哪天 `content_digest` 扩展到支持文件，这条断言会失败并提醒复核 ADR-026 的结论。

### 2.7 残留回收实测（`p32_reclaim.rs`，6 条）

| 用例 | 断言 |
|---|---|
| 持有者已死 | `removed = 1`，目录消失 |
| 持有者仍存活 | `kept_alive = 1`，目录**原样不动** |

| worker 工作目录 | 同上（`nmt-worker-<pid>-<epoch>/`） |
| 根目录不存在 | 空报告，不报错 |

## 3. 与原设计的偏差及原因

### D-31（LC-07）"任意版本依赖"只在删除最后一个版本时阻止

`{ "id": "X" }`（不写版本）字面上可以理解成"任何版本都行"，也可以理解成"必须有 X"。
我们选后者：只要还剩一个版本就不算破坏。理由：前者会让"升级 base 并清理旧版本"永远失败，
而那正是最常见的运维动作。语义写进了 `dependents_of` 的文档注释与本文档，不靠读者猜。

### D-32（缓存）FIFO 而不是 LRU

命中不改变淘汰顺序。代价：热键可能被后来的冷键挤掉（真实负载下命中率会更低）；收益：实现可审计
（一个 `HashMap` + 一个 `VecDeque`），不需要在每条记录上维护双向链表。换成 LRU 需要性能数据支撑，
那属于 P3.3 的活。

### D-33（缓存）只有引擎层缓存，没有跨引擎共享、没有持久化

两个 `BergamotNmtEngine` 各自一份缓存，进程退出即丢失。理由：跨进程共享需要一条缓存协议
（键的规范化、失效、并发、清理），与本阶段的"资源安全"目标无关；而持久化会让
"缓存里有一条 3 个月前的译文"变成现实，需要 TTL 与版本迁移，属于另一件事。

### D-34（缓存）`plan_digest` 在 `load()` 时计算，之后不随配置变化

`BergamotNmtConfig` 的字段是 `pub` 的，理论上宿主可以在加载后改 `protection` 再翻译——
此时计划摘要仍是旧的，缓存键会"撒谎"。处理方式：文档写明"`load()` 之后视 config 为只读"，
没有加锁也无法阻止误用（改成 `load()` 后冻结需要把 config 包一层 `Mutex`，收益不足）。
这一点在报告里显式列出，而不是假装不可发生。

### D-35（LC-08）崩溃注入用 `abort()` 而不是真的 `kill -9`

两者在"不析构、不 flush、不返回"这个层面等价；差别只在信号号（SIGABRT vs SIGKILL）与
是否产生 core。选 `abort()` 是因为不需要引入 `libc` 依赖，也不需要额外的信号处理代码。

### D-36（LC-08）`recover()` 的语义从"只清半成品"扩大为"收敛到一致状态"

`audit()` 的注释原本写着"程序不该替用户决定"，本轮让 `recover()` 删孤儿目录、丢掉效记录，
是**语义扩大**。安全论证见 §1.2 表格。没有改 `audit()`：它仍然只报告。
另外，子进程辅助测试 `child_install_with_crash` 在没被父进程点名时会**直接 return**——
这样 `cargo test -- --ignored` 全量跑不会因为辅助角色缺环境变量而失败（第一次全量跑就踩到了）。

### D-37（持久化）目录 fsync 只在 Unix 上做

`sync_dir()` 用 `#[cfg(unix)]`。Windows 没有可移植的目录 fsync，`sync_dir()` 直接跳过。
这意味着"断电后 rename 的目录项是否可见"在非 Unix 上**没有保证**，报告里如实写，
不用"跨平台持久化"这种说法。

### D-38（空闲回收）只有 API，没有后台线程

`evict_if_idle(ttl)` 需要宿主在自己的定时器里调用（CLI 传 `--nmt-idle-ttl` 也只是把值放进配置）。
不内置后台线程的理由：SDK 不该偷偷起线程改内存占用，尤其宿主可能自己已经在管生命周期。
代价是"没人调就永远不回收"，这一点写在 ADR-037 的增补里。

### D-39（性能）反向依赖扫描是 O(已安装版本数) 次清单读取

每次 `uninstall`/`cleanup` 都会遍历所有已安装版本、读它们的 `manifest.json`。资源规模在
几十个包时无害（毫秒级），上百个包时会有明显开销。没有加索引（索引本身也要维护一致性），
属于"先正确，等有规模再说"。
