## 1. 验收口径与结论

| 验收项 | 口径 | 结论 |
|---|---|---|
| 可离线查词 | 不联网、不接模型，从磁盘包查中文词条并给出英文释义与许可 | ✅ 通过（`translator-cli --dict resources/zh-en lookup 计算机`） |

| 完整性校验 | 每个文件 sha256 + 字节数，清单里的占位符直接拒收 | ✅ 通过（`manifest.validate()` + `open(root, verify=true)`） |
| 许可可追溯 | 每条释义都带来源 id 与 SPDX，包内附 LICENSE 原文 | ✅ 通过（CC BY-SA 4.0 原样落盘） |

| 规则引擎（§7.2） | 声明式规则、构建期编译、金样本强制、语言对门控 | ✅ 最小实现，见 §5 |

一句话结论：**P1 的“离线查词 + 词库可替换 + 最小规则引擎”三条都已成立，且用真实 12 万词条词库验证过；规则引擎按 §7.2 做到了「声明式 + 编译校验 + 金样本」，但只实现了两种动作（NFKC、术语替换），分句/词形/正则刻意没做（原因见 §5.4、§9.1）。**

## 3. 资源包格式 v1

### 3.1 目录结构

```
<pack-dir>/
├── manifest.json     # 清单：身份、许可来源、逐文件 sha256 与字节数
├── index.fst         # FST 键索引：UTF-8 词条 → 1 起始记录 id
├── entries.sqlite    # 只读记录库：entries + senses
└── LICENSE.txt       # 许可证原文（随包分发，不依赖网络）
```

### 3.2 `manifest.json`

```json
{
  "schema_version": 1,
  "id": "dictionary.cc-cedict.zh-en",
  "version": "0.1.0",
  "kind": "dictionary",
  "language": "zh-Hans",
  "target_languages": ["en"],
  "entry_count": 121584,
  "provenance": {
    "name": "CC-CEDICT",
    "source_url": "https://www.mdbg.net/chinese/dictionary?page=cc-cedict",
    "revision": "snapshot-2026-11-05",
    "license_spdx": "CC-BY-SA-4.0",
    "license_file": "LICENSE.txt",
    "retrieved_at": "2026-11-05"
  },
  "files": [
    { "path": "index.fst", "sha256": "db3a5cac…", "bytes": 1735750 },
    { "path": "entries.sqlite", "sha256": "3c4040b4…", "bytes": 19103744 }
  ]
}
```

### 3.3 SQLite 表

```sql
CREATE TABLE entries (
  id INTEGER PRIMARY KEY,      -- 与 FST 值一致，从 1 开始
  headword TEXT NOT NULL,
  normalized TEXT NOT NULL,
  traditional TEXT,            -- 繁体写法（若与简体不同）
  pinyin TEXT,
  pos TEXT,                    -- '|' 分隔
  source_id TEXT NOT NULL,
  source_license TEXT NOT NULL,
  confidence REAL NOT NULL
);
CREATE TABLE senses (
  entry_id INTEGER NOT NULL,
  idx INTEGER NOT NULL,
  definition TEXT NOT NULL,
  PRIMARY KEY (entry_id, idx)   -- 天然按 (entry_id, idx) 有序，查某词全部释义不需要额外排序
);
```

### 3.4 校验规则（`DictionaryManifest::validate`）

- `schema_version` 必须是已知版本（当前 1），否则拒收 —— 避免旧 SDK 静默误读新格式；
- `provenance.license_spdx`、`source_url`、`revision` 命中占位符白名单（`REQUIRED`/`TBD`/`TODO`/`UNKNOWN`/空串）直接报错 —— **不允许“先合进来以后再补许可”**；
- `files` 里每个文件必须存在且字节数一致；`verify=true` 时逐文件比对 sha256。

## 4. 关键设计决策

### P1-D1 词典做成可选 feature，不动既有 API

设计要求“替换词库不改 API”，但真实词库会引入 `fst` / `rusqlite` / `memmap2` / `sha2` 四个外部依赖。若直接进主路径，等于让所有宿主（含 Android）都得编一遍 C 版 SQLite。

做法：`translator-api` 增加 `dictionary` feature，默认关闭。

```toml
[features]
default = []
dictionary = ["dep:translator-dictionary"]
```

- 关：P0 的能力完全不变，仍只依赖 `pollster`；
- 开：`builder.dictionary_package("resources/zh-en")` 一行挂载，返回的 `Translator` 类型完全相同。

验证：`cargo tree -p translator-api` 在默认 feature 下不含 `rusqlite`；`cargo test -p translator-api`（默认 feature）与 `--all-features` 都通过。

### P1-D2 记录 id 从 1 开始，不用 0

FST 的 `MapBuilder` 允许任意 `u64` 值。第一版从 0 编号，于是 `id=0` 的词条在 SQLite 里查不到（`INTEGER PRIMARY KEY` 与 `AUTOINCREMENT` 语义都从 1 起），前缀查询直接 `Query returned no rows`。

现在打包时显式写入 1 起始的 `id`，插入语句显式带 `id` 列，不做隐式自增。测试 `打包后可被重新打开并查询` 覆盖这条。

### P1-D3 简繁双键 → 同一个 record，查询必须按 id 去重

CC-CEDICT 的一行是 `繁体 简体 [拼音] /释义/`。打包时把简体和繁体**都**写进 FST，值指向同一个记录 id。否则繁体输入查不到词。

副作用：`lookup("计算机")` 会先精确命中简体键，前缀流里又会遇到繁体键指向同一条记录，导致同一条词条出现两次。查询侧用 `HashSet<u64>` 按 record id 去重（`crates/translator-dictionary/src/lib.rs::lookup`）。测试 `前缀查询返回补全且不重复` 覆盖。

### P1-D4 只读 + mmap，把“内存”变成“页缓存”

- `index.fst` 用 `memmap2` 映射，`fst::Map` 直接在映射上二分，**不复制进堆**；
- `entries.sqlite` 以 `SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_NO_MUTEX` 打开，并设 `mmap_size=256MB`、`cache_size=-2000`（2 MB）。

效果：12 万词条的包，打开后立刻占用的 RSS 只有 ~128 KiB；查询触达的页才进 RSS（见 §6.3）。这对移动端是决定性的——冷启动不预读 19 MB。

代价写在 §8.3：RSS 会随随机查询逐步上涨，属于页缓存而非泄漏。

### P1-D5 语句缓存与语言标签缓存（基准驱动，不是凭感觉）

第一版 `load_entry` 用 `conn.query_row(...)` 和 `conn.prepare(...)`，每次查询重新 `sqlite3_prepare_v2` 两条 SQL。D-01 基准显示 release 下 p50 = 29.3 μs，而“同样的两条 SQL 直连 SQLite”只要 14.1 μs —— 差出来的 15 μs 全在 prepare 上。

改为 `prepare_cached` 后 p50 = 16.2 μs（−44%）；随后把清单语言在 `open()` 时解析成 `LanguageTag` 缓存起来（不再每次查询重新规范化字符串），p50 再降到 16.0 μs，剩下的 2 μs 是 FST 查找 + 结构体组装。

结论：**当前 87% 的查询耗时是 SQLite 本身**，继续优化只能改 schema（见 §9.2）。

### P1-D6 语言识别先做零模型启发式，接口留好

`translator-analysis` 定义 `LanguageIdentifier` trait，当前实现是脚本级启发式（假名→ja、谚文→ko、汉字→zh-Hans + ja 候选、西里尔→ru/uk、阿拉伯→ar/fa、拉丁→en + fr/de 候选）。`translator-core::text::guess_language` 只依赖 trait，将来注入 fastText 实现时调用方零改动。

设计文档 §7 要求“短文本或低置信度必须返回多个候选”，启发式实现直接返回候选列表（汉字的 zh-Hans 置信度只有 0.60，并附带 ja 0.25），测试 `汉字应返回多个候选` 固定这个行为。

## 5. 规则引擎（§7.2 / §7.3）

### 5.1 §7.2 覆盖情况

| §7.2 条目 | 状态 | 落地位置 |
|---|---|---|
| 可配置规范化（不做无条件 NFKC） | ✅ | 基础层 NFC + 空白折叠（`text::normalize`）；NFKC 作为**可选规则** `{"kind":"nfkc"}` 显式开启 |
| 声明式规则格式（JSON） | ✅ | `translator-rules` |
| 构建时编译为只读二进制 | ✅ | `RuleEngine::to_bytes()`：magic `TRULE\0` + schema + version + payload + sha256 |
| `schema_version` | ✅ | 未知版本直接拒收，不猜字段含义 |
| 语言对 | ✅ | `language_pairs: [["zh-Hans","en"]]`，`"*"` 通配；空数组 = 所有语言对 |
| 优先级 | ✅ | `priority` 升序，相同优先级保持文件内顺序（稳定排序） |
| 匹配条件 | ✅ | `contains`（子串）、`is_single_word`（复用 core 的 CJK 阈值判定）；两者可叠加 |
| 测试样本（金样本） | ✅ **强制** | 每条规则必须带 `samples`；编译时按"执行到本规则为止"跑一遍，不匹配就拒绝加载 |
| 术语表替换 | ✅ | `{"kind":"replace","from":...,"to":...,"whole_word":bool}` |
| 缩写展开 | ✅ | 同上，`whole_word: true`（只对空格分隔语言有意义） |
| 术语**约束**（译文必须包含某词） | ❌ | 需要输出侧校验，见 §9.1 |
| 分句 / 词形 / 标点策略 | ❌ | 分句等 P3 有 NMT 语料后再定；词形需 Lindera 与词典授权 |
| 正则类匹配 | ❌ **故意不做** | §7.3 要求防止灾难性回溯，而不带超时/长度上限的正则引擎正是该风险的来源 |
| URL / 邮箱 / `{占位符}` / 反引号代码保护 | ✅ | `text::protect` → 翻译 → `text::restore`（P0 已有），还原失败必产 `PlaceholderRestoreFailed` |

### 5.2 流水线位置

```text
校验 → 规范化 → 语言识别 → 【规则包】 → 占位符保护 → 缓存 → 路由 → 执行 → 还原 → 结果
                              ↑
              必须排在语言识别之后（规则按语言对生效）
              必须排在占位符保护之前（规则可能产出新的 URL/代码形态）
              必须排在缓存与路由之前（改写后的文本决定缓存键与走词典还是走 NMT）
```

`routing::select()` 因此新增了 `text` 参数：它原本判断 `req.text` 是不是一个词，
一旦规则把 `ｃａｔ` 折成 `cat`、把 `LLM` 展开成 `large language model`，判定结果就变了。

### 5.3 示例与实测效果

`translator-sdk/fixtures/rules/minimal.json`（3 条规则，带金样本）：

```json
{ "id": "norm.nfkc",   "priority": 10, "language_pairs": [["*","*"]],
  "action": { "kind": "nfkc" }, "samples": [{ "input": "ｃａｔ", "expect": "cat" }] }
{ "id": "term.robot",  "priority": 50, "language_pairs": [["zh-Hans","en"]],
  "when": { "is_single_word": true },
  "action": { "kind": "replace", "from": "机器人", "to": "robot" } }
{ "id": "term.llm",    "priority": 60, "language_pairs": [["en","zh-Hans"]],
  "action": { "kind": "replace", "from": "LLM", "to": "large language model", "whole_word": true } }
```

端到端对比（`translator-cli` + Mock 插件）：

```text
$ translator-cli translate "ｃａｔ"                      → 引擎 mock.nmt       译文 [nmt en->zh-Hans] ｃａｔ
$ translator-cli --rules fixtures/rules/minimal.json translate "ｃａｔ"
  规则包：id rules.zh-en.minimal v1 / 规则数 3 / 生效 norm.nfkc / 处理后 cat
  引擎    mock.dictionary                               译文 猫
```

**这条对比是本次规则引擎最有价值的证据**：没有规则时全角输入词典查不到、只能退化到 NMT；
加上规则后同一个请求走了词典并拿到了正确释义。

### 5.4 一次真实 bug：语言识别把全角字母当成"无法识别"

第一次端到端跑 `ｃａｔ` 时直接失败：

```
[InvalidRequest] 无法自动识别源语言，请显式指定 source
```

原因是 `HeuristicIdentifier` 用 `c.is_ascii_alphabetic()` 判断拉丁文本，全角 `ｃａｔ` 一个
ASCII 字母都没有 → 返回空候选 → 流水线在**语言识别**阶段就失败，规则包根本没机会执行。

这是"规则排在语言识别之后"这个顺序暴露出的真实缺陷，修法不是把规则提前（那会失去语言对门控），
而是让识别器认识全角拉丁（`U+FF21–FF3A`、`U+FF41–FF5A`）。测试 `全角拉丁字母也算拉丁` 固定该行为。

**教训**：流水线的顺序决定了哪些缺陷会被放大。规则放在识别之后，等于要求识别器
必须能处理"规则本来要修的那种脏输入"。

### 5.5 规则开销（release，本机）

| 输入 | 字节 | p50 | p95 |
|---|---:|---:|---:|
| 单词（`机器人`） | 9 | **287 ns** | 297 ns |
| 短句（14 字） | 39 | **777 ns** | 863 ns |
| 长段落（600 字） | 3,600 | 30.9 μs | 32.0 μs |
| 全角长文（1000 字，NFKC 重建整串） | 3,000 | 24.7 μs | 25.9 μs |

与词典查询 p50 17 μs 相比，**短输入下规则开销约 2%**，可以认为"免费"。
长段落上规则与翻译本身同量级，但那段文本本来就要走 NMT（毫秒级），影响可忽略。

### 5.6 为什么规则不能进 `TranslationResult`

规则 id 目前只能通过 `Translator::explain_rules()` 查看，`TranslationResult` 里没有。
原因：`TranslationWarning` 是公开枚举，加变体会破坏宿主的穷尽 `match`；而这是个 SDK，
破坏性变更必须留给大版本。折中方案是独立的诊断入口，代价是"翻译结果不携带规则 trace"。

这条是**有意取舍**，不是遗漏：

```rust
let preview = translator.explain_rules("ｃａｔ", &en(), &zh());
assert_eq!(preview.applied, vec!["norm.nfkc".to_string()]);
```

### 6.4 一次“基准数据造假”事故（保留，作为教训）

第一版基准用 `词00000 … 词09999` 当词条，跑出来：

```
记录 10000 / 键 20000
index.fst  202 B      ← 2 万个键，索引 202 字节
```

这不是 bug：**FST 是最小 DFA，会合并共享后缀和等价子树**。连续数字让 4 个数字位塌缩成几十个状态，2 万个键压到 202 字节完全合理。但它对“索引有多大”毫无参考价值——按它算出的“每键 0.01 字节”会让人误以为 100 万词条只要 10 KB。

改为固定种子的伪随机汉字词条（取自高频字池）+ 约一半词条带繁体键后，得到 **10.5 字节/键**，与真实 CC-CEDICT 的 **8.8 字节/键** 同一量级，基准才重新有意义。

这条写进这里是因为：**基准数据本身也需要被质疑**，而“数字变小了”看起来像是优化成果。

### 6.5 与设计文档 §9.3 预算对照

| 预算项 | 目标 | 实测 | 判定 |
|---|---|---|---|
| 无模型核心 SDK 额外 RAM | < 10–20 MB | 进程总 16.5 MB（含测试框架与合成数据） | ✅ |
| 字典查询状态额外 RAM | < 30–50 MB | 进程总 24.3 MB（12 万词条真实包） | ✅ |

注：§9.3 明确写了这些是“目标/停止条件，不得在 README/市场文案中称为已验证性能”。本报告只声称“本机实测值”，不做跨设备承诺。

## 8. 已知限制（诚实清单）

1. **只打包了 CC-CEDICT 一种资源**。Kaikki/Wiktionary、JMdict 只做了候选评估（见 `02_翻译资源候选与备选清单.md`），没有实现解析器。当前"多词库"能力是靠包格式支持多包，而不是已有多个包。
2. **单方向**：`zh-Hans → en`。包里 `target_languages` 是数组，结构上支持多向，但没有 en→zh 的词库（CC-CEDICT 是汉英单向的）。
3. **RSS 会随查询上涨**。`entries.sqlite` 走 mmap，查询触达的页计入 RSS；实测随机查询 1 万次后 +9.8 MB（真实包）。这不是泄漏（页缓存可回收），但如果宿主需要硬上限，得把 `mmap_size` 调小或改成普通 pread 模式 —— 这一项还没做压力测试。
4. **`lookup` 的 `limit` 是“最多返回”，不是“恰好返回”**：精确命中优先，前缀补全在后，去重后可能少于 `limit`。
5. **没有做 `shared_cache` / 多连接**。`DictionaryPackage` 内部是一个 `Mutex<Connection>`，串行化所有查询。单线程 p50 16 μs，但并发场景未测（P5 再评估）。
6. **前缀查询结果未按相关性排序**，就是 FST 的字节序（对中文而言约等于字典序），不是词频序。
7. **`confidence` 恒为 1.0**（精确命中），没有做模糊匹配/编辑距离回退。输入错别字会直接 miss。
8. **基础规范化只做 NFC + 空白折叠**。全角/半角需要通过规则包的 `nfkc` 规则显式开启（`Ａ` 只有在挂载规则包后才能查到 `A`）——这是刻意的：无条件 NFKC 会改变代码与符号语义。
9. **打包工具只认 CC-CEDICT 的文本格式**（`繁体 简体 [拼音] /释义/`），其他格式要写新解析器。
10. **未做并发/多线程下的资源包热替换**（`open_as_plugins` 返回 `Arc`，替换需要重建 `Translator`）。
11. **规则只作用于源文本，不做输出侧校验**。术语"约束"（译文里必须出现某词）没有实现，因此规则无法发现引擎把术语译错。
12. **规则一次一条串行执行**，没有分组短路/索引优化。规则数到几百条时需要按语言对分桶，现在只有 3 条，实测开销 287 ns/次。
13. **规则包不带签名**，只有 sha256（防损坏，不防篡改），与词典包同一取舍。
14. **规则 trace 不进 `TranslationResult`**，只能通过 `explain_rules()` 查（原因见 §5.6）。

## 9. P1 未完成项与去向

### 9.1 规则引擎 —— 做完了框架，没做完语义

**已做**：JSON 声明式格式、构建期编译（含 magic/sha256 的只读二进制）、`schema_version`、
语言对门控、优先级、`contains`/`is_single_word` 条件、金样本强制校验、两种动作（`nfkc`/`replace`）、
`explain_rules` 诊断入口、CLI `--rules`、示例规则包。

**没做**：

| 缺什么 | 为什么现在不做 | 去向 |
|---|---|---|
| 术语**约束**（校验译文包含指定词） | 需要输出侧钩子，而 `TranslationResult`/警告枚举的扩展属于破坏性变更，要和语义规则一起规划 | P2 与 glossary 一起 |
| 分句 / 标点策略 | 分句效果依赖真实 NMT 才能评估好坏（P3 之前无法给金样本） | P3 |
| 词形（Lindera 等） | 需核实底层词典授权与移动端体积（资源文档 §9 未完成） | P3 前后 |
| 正则类匹配 | §7.3 明确要求防灾难性回溯；不引入带超时/长度限制的正则引擎就不做 | 可能永不实现 |
| 规则按语言对分桶 | 3 条规则时无意义，数百条规则时才需要 | 规则数量上来再做 |

**为什么先把框架做扎实**：规则是唯一能"在不重新训练模型的前提下修正译文"的手段，
而它也是唯一能"悄悄改坏所有译文"的手段。所以本次把成本放在**编译期拒绝坏规则**
（金样本、空操作检测、重复 id、非法语言对）上，而不是放在动作数量上。

### 9.2 用单条 SQL 换掉两次查询 —— 已知的下一步优化

当前每次查词 = 1 次 `entries` 点查 + 1 次 `senses` 范围查。基准显示这 14 μs 占全部耗时的 87%。若把释义序列化成 JSON 存进 `entries` 的一个列，可以压到单次查询，预估 p50 降到 8~9 μs。

没做的原因：这要改 schema（`SCHEMA_VERSION` 从 1 升到 2，且要保留旧包读取路径），属于破坏性变更，应当和 P2 的“资源包版本与回滚”一起做，而不是在 P1 末尾偷偷改格式。

### 9.3 语言识别换成 fastText

启发式对短文本和语码混合（如 `iPhone 好用`）会给出低置信度。fastText LID 模型 176 MB（压缩后更小），需要先评估体积是否可接受（资源文档 §9 的许可与体积审查未完成）。

### 9.4 其他延后项

| 项 | 去向 | 原因 |
|---|---|---|
| Kaikki / JMdict 打包 | P2 之后 | 需要各自的解析器与许可审查 |
| Lindera 词形分析 | P3 前后 | 需核实底层词典授权与移动端体积 |
| 并发查询压测、`shared_cache` | P5 | 需要真机与内存压力事件 |
| 词典包签名（非仅哈希） | P7 | 需要密钥管理方案 |
| 规则包签名 | P7 | 同上 |
