## 0. 结论与边界

**P3.1-C/D/E 的"能翻译"终于变成了"公共入口能翻译，且结构不会被静默破坏"**：

```text
translator-cli --features nmt -- translate 'Hello world!' --policy local --nmt --diagnose
  → 译文    你好,世界!
    引擎    nmt.bergamot.cli
    模型    nmt.enzh.mozilla@3.0#4e5accc141373565ddc8fa1565bceaa8
    运行时  bergamot-cli / 线程 1 / beam 1 / 保护 protect-seg-v1 / 计划摘要 dcc88e56fc890b9a
```

三件事各自成立：

1. **C（严格保护）**：受保护跨度（URL / 邮箱 / 反引号代码 / 模板变量）在真实 Bergamot 上**逐字节还原**；数量、身份、顺序任一不符即 `IntegrityFailure`，不返回"看起来正常"的译文。默认策略是**分段**（受保护跨度根本不进模型），标记策略保留但明确**不是安全路径**——因为实测没有任何一种标记能稳定穿过真实 Marian（§2.6）。
2. **D（生命周期）**：`ResolvedExecutionPlan` + 稳定摘要（`plan-v1`，金值已钉死）、single-flight 加载、排队截止时间、在飞请求计数（租约的可观测部分）落地；`docs/17` §4.2 的 LC-01…06/09/10 有实现与测试，LC-07/08 明确留给 P3.2。
3. **E（统一入口）**：`translator-api` 新增可选 feature `nmt-bergamot` 与 `TranslatorBuilder::nmt_bergamot()`；`translator-cli` 新增 `--nmt`；默认 `cargo build`/`cargo test` 的依赖树里**没有** `translator-runtime`/`translator-nmt-bergamot`（`cargo tree` 证据见 §2.8）。

本轮**没有**、也不声称做到：

- **P3.2**：资源反向依赖（LC-07）、安装关键点 `kill -9` 注入与 `recover()`（LC-08）、崩溃后快照清理（PID 复用核实）；
- **P3.3**：PSS / 长时间稳定性（1000 次 + 10 分钟）/ 并发吞吐 / 统一质量评分器；
- **P3.4**：权重许可证、CI、打包分发；权重**依旧不入库**；
- 任何非 Linux 平台（`docs/17` §5 的 CI 分流未接入，本机手工执行）。

**P3 不标 Done。**`docs/17` 的 pending 表在本轮只被部分改写（§5）。

## 1. 实际实现内容

### 1.1 `translator-core::protection`：保护计划（C 的核心）

新增 634 行、**不依赖任何后端**（纯 Rust，可被词典/NMT/未来远程共用）：

| 项 | 取值 | 说明 |
|---|---|---|
| `STRATEGY_VERSION` | `protect-seg-v1` | 分段策略版本（进执行计划摘要） |
| `MARKER_VERSION` | `protect-mark-v1` | 标记策略版本（进执行计划摘要） |
| `ProtectionMode` | `Segment` / `Marker` | 默认 `Segment`（理由见 §2.6） |
| `Piece` | `Plain` / `Protected(id)` / `Literal(text)` | `Literal` 专放换行 |
| `ProtectedItem` | `{id, kind, start, end, original}` | `start/end` 是**原文**字节区间 |
| `ProtectionError` | `Missing` / `Duplicated` / `UnknownMarker` / `SegmentCount` | 全部映射 `IntegrityFailure` |

要点：

- 沿用 P2 的 `ProtectedSpan` 扫描器（ADR-009），**不重写**扫描规则；`normalised_spans()` 排序并丢弃重叠，保证同一文本永远得到同一编号。
- 标记策略的掩码固定为 `#P{n}#`，但**这不代表它安全**：还原时逐 ID 校验"恰好出现一次"，出现未知标记、缺失、重复、大小写被改（扫不到）都报错。
- **换行单独成为 `Piece::Literal`**：P3.1-B 实测 worker 把 `\n` 换成空格，如果换行混在 `Plain` 里会被模型吃掉；现在换行既不进模型、也不参与 `plain_texts()` 计数。
- 分段策略的 `assemble()` 先查段数（`SegmentCount`），再按 `Piece` 顺序拼回原文片段，最后 `verify_structure()` 复核"每个片段都在、顺序不乱"。
- 诊断只给类别与数量（`describe_protection()`），**不写受保护原文**。

### 1.2 `translator-core::plan`：执行计划与稳定摘要（D 的核心）

`ResolvedExecutionPlan`（`PLAN_SCHEMA = plan-v1`）覆盖 `docs/17` §4.1.1 要求的全部维度：

```text
engine_id / runtime / runtime_build / model_revision / file.{role}=sha256（5 个文件）
/ lang.source / lang.target / decode.beam_size / decode.cpu_threads
/ protection（策略版本）/ rules_version / glossary_digest / pipeline_version / privacy_domain
```

- `canonical()`：键按字典序、`k=v` 逐行、`\` `\n` `\r` `=` 全部转义（防止字段值伪造字段）；
- `digest()`：对 canonical 字节做 sha256（64 hex），`short_digest()` 取前 16 位给日志/诊断；
- **金值锁定**：`digest()` 的具体值被钉死在单元测试里（`67d2768e…`），任何无意的编码变化都会让所有缓存身份漂移，必须显式改 `PLAN_SCHEMA` 才允许改金值；
- 真实运行的摘要（CLI 打印）：`dcc88e56fc890b9a`。

**它还不是缓存键**——真实 NMT 路径**没有接缓存**（D-22），`content_digest` 依旧只作诊断（ADR-026）。

### 1.3 `translator-runtime`：single-flight、排队截止时间、在飞租约

| 变更 | 位置 | 语义 |
|---|---|---|
| `request_with_timeout(req, timeout)` | `worker.rs` | `request()` 的显式超时版本；`WorkerConfig` 的 10 s / 30 s / 15 s 分别用于其他/加载/翻译 |
| `load_gate: Mutex<()>` | `transport.rs` | **single-flight**：只有拿到闸门的调用者真正加载，其余在闸门外排队并在进入后复用结果（LC-01） |
| `guard_until(deadline)` | `transport.rs` | 用 `try_lock` + 1 ms 睡眠轮询，到期返回 `Timeout{operation:"queue"}`；**不再在 Mutex 上无限等待**（LC-04） |
| `active_requests: AtomicU32` | `transport.rs` | 在飞翻译计数（租约的可观测部分，LC-02 的"不打断"证据） |
| `translate_with_deadline(job, deadline)` | `transport.rs` | 排队 + 执行的**绝对**截止时间 |
| `load()` 校验 `worker_epoch` | `transport.rs` | 缓存命中必须同进程代次，避免拿旧 worker 的 `loaded` 冒充（LC-03） |

**卸载语义（精确定义）**：`unload()` 取状态锁；正在翻译的请求持锁执行 native 调用，因此 unload **等待**其完成，而不是插队杀进程、也不返回"Busy"（D-23）。卸载后 `identity()` 为空，下一次 `translate` 自动重新加载（实测重载 ≈ 1.13 s，含快照 + native load）。

### 1.4 新 crate `translator-nmt-bergamot`：真实引擎（E 的核心）

492 行，一层薄适配，**不含协议细节**（帧、pid、socket 都在 `translator-runtime` 里）：

```text
BergamotNmtEngine::translate_blocking
  ├─ 空/纯空白文本 → InvalidRequest（不把空白当译文）
  ├─ load()（幂等、闸门保护）→ ModelIdentity
  ├─ ProtectionPlan::build / build_marker
  ├─ Segment：逐条 plain 段调用（空白段直接透传）→ assemble
  │  Marker ：整句掩码调用 → restore（严格还原）
  └─ TranslationResult{engine_id, model_id=revision, elapsed_ms}
```

- `ENGINE_ID = "nmt.bergamot.cli"`；`MODEL_FILES` 五项（model / srcvocab / trgvocab / lex / nonbreaking_prefix）。
- `BergamotNmtConfig` 全部路径**显式传入**（`new()` / `from_env()`），不读隐含默认；`protection` 默认 `Segment`。
- `descriptor()`：`capabilities=[Nmt]`、`priority=100`（高于 Mock）、`license="MPL-2.0 (runtime) / model weights pending"`。
- `supports()`：只认配置的那一个语言对（en→zh-Hans），不做语言对推断。
- 错误：运行时错误原码透传（`RuntimeError::code()`），保护错误统一 `IntegrityFailure`；**没有任何自动远程回退分支**。

### 1.5 `translator-api` 与 `translator-cli` 接线

- `translator-api` 新增 feature `nmt-bergamot = ["dep:translator-nmt-bergamot"]`（默认关闭）+ `TranslatorBuilder::nmt_bergamot(config)`；构造期只做文件存在性 + 摘要校验，不 spawn 进程。
- `translator-cli` 新增 feature `nmt` 与 8 个选项：`--nmt`、`--nmt-native`、`--nmt-model-dir`、`--nmt-worker`、`--nmt-snapshot-root`、`--nmt-protection`、`--nmt-threads`、`--nmt-beam`（另有 `--nmt-source/--nmt-target`），并认 `NMT_BERGAMOT_BIN` / `NMT_MODEL_DIR` / `NMT_WORKER_BIN` / `NMT_SNAPSHOT_ROOT`，**命令行优先于环境变量**。
- `--nmt` 时 CLI **先显式 load** 再进入子命令：模型坏了在启动阶段就报错，而不是第一条译文时炸。

- 未编译 `nmt` 特性却传 `--nmt`：明确返回 `CapabilityUnavailable` 并提示重编译命令，**不静默降级成 Mock**。

### 1.7 为什么默认是"分段"，不是"占位符"（本轮最重要的设计判断）

`docs/17` §3.1 的原话是"采用唯一、无碰撞的模型输入标记……不可假定某一种 marker 一定稳定"。
我们把这句话当真做了实验：**5 种候选标记 × 7 类句子**打真实 Marian，无一通过全部（§2.6）。
所以最终实现：

- **默认 `Segment`**：受保护跨度在掩码阶段就被摘出，模型物理上看不到它们；还原是把模型产出的纯文本段与原文字节拼接，因此"标记被吞/被改写"这一类失败**在结构上不可能发生**；
- **保留 `Marker`** 作为可选策略，严格校验，失败报 `IntegrityFailure`——它存在的意义是**对照实验**与未来换用更稳的模型时的备用路径，**不是**默认安全保证。
- 代价是真实存在的（§2.7）：一句话里有 N 个受保护跨度就要发起 N+1 次 native 调用，且每段失去上下文（`line1\nline2 {x}\nline3` → `线1\n线2 {x}\n线3` 读起来像逐段硬翻）。

| LC-04 | 排队第二个请求 deadline 到期 → native 调用前返回 Timeout | **通过** | `lc04`：`operation=="queue"`，耗时 < 300 ms |
| LC-05 | 翻译中 native 死亡 → 原请求失败、不重放 | **通过（沿用 P3.1-B）** | `real_bergamot.rs` 崩溃用例（12 条内） |
| LC-06 | 卸载/重载 10 轮 → 不堆积快照与进程 | **通过** | `lc06` + `sp_real_单次加载卸载后不残留快照目录`（快照目录数前后一致） |
| LC-07 | 依赖 A 引用 B → B 卸载被拒 | **pending（P3.2）** | 未实现 |
| LC-08 | 安装关键点 `kill -9` → `recover()/audit()` 可修复 | **pending（P3.2）** | 已有 `audit`，但注入测试未做 |
| LC-09 | 内容指纹变化后不使用旧模型缓存 | **通过** | `lc03`（摘要变化） |
| LC-10 | 不配置真实后端时 Mock/空资源编译测试通过 | **通过** | 默认 `cargo test --workspace`（mock_e2e 9 条等） |

### 2.6 标记策略的实测失败面（为什么默认分段）

同一批句子在真实 Marian 上的结构完整性（"保留/正确"的用例数，满分 7）：

| 标记样式 | 通过 | 典型破坏 |
|---|---:|---|
| `[[P1]]` | 0/7 | 变成 `[[P1]`（吃一个 `]`） |
| `{{P1}}` | 0/7 | 变成 `(P2})`（改写成括号） |
| `<P1>` | 0/7 | 第 2 个标记被吞 |
| `__P1__` | 0/7 | 变成 `___P4__` |
| `«P1»` / `【P1】` / `@P1@` | 0/7 | 第 2 个标记被吞 |
| `⟦n⟧` | 3/7 | 丢标记、重复标记 |
| `⟦Pn⟧` | 4/7 | 丢标记 |
| `%Pn%` | 5/7 | 出现 `5%` 之类的伪影 |
| `⟦Q7Pn⟧` | 5/7 | 丢标记 |
| `#Pn#` | **6/7** | 1 类失败：标记被复制 / `##` 伪影 |

结论：**没有一种标记能稳定穿过真实模型**，"唯一无碰撞标记"在这个后端上不成立。这正是 `docs/17` §3.1 要求"测试标记是否会被删除、复制或改变形态"的意义，也是 ADR-034 把默认策略定为分段的依据。

本轮 `sp_real_08_09` 的 4 个模板句在标记模式下**全部结构完整**（`#Pn#` 在我们的 4 个用例上恰好没踩到那 1/7），但**不能**据此把标记模式当安全路径：它依赖输入恰好落在模型"愿意照抄"的那一类里。

### 2.7 分段的代价（延迟 + 质量）

同一引擎、beam=1、1 线程，分段模式逐段调用：

| 输入 | 受保护跨度 | 耗时 | 译文 |
|---|---:|---:|---|
| `Hello world!` | 0 | 9 ms | 你好,世界! |
| `Hello {name}!` | 1 | 10 ms | 你好 {name}! |
| `call {a} and {b} at https://x.example/a` | 3 | 15 ms | 打电话 {a} 而且 {b} 在 https://x.example/a |

- 延迟随跨度数近似线性（P3.1-B 基线：热 p50 13.17 ms/次 native 调用），**没有**超出预期；
- 质量代价真实存在：`line1\nline2 {x}\nline3` → `线1\n线2 {x}\n线3`，每段独立成句、失去跨段上下文；`看 https://x.example/a 现在` 这种"现在"后置也是分段的痕迹；
- 本轮**不**给"分段 vs 标记"的质量评分（P3.3 才有统一评分器），只声明结构正确性。**不要**把 §2.3 的通过数当翻译质量分。

### 2.9 无残留核对

- 正常路径（CLI 一次完整运行）：快照根目录条目数加载前 = 加载后（2 → 2，实测另有 2 个来自更早的异常退出残留）；
- `sp_real_单次加载卸载后不残留快照目录`：`load → unload → Drop` 之后目录数不变；
- 进程：跑完 `cargo test --workspace --all-features -- --ignored` 后 `nmt-worker` / `bergamot` 无残留（测试脚手架里的 `OnceLock` 共享引擎保留 1 个快照目录，是进程退出不 Drop 静态值导致的**测试脚手架**行为，不是生产路径行为）；
- 诚实边界：`kill -9` 留下的快照**不会**被自动清理（P3.2 LC-08 范围）。

## 3. 与原设计的偏差及原因

### D-20（C，最重要）默认策略是分段，不是"占位符标记"

`docs/17` §3.1 期望"唯一、无碰撞的模型输入标记"。实测 5 种标记 × 7 类句子无一全过（§2.6），且 `docs/17` 同时写了"若真实模型无法稳定保留 marker，不得通过放宽断言宣布成功"。
因此把**分段**定为默认：受保护跨度不进模型，结构正确性由构造保证，而不是由模型"配合"保证。标记策略保留为可选 + 严格校验，并在文档里明确它**不是**安全路径。

### D-21（D）排队截止时间是轮询实现，不是队列

`guard_until()` 用 `try_lock` + 1 ms 睡眠轮询，因为并发恒为 1、没有独立队列结构。代价：没有 FIFO 公平性、最坏多 1 ms 抖动、拿不到"队列长度"指标。真要排队调度应在 P3.3 的并发工作里重做，而不是在锁上继续加参数。

### D-22（D）执行计划摘要已可算，但真实 NMT 仍未接缓存

`plan-v1` 摘要覆盖了 ADR-026 要求的五项 + 语言方向 + 保护策略 + 规则/术语，但**没有任何缓存消费者**：真实路径每次请求都重新调用 native。所以本轮只能说"缓存身份已就绪"，不能说"缓存已按计划隔离"。ADR-026 仍是 Proposed。

### D-23（D）`unload` 等待而不是拒绝

`docs/17` §4.1.3 允许"等待/安全取消/返回明确错误"三选一。我们选了**等待**（串行锁），因为返回 Busy 会把并发复杂度推给宿主，而当前并发恒为 1。代价：卸载延迟取决于在飞请求耗时（毫秒级），且没有"取消进行中请求"的能力。

### D-24（E）真实引擎是可选 feature，默认二进制不含它

`docs/17` §5 的期望命令是 `translator-cli translate … --diagnose`。实际需要 `--features nmt` 编译 + `--nmt` 运行。
理由：设计要求"默认 `cargo build` 不拉取 native C++/模型权重"，而 CLI 是 workspace 的默认成员。代价：验收命令比 `docs/17` 的示意多两个开关，这一点在 README 与本文档里都写明，**不假装**默认二进制能跑真实模型。

### D-25（E）一个引擎实例只服务一个固定语言对

`supports()` 只比 `(en, zh-Hans)`（来自配置）。多语言对需要多实例（多 worker、多 native），内存代价是 342 MiB/实例，属于 P3.3/P4 的容量规划，不在本批做。

### D-26（E）`runtime_build` 在 CLI 里是 `unknown`

native 的构建标识没有自动来源（Bergamot 不是 cargo 包，`bergamot --version` 不稳定）。CLI 通过 `NMT_RUNTIME_BUILD` 环境变量传入，未设置时如实显示 `unknown`，**不用 commit 猜**。它仍然进执行计划摘要（`runtime_build=unknown` 就是一个诚实的身份）。

### D-27（C）`Marker` 模式保留但降级为对照实验

它会在失败时正确报 `IntegrityFailure`（这是 SP-08/09 的覆盖方式），但整体可靠性低于分段。保留它的价值：换模型/换后端时可以重新测量，而不是永久失去那条路径。

### D-28（C）分段损伤译文流畅度，这是已知代价

逐段翻译丢上下文。`docs/17` 允许"对必要的文本采用安全分段或其他替代策略"，但没规定质量下限；本轮只声明结构正确，质量留给 P3.3 的统一评分器（§6.2 明确要求"结构精确保留与语言翻译质量分开评分"）。

### D-29（C）SP-08/09 的"故障注入"在分段模式下没有注入点

诚实说明见 §2.3 末段：标记模式的错误路径测得很实，分段模式的"防伪造标记"靠的是"模型看不到标记"这一构造事实，不是靠某次注入测试。

### D-30（流程）真实模型测试仍不进默认门禁，CI 未接入

`docs/17` §5 要求"Linux CI 区分无模型默认门禁与可授权下载模型的集成任务"。本轮做到的是**命令分层**（默认 / `--ignored` + 环境变量），CI 配置文件仍未提交（P3.4 范围）。
