## 0. 执行摘要与正式裁定

**总体裁定：认可 P4 实验工作包已交付，认可第二 NMT 后端插件替换可行性 `go`；认可将本次 ORT + OPUS-MT 候选替换现有 Bergamot 的决定为 `no-go`。P4 整体标记为 `conditional-go`，不表示 P4-G01～G08 全部门禁完整通过，也不表示可以正式发行。**

| 审查项 | 裁定 | 限定条件 |
|---|---|---|
| P4-01～P4-07 开发工作包 | 已交付（接受报告证据） | 应保留两个部分门禁的未闭合状态 |
| 第二真实 NMT 后端 | GO（可行性） | Linux x86_64 CPU，固定候选模型，编译期 feature/Builder 注册 |
| 通过统一 `Translator` API 替换后端 | GO（契约级） | 不等于任意外部插件动态加载、ABI 稳定或热替换 |
| ORT + OPUS-MT 取代 P3 Bergamot | NO-GO | 延迟、内存、长句与片段质量均不理想 |
| P4-G05 执行计划/身份 | 部分满足 | 尚未整合 `plan-v1` / 结果缓存隔离合同 |
| P4-G06 资源安全 | 部分满足 | 无 worker 隔离、租约和对等崩溃恢复 |
| P3 正式发行 | 继续阻断 | G12/G11/G06/G08/D-46 仍 open |
| 进入 P5 | 可以 | 必须记录条件验收及具体承接任务 |

应区分三件事：**工作包完成**、**原定门禁全部闭合**、**候选达到生产替换标准**。本阶段成立的是第一项，以及有限范围内的插件可行性；后两项不成立。`docs/23` §7.3 原定“P4-G01～08 通过”，而 `docs/26` §4.4 明示 G05/G06 仅部分通过。建议将这一差异登记为正式有条件验收，而不是改写历史门槛。

## 1. 审查范围、证据与已实现成果

### 1.1 基线与阶段演进

- **P3 / docs/23**：冻结 P3 语义与性能基线；允许有缺陷编号及回归的 hotfix；P4 目标是验证后端替换，而不是默认寻找更快模型。明确 A 类（同模型同精度）与 B 类（不同模型/精度的产品方案）比较边界。
- **P4-01/02 / docs/24**：`p3-frozen`、冻结 manifest、发行阻断台账和许可状态机；候选为 `ort + opus-mt-en-zh` 的 int8 ONNX；Python PoC 真实出译文，结论 `go-with-caveats`。
- **P4-03/04 / docs/25**：新增 `crates/translator-nmt-ort`、两层 feature、Rust 真实推理、Tokenizer 构建工具和 API 门面；证实无 Bergamot 时仍可调用 `Translator::translate()`；登记无 worker、无缓存等偏差。
- **P4-05/06/07 / docs/26**：新增 13 条真实模型合同测试、修复 `unk_id=None` 静默丢字、开展加载卸载和 100 次翻译观测；最后作出 `conditional-go` / 替换 `no-go` 裁定。

### 1.2 本阶段最有价值的成果

**（A）后端与主 API 解耦的实证。** ORT 引擎通过现有 `TranslationEngine/TranslationPlugin` 契约接入，不修改核心业务路由语义；只挂 ORT 后端亦可完成真实翻译，路由解释和能力枚举可观察。此处证明的是**构建期/注册期可选后端**，不应扩展为“具备动态共享库插件体系”。

**（B）默认依赖隔离。** `nmt-ort` 仅编契约，`nmt-ort-runtime` 才引入 ORT；报告给出的默认 `cargo tree` 中 `ort` 出现 0 次，默认 CLI `ldd` 不出现 `libonnxruntime.so`。`ldd` 只证明动态链接依赖状况，不能单独排除静态链接；结合依赖树，方可支持本项目声明的默认 ORT 隔离。

**（C）真实模型驱动的解码正确性。** 三处 ONNX 陷阱均由真实模型暴露或验证：SentencePiece piece id 与联合词表 id 不同；merged decoder 首步需提供正确长度的 encoder KV；缓存步 encoder KV **不更新但仍需作为图输入提供**。`Missing Input: past_key_values.0.encoder.key` 的失败记录非常有价值。

**（D）测试中发现并修复真实分词缺陷。** `unk_id=None` 曾导致词表外字符静默丢弃；修为 `<unk>` 后不再无声丢 token，却仍不能保证 emoji 等原字符保真。这是“分词器可接受”与“译文保真”两种能力的清晰边界。

**（E）能否替换与值不值得替换分离。** 虽然插件和结构测试通过，仍依据性能、内存及质量差距判定本候选不应成为默认后端，是正确的工程选择。

## 2. 功能、结构与质量审查

### 2.1 结构保真和语义质量必须分开验收

P4 延续 `protect-seg-v1`，受保护的 URL、模板变量、反引号代码等按原字节、顺序、次数拼装。`docs/26` §2.1 报告的结构回归结果支持该项能力。

但实际输出包括：

| 输入 | 报告中的输出示例 | 含义 |
|---|---|---|
| `Hello {name}!` | `你好{name}! ! 你个混蛋!` | 模板保留，但标点碎片生成严重幻觉 |
| `Visit https://example.com/docs today.` | `访问访问https://example.com/docs今天,我还想说` | URL 保留，但出现重复和无关续写 |
| `Run ` + 反引号代码 + ` before committing.` | 出现“运行运行”“承诺前” | 代码结构保留，不代表语义正确 |

**判定：结构保护测试可 PASS；翻译质量不可因此 PASS。** 面向软件本地化、技术文档及代码混排，质量门禁还需考虑否定、数字、术语、特殊 Unicode 和碎片生成。

### 2.2 片段化输入与候选模型的适配问题

当 `protect-seg-v1` 将完整语句拆成 `Hello `、`! See `、` for ` 等碎片，模型失去句法上下文；该候选在纯贪心解码下出现重复直至 token 上限。四层退化抑制（长度上界、无重复 3-gram、三连停、尾部周期收敛）可以缓解循环，但不能重建失去的上下文，亦可能误伤有意重复。

建议将当前抑制保留为**后端私有、版本化的安全策略**，不要继续无限叠规则。内部诊断可以分别记录 `ngram_block`、`repeat_stop`、`tail_trim`、`length_cap`、`eos_reached`，无需增加破坏穷尽匹配的公开 `TranslationWarning` 枚举变体。

### 2.3 词表外字符 D-71

`<unk>` 修复主要解决静默丢词，不保证译文携带 emoji、生僻字或源文中的任意符号。建议在未来所有 NMT 候选的共用测试中加入“非模型词表字符”的正向保真或明确拒绝测试；对必须保留的符号应由核心保护层定义独立规则。此为后续设计建议，**不是要求在 P4 冻结基线上直接修改 `protect-seg-v1` 语义**。

## 3. 性能、内存与可比性审查

### 3.1 B 类对比结果

同机、release、单线程、结果缓存关闭、热模型状态下，`docs/26` 记录：

| 字符数 | P4 ORT 候选 p50 | P3 Bergamot p50 | 比值（约） |
|---|---:|---:|---:|
| 17 | 118 ms | 6.78 ms | 17.4× |
| 94 | 657 ms | 25.05 ms | 26.2× |
| 499 | 2763 ms | 175.67 ms | 15.7× |

热后 PSS 约 **575 MiB**，P3 基线 **332.56 MiB**，约 **1.7×**。模型不同、精度不同、解码链路不同，故**不得把差异归因于 ORT 框架本身**。明确使用“ORT + OPUS-MT 候选组合”而非“ORT 框架性能”描述。

### 3.2 需要解释的跨阶段差异

`docs/24` §2.4 的 Python PoC 对 499 字记录 **830.75 ms**；`docs/25` §2.4 的 Python 参考同档为 **2652.33 ms**；`docs/26` §2.2 的 Rust 最终值为 **2763 ms**。目前不宜解释成确定的性能退化，也不能默认测例等价。建议补全输入文本 hash、源/输出 token 数、EOS、有效 token 上限、分词器 hash、解码策略、benchmark revision 等元数据，再判断差异来源。

### 3.3 资源回收与“长稳”限定

`docs/26` 报告：加载前 RSS 8.5 MiB；加载后 313.8 MiB；三档翻译后 RSS 578.3 / PSS 575.0 MiB；卸载后 RSS 249.0 MiB。另一次 5 轮加载/卸载 + 100 次翻译观测：第 20 与第 100 次均为 RSS 598.0 / PSS 594.7 MiB。

可以支持的结论是：**当前场景中没有观察到持续单调增长，卸载能释放部分资源。** 不能说“内存完全还原”或“已证明无泄漏”。卸载后 RSS 与加载前仍相差约 240 MiB，可能涉及运行库、allocator/arena 或进程堆残留，需要用独立进程生命周期及更长台架进一步分辨。

`ORT_STEADY_BYTES` 从 420 MiB 上调至 600 MiB 是合理的测量修正，但仍为软预算，不是跨模型、输入长度、平台均成立的硬上限。后续预算建议区分加载常驻、翻译峰值、卸载残留和安全余量。

### 3.4 性能术语修订

报告若将“每次重新编码、关闭结果缓存”称为“冷路径”，建议改为**热模型、结果缓存关闭**。推理内部 Decoder KV cache 与 SDK `PlanCache` 不是一回事，必须分别记录，以免混淆基准口径。

## 4. 架构未闭环事项：G05 与 G06

### 4.1 P4-G05：执行计划身份与缓存隔离

ORT 已报告模型资产摘要、runtime build、解码参数、引擎身份等，但尚未接入 `ResolvedExecutionPlan(plan-v1)`，也没有启用 `PlanCache`。因此“目前不串缓存”主要因为**没有结果缓存**，不能代替跨后端缓存隔离合同。

建议在启用 ORT 结果缓存之前设计兼容的计划版本升级（必要时 `plan-v2`）：

1. **模型层**：全部关键资产完整 sha256、Tokenizer、模型 revision、精度和导出版本。
2. **运行层**：engine/runtime ID、runtime build、线程或可影响结果的推理配置、解码策略版本及阈值。
3. **业务层**：语言方向、结构保护版本、规则/术语指纹、隐私域。
4. **测试层**：同文本跨 backend、跨 tokenizer、跨解码配置必须产生不同缓存身份；仅相同完整执行计划才允许命中。

摘要前缀可用于展示，**不得以短前缀代替缓存或完整性校验所需的完整内容摘要**。

### 4.2 P4-G06：执行隔离、取消、租约与恢复

ORT 当前运行在宿主进程，没有 Bergamot 的独立 Worker 故障边界；`timeout_ms` 当前被忽略；未接资源仓库租约、崩溃恢复。应将此判为**部分满足**，不宜称为与 P3 等价的资源安全后端。

推荐在 P5 的基础设施工作中评估统一 `RuntimeTransport`：

```text
Translator API / Coordinator
            |
      RuntimeTransport
        /          \
  InProcess       WorkerProcess
    |               |         |
   ORT          Bergamot     ORT / 其他
```

上述为**建议抽象，不是已实现结构**。明确请求/响应协议、deadline、取消等待与停止计算的区别、故障分类、模型身份、租约及恢复策略。避免未经门禁就重写一套大型通用 IPC 框架。

### 4.3 LC-04 不能用“测试成功”替代超时能力验收

`timeout_ms=1` 仍成功返回的测试，是**已知限制的回归固定**，不是“超时处理已实现”的正向验收。建议将其归到 `EXPECTED_UNSUPPORTED`，并在支持 deadline 后要求替换测试与更新文档。宿主停止等待并不代表底层 CPU 推理被取消。

### 5.2 13/13 通过的准确含义

`p4_contract.rs` 13 条测试包括正向能力证明和不支持/已知缺陷的特征化断言。建议门禁报告区分：

- **PASS**：实现并验证的目标能力，如模板/URL/代码保护、并发加载去重、身份变更、反复加载卸载。
- **EXPECTED_UNSUPPORTED**：Marker 模式明确拒绝、超时未实现、无独立 Worker 等。
- **OPEN / NOT VALIDATED**：租约、安装流程、外部 kill -9、长期并发及高压力长稳。

不能将“拒绝行为被正确验证”表述成“相应功能已实现”。`docs/26` 的 SP 直测与 LC 不适用说明总体清楚，但标题和结论仍应沿用这一分类。

### 5.3 建议补充的覆盖

- 并发 `translate()`、翻译与卸载竞争、不同模型并行加载。
- 长时间、多输入长度、内存压力、错误注入和模型重复切换。
- 固定质量金样本：短完整句、保护碎片、长技术句、否定/数字、混合脚本、emoji/词表外字符。
- 固定评分口径：结构保真率、语义忠实度、异常生成率和人工审核记录。

这属于 P5/P6 或发行前台架建议，不应反向将 P4 已有测试改写成未执行。

## 8. 建议的正式验收表述

建议在 P4 总结或验收记录沿用下列表述：

> **P4 研发交付有条件接受（conditional-go）。** P4-01～P4-07 所要求的第二后端实现、插件契约、结构回归、基准及回退证据已形成；P4-G01/G02/G03/G04/G07/G08 依据现有报告接受，G05/G06 仅部分满足，其未闭合合同明确转入后续工作。验证表明 Rust SDK 可以通过统一契约替换 NMT 后端，但不支持把当前 ORT + OPUS-MT int8 候选作为 P3 Bergamot 的默认替代方案。五项既有发行阻断项继续 open；任何含权重正式发行均需独立满足许可及发布门禁。

## 9. 结论与实施顺序

P4 的核心价值在于**证明后端可替换、保留 P3 默认路径、使失败和差异具有可追溯证据**；其价值不在于这次候选模型的译文质量或推理性能。

推荐顺序：

1. **先完成 P4 文档与台账勘误**：统一编号和“工作包完成 vs 门禁未闭合”的口径；保留 `p4.2` 版本证据。
2. **维持 Bergamot 默认路径**：ORT 仅作实验与兼容性对照，不默认启用，不声称替代成功。
3. **进入 P5 时先明确跨平台执行边界**：执行计划身份、Transport、取消/恢复和测试台架；范围仍应围绕跨平台目标控制。
4. **发行前逐条关闭五项阻断**：不将 P4 的默认 CI PASS 当作 release-mode 的替代证明。

**最终审查裁定：P4 研发验证成果可接受；候选生产替换不通过；P4-G05/G06 与发行阻断项继续明确跟踪。**
