## 2. 实际实现内容

### 2.1 协议：两个版本号，各自独立演进（ADR-010）

v1（P1 词典包，**不改一个字节**）：

```json
{ "schema_version": 1, "id": "...", "version": "...", "kind": "dictionary",
  "provenance": { ... }, "files": [ { "path": "...", "sha256": "...", "bytes": 0 } ] }
```

v2（新增，协议与存储分离）：

```json
{ "manifest_schema_version": 2,
  "payload_schema_version": "dictionary.sqlite.v1",
  "id": "...", "version": "...", "kind": "dictionary",
  "provenance": { ... }, "files": [ ... ],
  "dependencies": [ { "id": "rules.base", "version": "1.0.0" } ],
  "platforms": ["*"] }
```

要点：

- **识别方式不靠"试"**：先看有没有 `manifest_schema_version` 字段决定按 v1 还是 v2 解析。
  同时出现两个字段直接报错——避免"字段拼错的 v2 被当成 v1 解析成功"。
- **未知协议版本直接拒收**（`UnsupportedManifestSchema`），不猜字段含义。
- **未知 payload 版本不被静默接受**：解析阶段保留原字符串（`PayloadSchema::Unknown`），
  由兼容性检查统一拒绝；错误信息里能看到玩家写的那个版本号。
- **v1 的 payload 版本是推断的**：`kind=dictionary → dictionary.sqlite.v1`，
  `kind=rules → rules.json.v1`，其余记成 `Unknown("v1:<kind>")` 并判为不可读。
- `deny_unknown_fields` 全开：多写/拼错字段是错误，不是忽略。

### 2.2 兼容性判定：不理解就拒绝

`compat::check()` 汇总**全部**问题（不是遇到第一个就返回），便于一次看清：

| 问题 | 触发条件 |
|---|---|
| `UnsupportedManifestSchema` | 协议版本不在宿主能力表里 |
| `UnsupportedPayloadSchema` | payload 版本没有对应读取器 |
| `UnsupportedPlatform` | `platforms` 非空且不含 `*` 且不含当前 `os-arch` |
| `KindNotReadable` | `model` / `analyzer` / 未知 kind（本 SDK 尚无读取器） |
| `MissingDependency` | 依赖的 id 不在已安装集合 |
| `DependencyVersionMismatch` | 依赖版本与要求不等 |

依赖检查目前**只做精确版本匹配**，不做 semver 范围求解（理由见 §4.4）。

### 2.3 仓库：安装、激活、回滚、清理

目录布局：

```text
<root>/
├── state.json                      # 唯一可变文件
├── installed/<id>/<version>/…      # 落盘后视为不可变
└── staging/<id>-<version>-<pid>-<nonce>/   # 安装中目录，崩溃后由 recover() 清理
```

`install_from_dir` 的顺序（每步失败都会清掉 staging，且**不动**已装版本）：

1. 读清单（v1/v2 自动识别）→ 校验结构（id/version 可作目录名、sha256 格式、路径安全、payload 文件存在）；
2. 兼容性检查（含依赖）；
3. 复制到 `staging/`（不跟随符号链接，出现链接直接拒绝）；
4. **在 staging 上**逐文件校验大小 + sha256；
5. `rename(staging → installed/<id>/<version>)`（同一文件系统内原子）；
6. 写 `state.json`：临时文件 + `fsync` + `rename`；
7. 若第 6 步失败，回滚删除第 5 步落位的目录（不留下"有目录没记录"的孤儿）。

激活语义（保守，P2.3 之前不做热切换）：

- **首次安装自动激活**；
- 之后安装新版本**不夺取激活位**，`InstallOutcome { activated: false, previous_active }` 明确告知；
- `activate(id, version)` 把旧版本压入 `history`；`rollback(id)` 弹出一个并返回；
- `uninstall` 对激活版本返回 `ResourceInUse`；
- `cleanup(id, keep)` 保留"激活版本 + 最近 keep 个历史版本"，其余删除，**永不删激活版本**。

另有两个刻意的防护：

- `validate_component`：id/version 含 `/ \ : ..` 一律拒绝（否则能构造出写到仓库外的路径）；
- `state.json` schema 不匹配 → `CorruptState`，宁可启动失败也不猜。

### 2.4 规则包：可识别、可迁移、不可执行（ADR-009）

| 操作 | 函数 | 是否执行规则 | 旧包（`pipeline_version: 1`） |
|---|---|---|---|
| 加载执行 | `RuleEngine::from_json/load` | 是 | **拒绝**：`UnsupportedPipelineVersion(1)` |
| 看元数据 | `migrate::inspect(path)` | 否 | ✅ 可看，`executable=false` + 原因 |
| 迁移 | `migrate::migrate_json(json)` | 是（金样本） | ✅ 迁成 v2，**金样本不过就失败** |
| 离线工具 | `migrate-rules <file> [--inspect\|--check\|--out]` | 视参数 | ✅ |

迁移工具实测：

```text
$ migrate-rules /tmp/legacy_rules.json --inspect
id                 rules.demo.legacy
pipeline_version   1
可执行             否
不可执行原因       pipeline_version=1 已废弃（当前 2）：旧语义允许规则改写 URL/邮箱/代码

$ migrate-rules /tmp/legacy_rules.json --out /tmp/legacy_rules_v2.json
迁移完成：rules.demo.legacy@1
pipeline_version   1 → 2
金样本             1 条全部通过
输出               /tmp/legacy_rules_v2.json
```

### 2.5 受保护跨度与严格恢复（ADR-009 的收尾）

- `text::ProtectedSpan { start, end, kind }`，`kind ∈ {Url, Email, TemplateVar, Code}`，
  偏移是**字节偏移**、作用域是**传入 `protected_spans()` 的那份文本**。
  文档明确写了：流水线里传入的是 `normalize()` 之后的文本，因此**不要**把该偏移当作用户原文偏移；
  要映射需要 `normalize_with_map`（未实现，P3 视需要）。`ProtectedSpan` 不外露给 NMT 插件。
- `split_protected()` 与 `protected_spans()` 现在是同一扫描器的两种视图（`protect()` 也基于它）。
- **严格恢复**：`TranslatorBuilder::strict_placeholder_restore(true)` 时，关键占位符未能还原
  直接返回 `IntegrityFailure`，而不是返回缺内容的译文；默认仍是警告（与 P0/P1 一致）。

### 2.6 缓存与资源版本（ADR-011 的前提）

- `CacheKey` 新增 `resource_fingerprint`；`Translator::build()` 把它设为
  `"<dict id>@<version>;<rules id>@<version>"`。
- `Coordinator::bind_resource_fingerprint()` 换指纹时**清空缓存**。
- 当前资源在构建期绑定，换版本等于换 `Translator`（本身就是新缓存）；
  指纹进键是为了将来支持热替换时不静默读到旧结果。

## 4. 与原设计的偏差及原因

### 4.1 P2.2 没有实现租约，因此"热切换"被刻意禁止

评审要求"旧资源正在使用时不强行删除"，但租约在 P2.3。当前做法：

- 安装新版本**不夺取激活位**（`activated=false`）；
- 激活版本拒删；旧版本只能通过显式 `uninstall` / `cleanup` 删除。

**偏差**：因此"激活后旧版本仍在被打开的 SQLite 句柄使用"这一情形，目前只能靠
"删除是显式动作、使用者不会在无提示下被删"来保证，而不是靠引用计数。

**原因**：没有租约时引入自动热切换，等于用一个看不见的时序去赌。宁可少一个能力。

**风险留档**：Unix 上 `unlink` 对 mmap 安全；Windows 上若文件仍被打开，`remove_dir_all`
会失败并返回 IO 错误（不会误删成功）。P2.3 会用租约把这个窗口关掉。

### 4.2 金样本此前并不能代表真实行为（本轮修掉的设计缺陷）

实现迁移工具时发现：`pipeline_version` 的保护逻辑原先只在 `coordinator` 里，
`RuleEngine::verify()` 直接对整段文本跑规则。后果是——

> 一条"把 URL 里的 LLM 也改写"的旧规则，其金样本在引擎层面**能通过**，
> 因为保护发生在引擎之外。

这不是理论问题：迁移测试 `金样本过不了就不产出迁移结果` 一开始拿到的是 `Ok(...)`。

**修法**：把受保护跨度的跳过下沉到 `RuleEngine::run()`（引擎内部切分），
`coordinator::apply_rules` 改为只调用引擎并去重。这样"金样本校验的行为"与"线上行为"
是同一套实现。修完后该测试按预期返回 `SampleFailed`。

**偏差**：`TextRules` 的契约从"给我整段文本"变成"实现者需自己保证不改受保护跨度"，
已在 trait 文档写明；协调器不再重复切分（避免两套行为分叉）。

### 4.3 依赖检查只做精确版本匹配

**偏差**：没有 semver 范围求解，`version` 必须完全相等。

**原因**：现在只有一个真实依赖场景（词典包依赖规则包），版本求解会引入一整套比较器与
"冲突提示"设计；在 P2 阶段属于过度设计。等真的出现 A 需要 1.x、B 需要 2.x 的冲突再引入。

### 4.4 迁移工具只处理 JSON 输入

**偏差**：`migrate-rules` 读的是文本文件；旧**二进制**包只能 `--inspect`，不能直接迁移。

**原因**：二进制是"带校验的传输壳"，其 payload 就是 JSON；先转文本再迁移是两步手工操作。
没做是因为当前没有外部二进制旧包（二进制形态是 P1 才引入的，且从未发布）。
真要支持，只需让 `binary_payload()` 对 `migrate` 公开——已在代码里留了 `pub(crate)` 的公共解析器。

### 4.5 时间戳用 `unix:<秒>`

**偏差**：`installed_at` 不是 ISO 8601，而是 `unix:1793861775`。

**原因**：不想为一行时间戳引入 `chrono`/`time` 依赖（会给 Android 包体加东西）。
排序与相等比较够用；展示层如果要格式化，可以自己做。

### 4.6 缓存指纹是字符串拼接，不是执行计划指纹

**偏差**：`resource_fingerprint = "id@version;id@version"`，而不是 ADR-011 描述的
`ResolvedExecutionPlan` 稳定哈希。

**原因**：执行计划（引擎 + 资源 + 生成配置 + 隐私域）是 P2.4 的内容；本轮只需要
"资源版本变了，缓存必须失效"这一条。字段位置已经留在 `CacheKey` 里，替换实现不需要再改结构。

### 4.7 尚未实现（明确不在本轮）

| 项 | 状态 | 去向 |
|---|---|---|
| 资源租约、single-flight、TTL/LRU、内存预算 | 未实现 | P2.3 |
| 跨进程文件锁（`state.json`） | 未实现（只有进程内 `Mutex`） | P2.3 |
| 磁盘空间预检 / `OutOfBudget` | 未实现（空间不足表现为 IO 错误） | P2.3 |
| 输出侧术语约束、`translate_with_diagnostics` | 未实现 | P2.4 |
| `dictionary.sqlite.v2`（单 SQL） | 未实现 | P2.5（可选） |
| v2 清单的**打包工具** | 未实现（当前只有 v1 打包器 `pack-dictionary`） | P2.5 或随首个 v2 需求 |

> 最后一条要特别说明：`translator-resource` 能**读** v2，但仓库里还没有工具能**生成** v2 包。
> 现在 v2 的测试包是测试代码里现场构造的。这不算"v2 已可用"，只能说"v2 读取路径已就绪"。

| # | 评审验收条件 | 结论 | 证据 |
|---|---|---|---|
| 1 | 旧 v1 词典包能正常查询 | ✅ | §3.2 真实包 install+lookup；`v1旧包可以直接安装`、`真实v1词典包若存在则必须被识别` |

| 5 | 版本切换后不会错误读取旧缓存 | ⚠️ 部分 | `资源指纹不同不得共享缓存` 已覆盖；运行期热切换属 P2.3/P2.4，本轮不做 |
| 6 | 活跃资源不会被强制删除 | ✅ | `激活版本不可删除`、`cleanup只删超出保留数的旧版本` |

第 5 条我给的是"部分"，因为评审要求的是"版本切换后不读旧缓存"，而**切换能力本身**（热替换）
属于 P2.3/P2.4。当前保证的是：换资源 = 换 Translator（新缓存）+ 指纹进键，两者都不允许旧缓存被复用。

## 6. 下一阶段（P2.3）入口

进入 P2.3 时需要在现有结构上加：

1. `ResourceLease`：`acquire(id, version)` 返回句柄 + 引用计数；`uninstall` 在有租约时进入 `Evicting`；
2. single-flight：同一 `id@version` 并发加载只构建一次（`OnceCell`/`Mutex<Option<Arc<…>>>`）；
3. 预算：`ResourceBudget { max_peak_ram, max_concurrent }` + 准入控制 + 触顶回收；
4. 跨进程锁：`state.json.lock`（`flock`/`LockFileEx`），否则两个 CLI 并发安装会互相覆盖；
5. 观测：匿名 RSS / 文件映射 RSS / 峰值 / 租约数 / 推理并发数（ADR-013 要求"不得宣传为硬上限"）。
