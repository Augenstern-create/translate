### 1.2 有条件验收台账（R-02 的核心交付）

`fixtures/p4/acceptance.json`（schema `sdk-p4-acceptance/v1`）把三件事拆开：

- `work_packages`：P4-01～P4-07 的交付状态与证据指针（全部 `delivered`）；
- `gates`：P4-G01～G08 的 `pass` / `partial`，`partial` 必须带 `open_items`；
- `carry_over`：8 条承接项，每条必须有 `priority` / `owner` / `exit_evidence`；
- `release_blockers_reference`：只引用 `fixtures/release-blockers.json` 的 id，**不复制解释**。

`tools/p4-acceptance.py --check` 的规则（写死在代码里，不靠人记）：

1. `status=pass` 的门禁**不得**带 `open_items`；`partial` **必须**带；
2. 每个 `open_item` 必须在 `carry_over` 里存在，且带退出证据（没有退出证据的承接项等于没承接）；
3. `carry_over.from_gate` 必须指向存在的工作包或门禁；
4. 引用到的阻断项必须与台账**完全一致**且仍全部 `open`——不允许在验收文件里"顺手"写闭。

它已接进发行门禁：`check-release.py` 现在是 **C1～C9**（C8 台账、**C9 P4 验收台账**）。

### 1.3 比较方法修正（R-04 的实质）

审查把它当"缺解释"，实测后发现是**方法错误**，比措辞问题严重：

- `docs/24`/`docs/26` 里 Bergamot 的 6.78 / 25.05 / 175.67 ms 来自 `tools/p33-bench` 的固定语料
  （`corpus.rs` 那段"图书馆"长文按词边界截断），**与 ORT 那三句不是同一批文本**；
- 因此"慢 15.7～26.1×"把**文本差异**算进了框架差异里，违反本项目自己写的口径
  （"比较 runtime 时使用同一模型和同一源句"）。

修正动作：

1. 新增 `crates/translator-nmt-bergamot/examples/bergamot_bench.rs`：**逐字相同**的三句、
   同一口径（热模型、`cache_capacity=0`、单线程、p50）、内存按**进程树**合计
   （worker 是 Rust 进程，真正吃内存的是它拉起的 `bergamot` native，按进程名认会漏掉约 280 MiB）；
2. `p4_bench` 升到 `p4-ort-bench/v2`：每档记录 `text_sha256` / `src_tokens` / `src_len_with_eos` /
   `token_cap` / `tokenizer_sha256` / `decode_policy` / `benchmark_revision`；
3. 两边基线文件都入库：`fixtures/nmt/baseline-p4-ort-linux-x86_64.json`、
   `fixtures/nmt/baseline-bergamot-same-texts-linux-x86_64.json`。

### 1.4 顺手修掉的两个测量污染（自查发现）

| 问题 | 现象 | 处理 |
|---|---|---|
| bench 里每档新建一份分词器 | 3.8 MB 的 JSON 词表展开后常驻几十 MiB，直接把 PSS 抬高到 **648 MiB** | 改成**加载权重前**算好元数据并 `drop`，内存回到 **575 MiB**；并在代码里写清为什么不能复用位置 |
| 分词器建在 `engine.load()` 之后 | 同上，且会与引擎自己的分词器叠成两份 | 挪到 `load()` 之前 |

这两条正是审查 §3.3 提醒的"测量工具自己污染被测对象"的具体实例，记录在此以免重犯。

### 2.3 同文本 A/B（修正后）

同一批三句、同一口径、同机（i5-8250U，release，单线程，结果缓存关闭，热模型）：

同文本的质量对照（同一句 94 字符，最能说明问题）：

| | 译文 |

| Bergamot | `翻译质量取决于训练数据、令牌转换和解码参数,因此每次发布时在发货前都必须使用固定的黄金套装进行检查。` |

两者都没把 `golden set` 译对（"黄金套装"也不对），但 Bergamot 的 `training data`/`shipping` 是对的，
ORT 候选把 `training data` 译成"培训数据"、`tokenizer` 译成"代谢器"。**方向性结论不变，证据更硬。**

## 3. 与原设计的偏差及原因

本轮新增/更正的偏差（编号接 `docs/26` 的 D-76）：

| 编号 | 偏差 | 原因 / 影响 |
|---|---|---|
| **D-77** | `docs/25` §5 的三行阻断项含义写错（G06/G08/D-46），`p4.1`～`p4.2` 一直带着错 | 写表时凭记忆补标题，没回查台账。危害不是"读着别扭"，而是**让人误以为某项已有人认领**（G06 取消在途、G08 外部 kill -9 实际没人碰）。已更正 + 留勘误；今后阻断项标题只准从 `fixtures/release-blockers.json` 抄 |
| **D-78** | `docs/24`/`docs/26` 的 A/B 比较用了**不同文本**（Bergamot 来自 `p33-bench` 固定语料），得出 15.7～26.1× / 1.7× | 把文本差异算进了框架差异，违反本项目自己的口径（`docs/01` §12.2）。已用逐字相同三句重测：**10.9～15.0× / 1.63×**。方向不变、倍数作废 |
| **D-79** | 测量工具两次污染被测对象：bench 里每档新建分词器 → PSS 虚高约 70 MiB；Bergamot 侧只读 `/proc/self` → 内存少算约 280 MiB | 前者靠"加载权重前算元数据并 drop"修掉，后者靠 `ppid` 遍历进程树修掉。教训：**测量工具本身要当成被测对象来审**，所以两个例子都把"为什么这么写"钉在代码注释里 |
| **D-80** | `13/13 PASS` 里混着"确认不支持"和"确认已知缺陷" | 措辞问题但有实质危害：读者会把 `lc04`/`d71` 读成"能力已验证"。已按 PASS / EXPECTED_UNSUPPORTED / OPEN 三类出具（`docs/26` §2.1），台账里也分 `status` 与 `expected_unsupported` 字段 |
| **D-81** | `acceptance.json` 里的承接项允许挂在工作包（P4-05/06）而不是门禁上 | 性能台架与质量金样本确实来自工作包而非 G 门禁；校验器因此接受"门禁或工作包"两种来源，但**仍要求退出证据**。写在这里是避免下一轮有人以为校验器漏了一种情况 |
| **D-82** | `OrtIdentity` 增加 `decode_policy` 字段（公开结构体加字段） | 为了 R-07：同一权重换解码策略就是另一个身份，只摘要权重不够（ADR-026）。这是**加字段而非改语义**；宿主若用结构体字面量构造会编译失败，但该类型只由引擎产出，实际影响为零。它也是将来接 `plan-v1` 的原料 |

## 5. 下一阶段建议（采信 `docs/27` §7，落到本项目编号）

1. **P5 先做执行边界**：`plan-v2`（或等价的计划扩展）+ `RuntimeTransport` 的故障/取消合同。
   顺序上先摘要后隔离：没有可信身份，隔离做得再好也说不清"跑的是哪一份"。
2. **不要在这个候选上做性能冲刺**。瓶颈在模型质量与碎片语义，不在运行时；先换候选再谈优化。
3. **质量台架**（金样本 + 人工评分口径）与**长稳/并发台架**应一起立项，否则质量结论永远停在 C 类。
4. **G11（真实 runner）/G12（权重授权）/D-46（许可正文）** 属发行专项，不随 P5 功能推进而关闭。
5. 本轮新增的两个校验器（`p4-acceptance.py`、C9）建议在 P5 继续沿用：**验收口径也要有回归测试**。
