## 0. 结论 / 决议

**决定：冻结 P3 功能基线；P3 功能验收通过，整体状态保留为 `Conditional`；批准进入 P4 的插件替换验证。**

- “冻结”是指**不再往 P3 新增功能、调整对外翻译语义或重构已有稳定路径**；不意味着 P3 已无缺陷、模型可以对外再分发或 Linux CI 已在真实 runner 通过。
- 允许有明确缺陷编号与回归测试的 P3 **安全/正确性修复**，走 `hotfix` → 评审 → 回归 → 回合并，禁止把 P4 实验直接混进冻结基线。
- P4 的核心成果不是“又实现一个更快的模型”，而是**在不修改 `translator-api`、`Coordinator` 和字典/规则业务接口的前提下，替换真实 NMT 后端，证明兼容性、正确性和资源收益**。
- **P4 先开展后端可行性筛选**。不能假设现有 Mozilla/Bergamot 量化权重可直接由 ncnn 或 ORT 执行；若模型不同，只能做“用户体验/部署方案比较”，不得宣称同模型运行时性能优劣。
- P3 未闭合的发行条件应登记在单独的 `release-blockers` 台账，不因开启 P4 自动放宽。

## 1. P3 技术审查：已经证明了什么

### 1.1 P3.1：本地 NMT 真实接线及结构保护

`docs/18` 记录：

1. Linux 上 `translator-api → Coordinator → nmt.bergamot.cli → translator-runtime → nmt-worker → bergamot` 已产生真实英译中译文，不再是 Mock。
2. 默认的 `protect-seg-v1` 把 URL、邮箱、反引号代码和模板变量从模型输入中摘出，按原始字节拼装；`Marker` 模式虽有完整性校验，但真实 Marian 标记存活率不足，**不可作为默认安全路径**。
3. `ResolvedExecutionPlan(plan-v1)` 已包含模型各文件摘要、运行时构建、解码配置、语言方向、规则/术语和隐私域等维度；最初还没接真实缓存，随后在 P3.2 收口。
4. single-flight、排队截止时间和单 in-flight 默认策略已有合同测试，但排队采用锁竞争轮询而非公平 FIFO。

**审查意见**：默认分段结构保护是合理的工程取舍，结构正确 ≠ 译文自然。P4 替换后端时必须把分段策略作为独立、可版本化的业务层保留，不能让后端自由改变受保护文本语义。

### 1.2 P3.2：模型生命周期与资源一致性

`docs/19` 记录：LC-01～10 均有实现与测试；资源反向依赖检查、五个安装崩溃注入点（使用 `abort()`）、状态 `audit/recover`、PID+启动标识的残留回收、模型在飞请求与空闲卸载协调、真实 NMT `PlanCache` 已落地。

**特别注意三项边界**：

- `PlanCacheKey = (plan_digest, target, text_digest)`，缓存只保存成功结果；同一 `model_id` 不足以标识词表、短名单和前缀文件，因此**缓存命中必须根据完整执行计划**。
- `evict_if_idle(ttl)` 是宿主主动调用的 API，**没有后台定时回收线程**；若宿主不调就不会自动卸载。
- 内存预算是加载前的估算/准入控制，不是实际 RSS/PSS 的硬上限。未来换 ncnn/ORT，不能沿用 Bergamot 的固定内存估计值。

**需优先源码复核的潜在缺陷（仅审查疑点，非已证实）**：`docs/19` D-34 提到 `BergamotNmtConfig` 的公开字段理论上可能被加载后修改而不刷新 `plan_digest`。P4 前应验证配置所有权、是否存在共享可变路径及缓存失效测试；若可变，考虑冻结运行配置或使其变更触发新执行计划。

### 1.3 P3.3：性能、内存和质量

以下均来自 `docs/20` 的**单机报告测量**，未在当前审查独立复测：

| 场景 | 数值 / 观察 | 必须附带的口径 |
|---|---:|---|
| 17 / 94 / 499 字热翻译 p50 | 6.78 / 25.05 / 175.67 ms | release、beam=1、native 线程=1、缓存关闭、热模型 |
| 63 字含 2 处保护跨度 | 19.95 ms | 分段为 3 次 native 调用 |
| 并发 1 / 2 / 10 吞吐 | 39.3 / 37.3 / 31.0 rps | 单 worker、单 in-flight、非 FIFO 排队 |
| native 稳态内存 | RSS 340.80 / PSS 332.56 MiB | Linux `/proc`，热态 |
| 卸载前后全进程树 PSS | 340.30 → 3.07 MiB | native 退出；快照无残留 |
| 600 s / 3,000 次 | 0 错误，RSS 348.52 → 349.76 MiB | 仅证明该次长稳；非“绝无泄漏” |
| 自动结构 / 数字事实样本 | 22/22、22/22 | 不能替代人工翻译质量评分 |

**审查判断**：OpenBLAS/OpenMP 线程超订修复应视为关键基线的一部分。P4 不允许拿不同线程约束、不同模型或包含缓存命中的数据与这些数字直接作优劣结论。并发 10 的 p95 高达约 1.18 s，说明公平性仍是限制；但除非妨碍 P4 合同测试，不在本轮对调度器大改。

### 1.4 P3.4：发行链路

`docs/21` 记录：365 passed / 0 failed / 41 ignored，单独运行真实模型 41 passed；许可台账与机器检查器均已编写，本机带权重运行 `check-release.py` 七项 PASS；CI workflow 已写，但没有真实 runner 运行证据。

**重要区分**：

## 2. P3 冻结：执行规范（立即生效的项目决定）

### 2.1 冻结范围

冻结以下行为及接口的**对外语义**：

- `translator-api` 的 `translate / lookup / detect_language / translate_with_diagnostics` 与 `TranslationPolicy`；远程默认禁用。
- 字典结果的释义和来源、不受 NMT 术语强制替换；`TermPolicy::Warn` 默认值。
- `protect-seg-v1` 对受保护片段逐字节保真；保护失败的 `IntegrityFailure` 语义。
- `TranslationEngine` / `InferenceBackend` / `RuntimeTransport` 能力边界；`plan-v1` 的序列化与摘要语义。
- 资源 manifest/payload 双版本、v1 词典只读兼容、资源租约/回滚/对账。
- Linux 单 worker / 单 in-flight 的 Bergamot 性能**基线配置**；不冻结“未来只能单 worker”。

**不冻结**内部实现细节、对 P4 适配器必要的新增类型、测试器和独立插件 crate；但任何对外兼容性变更都需要 ADR、契约测试和明确的迁移方案。

## 3. P4 的目标与非目标（严格按原架构 §13）

### 3.1 正式目标

**P4 = 插件替换验证**。在 Linux CPU 上至少实现一个**可真实推理**的备用 NMT 后端，注册为独立插件，使同一公共 `Translator` API 调用可以选用 Bergamot 与候选后端，并输出统一的兼容性、正确性、质量、性能与内存报告。

核心验收句：**删除/禁用 Bergamot 插件时，主 API 和业务路由不修改；装入备选插件后，能够输出真实译文并通过通用合同测试。**

### 3.2 不包含的任务

- 不做 UI、Android/Windows/macOS 真实移植（它们属于原 P5）。
- 不开发 Remote LLM Provider（原 P6），不把网络翻译作为候选失败后的静默回退。
- 不在 P4 对外分发许可尚未确认的 Mozilla 模型权重。
- 不以实现 ncnn 为名从零训练新模型，或重写整个 Marian Encoder–Decoder，除非可行性验证证明投入合理并单独批准。
- 不因新适配器而破坏 `plan-v1`、字典/术语和结构保护语义。

### 3.3 两种对比类型，必须在报告中分开

| 类型 | 前置条件 | 允许的结论 |
|---|---|---|
| **A. 同模型、同精度/解码策略的运行时对比** | 同一可复现权重与等价 Tokenizer/shortlist、beam、batch、语言对；差异明示 | 有条件地比较 runtime 延迟、内存、加载、卸载与译文一致性 |
| **B. 不同模型/不同量化的产品方案对比** | 同语言对、同语料、质量独立评价、资源规格固定 | 比较用户体验、包体、设备适用性；**不得把性能差异归因于 runtime** |

如果现有 Mozilla `intgemm` 格式不能被 ncnn/ORT 重用，**不得假设转换成功就等价**。要先找可合法获取的原始 checkpoint 或共同可导出的模型，才能形成 A 类报告；否则 P4 可以先做 B 类但必须如实标注，且仍需证明插件替换。

## 4. 后端候选与 P4 技术路线

### 4.1 候选优先顺序（建议，不宣称已验证）

| 候选 | 价值 | 关键阻碍 | P4 决策 |
|---|---|---|---|
| **ONNX Runtime（ORT）+ 可导出的 Marian/OPUS-MT** | 模型转换与验证生态相对成熟；Linux CPU 基线、后续跨平台有价值 | Encoder/Decoder-with-past、特殊 token、量化、动态形状、运行库体积 | **先做“第二后端可行性”候选** |
| **ncnn + 可转换的轻量 seq2seq** | 移动端 CPU/Vulkan、内存分配机制符合长期目标 | Marian 跨注意力、逐 token 解码、KV 缓存、动态形状/算子支持 | **并行做短周期可行性门禁；通过后投入** |
| **CTranslate2 / 其他成熟 Marian runtime** | 作为备选桥梁，容易验证模型格式与译文 | 原生库构建与 Android 支持、体积 | 当 ORT/ncnn 未达到可用条件时启用 |
| Burn / Candle | Rust 原生推理研究价值 | 已有翻译模型可执行链/开发成本未证实 | 本轮不作为强制交付 |

**理由**：ncnn 是长期低内存目标的重要候选，但“必须先有能完整翻译的 seq2seq 适配”是进入优化前提。ORT 通常更适合先验证插件替换和现成模型导出流程；它的最终 RAM 是否优于 Bergamot 同样必须实测。

### 4.2 ncnn 可行性门禁（出现任一关键失败则暂缓，不拖住 P4）

1. 确认目标 checkpoint、许可证与可转换格式，不使用未经授权的闭源模型包。
2. 对模型层逐项检查：embedding / Encoder / Decoder / Cross-Attention / causal mask / KV cache / 动态形状 / 语言 token / EOS / Beam Search。
3. 基于 pnnx/ONNX 转换尝试，保存实际成功/失败日志、算子清单与输入输出张量形状。
4. 对一组固定句子，与原框架逐阶段核对 logits/token 序列；**仅转换成功不是验收**。
5. 实测加载、热翻译、PSS/RSS、线程占用、卸载；内存不优于对照时应说明适配价值。
6. 超出预定探索预算、无正确 Decoder 或无法产生合法译文时，输出 `no-go` 报告，继续 ORT/CT2，而非无限追加 ncnn 适配工作。

建议把上述步骤作为一个明确的**探索门禁**，不是新增 P4-A/B/C 正式阶段。可在同一个 P4 实施报告中记录进展。

## 5. 插件化接口与工程设计

### 5.1 依赖边界（必须保持）

```text
CLI / UI / Rust App
        │
        ▼
 translator-api          ← 不依赖某个具体 native runtime
        │
        ▼
 Coordinator / Engine Registry
        │
        ├── DictionaryProvider + Rule Engine
        │
        ├── LocalNmt TranslationEngine
        │       ├── runtime-bergamot (现有参考实现)
        │       └── runtime-ort / runtime-ncnn (P4 新插件)
        │
        └── RemoteProvider (P6，保持接口预留)

 Resource & Model Manager 作为横向共享依赖
```

可考虑 `translator-nmt-ort`、`runtime-ort` 或 `translator-nmt-ncnn`、`runtime-ncnn` 的独立 crate。默认 feature 仍不拉入 native runtime、模型权重、网络客户端。**具体 crate 名称在确认现有 Workspace 命名后确定，避免为了文档改名。**

### 5.2 建议的兼容描述（示意，不作为已实现代码）

```rust
pub struct RuntimeCompatibility {
    pub runtime_id: String,
    pub model_architecture: String,
    pub model_format: String,
    pub tokenizer_format: String,
    pub supported_precisions: Vec<String>,
    pub supports_decoder_cache: bool,
    pub platform: String,
    pub validated_model_revisions: Vec<String>,
}
```

与 `InferenceBackend::supports_model()` 的返回保持一致：**先明确兼容，再尝试加载**；`RuntimeCompatibility` 只描述声明能力，加载时仍需文件完整性验证、算子检查和运行时初始化。

### 5.3 执行计划必须覆盖替代后端身份

应包含：`engine_id`、`runtime_id`、**runtime build**、权重/Tokenizers/shortlist/prefix 等资产的全文件摘要、解码参数、语言方向、保护策略版本、规则/术语指纹与隐私域。

- 若新后端需要新增字段，使用新的计划 schema（例如 `plan-v2`），不可悄悄改变 `plan-v1` canonical digest 的编码。
- 缓存必须按后端与模型内容隔离：相同文本在不同 backend 下**不得**误命中旧译文。
- 不通过 `model_id` 或“同一个文件夹名”判断可复用。
- 配置必须在模型加载后不可变，或变更触发新执行计划与缓存失效；避免 `docs/19` D-34 所述的配置漂移风险。

### 5.4 Transport 与故障隔离

- Bergamot 基线仍使用独立进程；新 native 后端原则上沿用 `RuntimeTransport` 的进程隔离与错误分类，而不是未经审查在宿主内直接调用 C/C++。
- 若 ORT/纯 Rust 路径确需进程内运行，必须提交**安全边界差异说明**（崩溃影响、内存释放、取消策略）与替代合同测试。
- 不自动重放失败请求、不自动发送远程 LLM；`LocalOnly` 始终离线。
- 维持 stdout 帧协议边界与 stderr 诊断分离；模型加载失败、坏文件、时序错配统一可报告。

### 5.5 资源包及许可

每个模型包注册：文件列表/sha256、来源 revision、真实许可、模型架构/语言对、Tokenizer、runtime 兼容矩阵、实际峰值内存和最低版本。没有验证的兼容性不得标成 `validated=true`。

候选包和 Bergamot 包彼此独立；即使更换后端，也**不能删除仍由旧实例租用的模型文件**。沿用 `ResourceLease`、`audit/recover` 和版本化目录。

## 6. P4 实施工作包（单阶段，避免继续拆碎正式里程碑）

| 工作项 | 工作内容 | 必须交付物 |
|---|---|---|

## 7. P4 验收门槛（建议）

### 7.1 必须全部通过的功能门槛

| 编号 | 测试/验收内容 | 通过条件 |
|---|---|---|
| P4-G01 | 真实备选模型翻译 | 在 Ubuntu CPU 上使用新插件得到真实译文，有来源、校验和、命令、版本 |
| P4-G02 | 插件替换证明 | 禁用 Bergamot 后，无须修改 `translator-api`/Coordinator 代码，仍能通过 `Translator::translate()` 译句 |
| P4-G03 | 插件能力/兼容性 | 不支持语言对、架构、格式返回明确错误；无假兼容 |
| P4-G04 | 结构保护 | SP-01～12；URL/邮箱/代码/模板变量按字节保留，失败显式 `IntegrityFailure` |
| P4-G05 | 模型和运行时身份 | `plan_digest` 覆盖新 runtime、全部模型资产和解码策略；跨 backend 不串缓存 |
| P4-G06 | 资源安全 | 校验失败不启动 native；加载/卸载/租约/崩溃恢复等合同测试通过 |
| P4-G07 | 默认构建隔离 | 没启用候选 feature 时无额外 native 依赖；全部 P3 既有门禁无回归 |
| P4-G08 | 对比与报告 | 分 A 类/B 类、准确标注同模型否、同精度否、同机器否、是否缓存命中；性能报告含 PSS/RSS |

### 7.2 性能门槛与质量门槛

采用与 P3.3 **同一机器、同批句子、同构建档位和明确线程配置**的成对交替测量。报告至少包括：

- 空闲常驻开销、模型文件大小、启动前/加载后/翻译峰值/卸载后 RSS 与 PSS。
- 17/94/499 字热翻译延迟 p50/p95/p99、含保护跨度短句、缓存关闭与缓存命中分开。
- 1/2/10 请求并发与公平性、超时处理、10 分钟长稳、错误率。
- 字节级结构正确、数字事实保留、否定/术语/代码/混合脚本的人工评审；每个模型至少列出已知失败样本。

**初始决策阈值（建议，不是已达成指标）**：替代引擎在质量基本相当且 PSS/延迟没有严重退化时可标 `go`；若某项显著优势伴随重大质量风险，标 `conditional`；无法完成正确 seq2seq 推理或破坏结构/安全契约则 `no-go`。不要凭任意单一百分比自动决定框架优劣。

### 7.3 P4 完成定义

通过 P4-G01～08；留下**可运行的第二引擎插件和对照证据**。若 ncnn 被判 `no-go`，但 ORT/CT2 通过，可视为 **P4 完成、ncnn 研究阶段性关闭**；不要求 ncnn 必须通过才能结束 P4。

如任何替代方案都未能通过，P4 不得假装完成，应明确输出已验证的阻塞点、继续 Bergamot 的风险与下一步替代方向。

## 8. P3 Conditional 项关闭台账（P4 不得遗忘）

| ID | 当前状态 | 关闭证据 | 是否阻塞 P4 开发 | 是否阻塞正式发行 |
|---|---|---|---|---|
| **G12** 权重再分发许可 | 未确认 | 模型具体权重的有效授权/许可文本及审核记录；或采用明确许可的替代模型 | 否 | **阻断含权重发行** |
| **G11** CI runner | 未执行 | 真实 Linux runner 的 workflow run 链接、日志/产物；真实模型 job 单独证明 | 否 | 是，作为既定发行门槛 |
| **G06** 取消在途请求 | 未实现 | 单 in-flight 和排队中取消合同测试；不留 zombie/native 孤儿 | 否 | 是，作为 P3 总验收条件 |

| **D-46** 许可正文 | 缺失 | 官方 MIT/Apache-2.0 正文入库并进制品检查 | 否 | 是，源码/二进制正式发行前处理 |

**判定补充**：不含模型权重的开发者源码/SDK 与“开箱即用含权重离线包”是两种分发模式，许可审核范围不同。不得用“用户自行下载”当作已解决许可证义务的替代证明；应为每种分发模式分别做合规审查。

**机器检查器建议修改方式**：将权重许可状态明确为 `pending → reviewed_allowed/reviewed_denied`，转换必须有来源、审核时间、审核人和具体适用范围；当前所有 pending 一律阻断含权重制品。调整只能在独立发行审查中完成，不能由 P4 测试自动解禁。

## 9. 风险清单与防偏移措施

| 风险 | 后果 | 控制措施 |
|---|---|---|
| ncnn 适配模型算子不完整 | 研究占用整个 P4 | 先 PoC 和 no-go 门禁；保留 ORT/CT2 备选 |
| 同名模型实际权重/Tokenizer 不同 | 错误归因性能差异 | 内容摘要+checkpoint lock；A/B 对比分类 |
| 新后端破坏保护跨度 | 用户数据结构被改坏 | `protect-seg-v1` 由 core 控制，SP 合同测试必须通过 |
| 计划摘要遗漏 runtime/配置 | 跨后端旧缓存污染 | 完整 `ResolvedExecutionPlan`、跨引擎缓存测试 |
| 新库引入更多动态依赖 | 发行难、内存大 | feature gate、`ldd`/包体清单、加载前检查 |
| 高并发下队列饿死 | p95 秒级，移动端体验差 | P4 测试现状并记录；若改 FIFO 必须单独 ADR/回归 |
| 模型许可不明 | 法务/分发风险 | 不入库、不分发权重；license 台账继续禁发 |
| P3 功能基线被实验污染 | 无法可信对照 | 冻结 tag + P4 独立分支 + hotfix 隔离 |
