# P4-03 / P4-04 报告：第二个真实 NMT 后端的实现与插件替换验证

- 日期：2026-11-05
- 阶段：P4-03（实现插件）+ P4-04（插件替换验证）
- 上一阶段：`docs/24`（P3 冻结 + P4-02 可行性门禁，tag `p4.0`）
- 本阶段 tag：`p4.1`
- 结论一句话：**第二个真实后端已经能在同一个 `Translator` 契约下产出真实译文，默认构建仍然零 native 依赖；
  但它是 B 类候选（不同模型、不同精度），质量和延迟都明显差于 P3 的 Bergamot 基线，因此这是"插件替换可行"，
  不是"可以拿它替换 P3 后端"。**

---

## 0. 先划清口径（后面所有数字都受这几条约束）

1. **B 类比较**：本后端的权重是 `Xenova/opus-mt-en-zh` 的 int8 ONNX 导出，与 P3 的 Bergamot 基线
   **不是同一个模型、不是同一个精度、不是同一条解码实现**。凡是拿两者比出来的差异，**不得**归因于
   "ONNX Runtime 比 Bergamot 快/慢"（ADR-045）。
2. **进程内**：本后端跑在宿主进程里，没有像 Bergamot 那样再套一层 worker 进程（ADR-027 的隔离在这里
   **没有**落地，见 D-60）。所以"崩溃带走宿主"这条风险仍然存在。
3. **无缓存**：`PlanCache` 没接（D-62）。下面所有延迟都是"每次独立编码 + 贪心解码"的冷路径。
4. **单线程**：`intra_op_threads=1`。门禁阶段已测过加线程几乎无收益（`docs/24` §2.4），本阶段没有重复测。
5. **内存是进程数**：Rust 侧 RSS/PSS 含 ORT 静态链接进来的运行库与 int8 权重，**不能**与 Python 侧数字
   直接对消（Python 那份还带着解释器和 torch 的残留页）。

### 1.2 三个 ONNX 陷阱在 Rust 侧怎么落的

门禁阶段（`docs/24` §1.4）记下的三条，在 Rust 实现里各自对应一处**带断言**的代码：

| 陷阱 | 落法 | 证据 |
|---|---|---|
| `source.spm` 的 piece id ≠ 模型 id | 不调 `*.spm`，改用按 65,001 项联合词表构造的 `tokenizer.json`；并在测试里钉死 `Hello world!` → `[3828, 431, 50]` | `分词器id空间对齐联合词表` |
| merged decoder 首步 encoder K/V 必须给真实 `src_len` | 首步用 `initial_past(src_len)` 造 24 个 `past_key_values.*` | `g01_真实模型产出译文` |
| 缓存步的 `present.*.encoder.*` 是 0 长度占位 | 只在 step 0 取一次 encoder 缓存并**固定**，之后每步照喂（但不再更新） | 见下 |

第三条在本阶段**第一次写错**并被真实模型打回，值得记下来：

- 第一版逻辑是"step > 0 时跳过 encoder 侧 present"，于是 step 2 的 feed 里**完全没有** encoder 缓存，
  ORT 报 `Missing Input: past_key_values.0.encoder.key`（`Reshape_2` 上失败）。
  原因：合并解码器把 encoder 缓存声明成**图输入**，两个分支共用，少喂一个直接崩；
  "不回喂"的正确读法是"**不更新**"，不是"不提供"。
- 修法：`enc_past` 单独保存 step 0 的输出，之后每步都喂它，但只用 decoder 侧 present 更新 `past`。

### 1.3 退化抑制：本阶段唯一一处"超出最小可用"的实现

**现象**：受保护跨度分段（`protect-seg-v1`）会把句子切成 `Hello `、`! See `、` for `、` options.`
这种碎片。同一个碎片喂给这个模型，贪心解码会一路重复到撞上 token 上限：

```
Hello {name}! See https://example.com/a for `cargo test` options.
  修复前 -> 你好 你好 你好 …（97 次）{name}看见没?https://example.com/a用于`cargo test`选项。
```

**先确认这不是我这个解码循环的 bug**：同一份权重、同一套 inputs 在 Python 参考实现里跑出**同样的 64 次重复**
（`fixtures/p4/python-merged-parity.json` 同源脚本，见 §2.6）。而 P3 的 Bergamot 在同样的分段下给出
`你好 {name}您的订单 {order_id} 已经发货了。`——所以这是**本候选模型 + 纯贪心**的组合缺陷，不是"中文就长这样"。

**做了什么**（四层，全部确定性、不含模型调用）：

| 机制 | 规则 | 目的 |
|---|---|---|
| 长度上界 | `cap = min(max_new_tokens, src_len*8/5 + 12)` | 碎片最多跑到源长的 1.6 倍 |
| 无重复 n-gram | 生成 3-gram 与历史重复的候选**不参与**竞争（全被禁时退回原始 argmax） | 不让循环自我强化 |
| 三连停 | 连续 3 个相同 token 立刻结束解码 | 省掉无意义的解码步 |
| 尾部收敛 | 尾部同周期块连续 ≥3 次、周期 ≤4 时砍到只剩一轮 | 把 `你好×3` 收敛成 `你好` |

**代价（必须说清）**：

- 阈值是**工程选择**（3-gram / 3 连 / 1.6 倍），不是模型契约。真实的"有意重复"（例如连续强调）会被误削；
  出现两次的重复（`哈哈`）不动，这是我们选的保守边界。
- 抑制会让模型**转向次优 token**，输出可能比"重复"更莫名其妙（实测出现过 `你好 你好 你好 ▁ 你好 你好` 的锯齿形，
  才加了"三连停 + 尾部收敛"）。
- 触发次数记在 `OrtNmtEngine::degeneracy_count()` 上，**没有**加 `TranslationWarning` 变体：
  给公开枚举加变体会破坏宿主的穷尽匹配（这条在 P3 已定），因此可观测性放在引擎句柄上。

### 1.4 契约与拒绝路径（全部显式失败，不静默降级）

| 情况 | 行为 |
|---|---|
| 缺 `encoder/decoder/tokenizer.json` | 构造期就失败，**一次报全**缺哪几个（`ResourceNotInstalled`） |
| `ProtectionMode::Marker` | 构造期 `CapabilityUnavailable`，并在消息里指名"请用 protect-seg-v1" |
| 语言对不匹配（含直接持有引擎句柄、绕过 Coordinator） | `CapabilityUnavailable`，消息里写出"本引擎只做 en → zh-Hans" |
| 空文本 / 全空白 | `InvalidRequest`，不把空串当译文返回 |
| 同一 `engine_id` 挂两次 | `build()` 失败（`InvalidRequest`，消息含「重复」），不会悄悄开两份会话 |
| 未开 `ort-runtime` 却调用 | `CapabilityUnavailable`，消息写明"本构建未启用 ort-runtime feature" |

第 3 条是**本阶段新加的**：门禁阶段只靠 `supports()` 把关，但宿主可以直接持有引擎句柄调 `translate()`，
此时若语言对不符，结果会被贴上错误的 `source` 标签——这是"看起来成功"的错，必须报错。

### 1.5 默认构建隔离（P4-G07 的做法）

两层 feature，默认构建不碰 ORT：

```
translator-api/nmt-ort          -> 只编契约（无 ort 依赖）
translator-api/nmt-ort-runtime  -> nmt-ort + translator-nmt-ort/ort-runtime（链接 ORT）
translator-nmt-ort/ort-runtime  -> dep:ort + dep:ndarray
```

实测：`cargo tree -p translator-api --edges normal` 在没有 feature 时 **19 行、`ort` 出现 0 次**；
开 `nmt-ort-runtime` 后同一条命令是 **165 行**。默认构建的 `translator-cli` 二进制 `ldd` 里没有
`libonnxruntime.so`（ORT 是静态链接进示例二进制的，`p4_bench` 因此有 33 MB）。

### 1.6 资产与工具

- 运行时只需要 3 个文件：`encoder_model_quantized.onnx`、`decoder_model_merged_quantized.onnx`、
  `tokenizer.json`（前两个来自候选锁定文件，第三个由 `tools/p4/build-tokenizer.py` 生成）。
- 该工具做两件事：按 `vocab.json` 的 id 顺序建 Unigram 词表（分数借 `source.spm` 的 piece score，
  `</s>`/`<unk>` 记 0.0、其余缺省 -10.0），以及**在任何输出之前**先用 `[3828, 431, 50]` 自检 id 空间。
  用同一份输入重跑，产出的 `tokenizer.json` 与门禁阶段用的是**语义等价**的（JSON 逐键相等）。

### 2.4 延迟与内存（release、单线程、无缓存）

同文本、同 token 上界公式下，Rust 插件与 Python 参考实现（merged decoder）的对照——
这一栏回答的是"我的 Rust 实现有没有写歪"，**不是**"运行时哪个快"：

| 用例（字符数） | Rust 插件 p50 | Python 参考 p50 | 输出是否逐字节相同 |
|---|---|---|---|
| 17（`The library opens at 9.`） | **123 ms** | 120.03 ms | 相同（`图书馆9点开放`） |
| 94 | **653 ms** | 651.29 ms | 相同 |
| 499 | **2752 ms** | 2652.33 ms | **不同**（见 D-68：尾部空格导致分词差一个 `▁`） |

内存（同一进程、同一用例序列）：

| 口径 | Rust 插件 | Python 参考 |
|---|---|---|
| 加载前 RSS | 8.4 MiB | — |
| 加载后 RSS | 313.6 MiB | — |
| 跑完三档后 RSS / PSS | **578.1 / 574.8 MiB** | 877 / 870 MiB |
| 单次加载耗时 | 1301 ms | — |

与 P3 基线的距离（B 类，**不可归因于 runtime**）：

| 指标 | 本后端（Rust, 1 线程） | Bergamot（P3 基线） | 倍数 |
|---|---|---|---|
| 17 字 p50 | 123 ms | 6.78 ms | 18.1× |
| 94 字 p50 | 653 ms | 25.05 ms | 26.1× |
| 499 字 p50 | 2752 ms | 175.67 ms | 15.7× |
| 稳定内存（PSS） | 574.8 MiB | 332.56 MiB | 1.7× |

（Bergamot 那列来自 `docs/21`/`docs/24` 的同机实测，模型不同、精度不同，见第 0 节。）

### 2.4.1 关于 `docs/24` 的 830.75 ms 与本文 2652.33 ms 的差异（`docs/27` R-04）

这两个数字**不是同一次实验的两次读数**，不能拿来判断"有没有性能退化"。实测拆解（`fixtures/p4/explain-499-token-budget.json`，
同一文本、同一权重、同一 1 线程）：

| 变体 | p50 | 对应文档 |
|---|---|---|
| split decoder（`encoder` + `decoder` + `decoder_with_past`），`nmax=40` | 828.09 ms | `docs/24` §2.4 的 830.75 ms |
| merged decoder，`nmax=40` | 837.72 ms | ——（说明**解码图不是差异来源**，差 1%） |
| merged decoder，`nmax=192` | 2675.56 ms | 本文 2652.33 ms / `docs/26` 2763 ms |

结论：差异来源是 **token 预算**（40 步 vs 131 步），近似线性于解码步数。`docs/24` 那份 Python PoC 的
`tr()` 默认 `nmax=40`，所以 499 字那档其实是"被截断的快速测量"。P4 之后所有基线文件都带
workload 元数据（`text_sha256` / `src_tokens` / `token_cap` / `tokenizer_sha256` / `decode_policy` /
`benchmark_revision`），这类误读不再靠人记。

### 2.5 质量：本阶段最该被记住的部分

同一批输入的实际译文（`g01`、`p4_bench`）：

| 输入 | 输出 | 备注 |
|---|---|---|
| `The cat is on the table.` | `猫在桌子上` | 好 |
| `The library opens at 9.` | `图书馆9点开放` | 好 |
| `Translation quality depends on training data, tokenizer and decoding parameters…` | `翻译质量取决于培训数据、代谢器和解码参数…` | `training data`→培训数据、`tokenizer`→代谢器（门禁阶段已记录） |
| `A translation engine that runs entirely on the device…` | `…内存储由模型重量决定, 模型重量在负载时间固定…` | `model weights`→模型重量、`load time`→负载时间：**词对词硬译**，不是能用的人工译文 |

结论：**这个候选在短句上可用、在长句上不可用**。它证明的是"插件能换、结构保护不受影响"，
不是"质量够交付"。

## 3. 与原设计的偏差及原因

| 编号 | 偏差 | 原因 / 影响 |
|---|---|---|
| **D-60** | 第二后端**跑在宿主进程内**，没有 worker 隔离（ADR-027 未落地） | ORT 的失败模式与 Marian CLI 不同（它不 `abort`），但"进程崩溃带走宿主"的风险仍在。做隔离要么再写一层 IPC worker（P3 那套协议目前是 Bergamot 专用形状），要么等 P5 统一 worker；本阶段选择先验证"契约能换"，把隔离作为未完成项记在这里，不宣称已满足 ADR-027 |
| **D-61** | `ProtectionMode::Marker` **未实现**，构造期即拒绝 | 门禁阶段试过：把跨度替换成 `<0>`/`<x0>` 这类哨兵，模型**会**原样吐出来，但位置会漂、还会重复（实测 `您好 <x0>! <x1> 选项的 <x2> 选项请见 <x1> 。`）。宁可不支持，也不做"看起来支持"的假兼容 |
| **D-62** | **没有缓存**，也没接 `plan-v1` 摘要（P4-G05 只部分满足） | `OrtIdentity` 已给出 `model_revision`（三文件 sha256 前 16 位）、runtime build、线程数、token 上限，具备拼进计划摘要的原料；但把 `plan-v1` 的 14 个字段扩到"覆盖第二个 runtime + 解码策略"要动 `PLAN_SCHEMA`（ADR-035 规定改字段必须升版本），属于跨后端语义变更，不在本轮硬塞 |
| **D-63** | `timeout_ms` **被忽略**，也没有取消在途请求 | 进程内单线程解码是串行的，取消需要 volatile 标志 + ORT 侧没有可用的中断点；Bergamot 那份是"取消等待、不释放 native"，这里没有对等物。宿主要设超时只能在外面等 |
| **D-64** | `ORT_STEADY_BYTES` 从门禁阶段的 **420 MiB 上调到 600 MiB** | 门禁时是照 Python 宿主 RSS 折算的估计；Rust 进程内实测跑满长句后 PSS 574.8 / RSS 578.1 MiB。准入估计**偏低**会让宿主高估可用内存，所以按实测上调 |
| **D-65** | 退化抑制（长度上界 + 无重复 3-gram + 三连停 + 尾部收敛）是**本后端自己的**解码策略 | 见 §1.3。三条阈值都是工程选择，会误伤有意重复、也会把输出推向次优 token；触发次数可观测（`degeneracy_count()`），但**没有**进 `TranslationWarning`（加变体会破坏宿主穷尽匹配） |
| **D-66** | `tools/freeze-manifest.py --check` 的 `Cargo.lock` 判据**改成按冻结提交比**，并新增 `DRIFT` 行 | 原实现拿工作区 `Cargo.lock` 和冻结摘要比。P4 合法新增了 `ort`/`tokenizers`，第一次正常前进就会误报——冻结承诺的对象是 tag `p3.4` 那个提交，不是"HEAD 永不变"。不改这条，冻结校验会退化成"禁止前进" |
| **D-67** | 许可证白名单新增 `CDLA-Permissive-2.0`，第三方包数 **53 → 152** | 新依赖 `ort-sys` 的 **build-dependency** `ureq` 需要根证书数据（`webpki-root-certs`）。CDLA-Permissive-2.0 是数据许可、无 copyleft、只要求保留声明，且**只在构建期**用于下载 ORT 预编译包，不进发行产物。包数大涨主要是 `tokenizers` 带来的 |
| **D-68** | 分词桥接**不是**原 SentencePiece 流程的严格等价 | `tokenizer.json` 是"按联合词表重建的 Unigram"，分数借 `source.spm`。实测 17/94 两档输出与 Python 参考逐字节相同，499 那档在**尾部空格**上差一个 `▁` token，译文随之后续分叉（`完全运行在设备上` vs `完全运行于设备上`）。要彻底消除得改文本（剥尾空格），本轮选择**不改用户文本**，只记录差异 |
| **D-69** | 没挂词典时 `lookup()` 返回**空表**而不是 `CapabilityUnavailable`（P1 既有行为，本轮未改） | 这是观察项，不是本阶段引入的。ADR-003 只要求"查词与翻译分开建模"，没有规定"无 provider 必须报错"。要改它是 P1 的契约变更，需单独决策 |
| **D-70** | 构建期需要网络（或本地 ORT 缓存 / `ORT_LIB_LOCATION`） | `ort-sys` 的 build script 会下载 ORT 预编译包。默认构建不受影响（feature 没开），但"离线可构建"的承诺在 `nmt-ort-runtime` 这条路径上**不成立**，CI 里也没有为它准备缓存 |

## 6. 下一阶段建议（按优先级）

1. **先把 P4-G05 补上**：把 `OrtIdentity` 接进 `plan-v1`（升 `PLAN_SCHEMA`），否则第二后端一开缓存就会串味；
   接好之后再看要不要给 ORT 加缓存——它现在每次都是冷路径，缓存收益比 Bergamot 更大。
2. **质量优先于性能**：本候选的长句译文不能用（§2.5）。要么换一个中文侧更强的候选（仍走门禁），
   要么把"片段级翻译"升级成"整句 + 哨兵占位"，但后者必须先解决哨兵漂移（D-61）。
3. **worker 隔离（D-60）** 应作为 P5 的统一议题，而不是给 ORT 单独再抄一套 IPC。
4. **离线构建（D-70）**：给 `nmt-ort-runtime` 准备 ORT 本地缓存/镜像，否则 CI 里这条路径不可复现。
5. 冻结清单的 `DRIFT` 行（D-66）建议在 P5 引入"基线漂移需签字"的台账位，避免 DRIFT 被当成噪音。
